## 摘要
基于 NAND 的存储提供了扩展 LLM 前缀缓存所需的容量，但其块 I/O 路径除 NAND 延迟外，还会引入 CPU 缓存争用和主机 DRAM 暂存开销。我们的表征表明，即使以 DRAM 作为存储介质，这些接口成本仍然存在，这促使我们采用 CXL-SSD 来实现对基于 NAND 的容量的字节寻址访问。然而令人惊讶的是，现成 CXL-SSD 仍比本地 DRAM 慢约 3 倍，且并不比 NVMe SSD 更快，而通用预取几乎无益。我们提出 LM-CXD，一种专用于 LLM 前缀缓存的 CXL-SSD。LM-CXD 弥合了服务引擎与设备之间的语义鸿沟：服务引擎知道哪些 KV 块将被使用，而设备控制其放置与移动。它将 KV 块变为设备可见的 I/O 单元，向服务引擎暴露 NAND 到 DRAM 的进度，并将设备 DRAM 用作 GPU 可访问的缓冲区。LM-CXD 进一步将请求调度与窗口化预取协调起来，并将逐层 KV 移动与 GPU 计算流水化，以在有限的设备 DRAM 下隐藏 NAND 延迟。在五个 LLM 模型上，LM-CXD 相比现成 CXL-SSD 将平均 TTFT 最多缩短 2.6 倍（采用计算异步预取）和 4.03 倍（采用逐层预取），平均 TTFT 达到本地 DRAM 的 1.5 倍以内。

## Abstract
NAND-backed storage offers the capacity needed to scale LLM prefix caching, but its block I/O path incurs CPU cache contention and host-DRAM staging in addition to NAND latency. Our characterization shows that these interface costs persist even with DRAM as the storage medium, motivating CXL-SSDs for byte-addressable access to NAND-backed capacity. Surprisingly, however, a stock CXL-SSD remains about 3$\times$ slower than local DRAM and no faster than an NVMe SSD, while generic prefetching provides little benefit. We present LM-CXD, a CXL-SSD specialized for LLM prefix caching. LM-CXD bridges the semantic gap between the serving engine, which knows which KV chunks will be consumed, and the device, which controls their placement and movement. It makes KV chunks device-visible I/O units, exposes NAND-to-DRAM progress to the serving engine, and uses device DRAM as a GPU-accessible buffer. LM-CXD further coordinates request scheduling with windowed prefetching and pipelines layerwise KV movement with GPU computation to hide NAND latency under limited device DRAM. Across five LLM models, LM-CXD reduces average TTFT over a stock CXL-SSD by up to 2.6$\times$ with compute asynchronous prefetching and 4.03$\times$ with layerwise prefetching, achieving TTFT within 1.5$\times$ of local DRAM on average.

## 一、核心问题与整体含义（研究动机与背景）

### 1.1 背景：LLM 前缀缓存的容量瓶颈

- **前缀缓存（Prefix Caching）** 是 LLM 服务中减少冗余 prefill、降低 TTFT 的关键技术。RAG、多轮对话、自主 Agent 等应用会反复复用系统提示词、检索文档和对话历史，形成数万到数十万 token 的前缀。
- LMCache 等系统将 KV 缓存从 GPU 显存扩展到主机 DRAM 与存储层，但 **主机 DRAM 容量受限于内存通道和 DIMM 容量**，随着模型规模、上下文长度和并发量增长，将大规模前缀缓存常驻 DRAM 变得不切实际。

### 1.2 问题：块存储的三大固有开销

作者对前缀复用工作负载进行表征（§3.1），发现 NVMe SSD 导致 TTFT 严重退化的三个成本：

1. **CPU 缓存争用**：块 I/O 引入的 I/O 线程与推理线程共享 LLC，隔离其缓存可将 P99 TTFT 降低最多 **44%**。
2. **主机 DRAM 暂存**：块接口强制每个 chunk 先经过主机 DRAM，GPU 无法避免这次 staging copy；即使介质换成 DRAM（ramdisk），仍比直接 DRAM 慢 **1.8×**。
3. **NAND 延迟本身**：占 SSD 减速的一半以上；用 DRAM 替换 NAND 可弥合 SSD 到直接 DRAM 差距的 61%。

### 1.3 关键洞察：块接口的成本与介质无关

- 这些接口成本**并非由存储介质决定**：ramdisk 保留块接口后依然慢 1.8×，说明块接口本身是根因。
- **GPUDirect Storage（GDS）** 虽然绕过了 CPU 和主机 DRAM，但数据仍需先读入 VRAM 暂存缓冲区，再由 `load_and_reshape` 内核重排到 vLLM 的 KV 布局——只是把块接口的成本搬到了 GPU 和 VRAM 中，并未消除。

### 1.4 CXL-SSD 的机会与语义鸿沟

- CXL-SSD 结合 CXL Type-3 内存接口与 NAND + 片上 DRAM 缓存，提供**字节可寻址**访问，理论上可消除块接口。
- 但作者表征发现：**现成 CXL-SSD 仍比本地 DRAM 慢约 3×，且不比 NVMe SSD 更快**；通用 next-n 预取几乎无益，甚至增加无效 NAND I/O。
- 根本原因在于**语义鸿沟**：服务引擎知道哪些 KV chunk 将被消费，设备控制 chunk 的放置与移动，但二者之间缺乏共享接口。设备只收到地址而非 chunk 语义，服务引擎只在移动完成后才获知进度。

## 二、方法论：LM-CXD 的核心思想与关键技术

### 2.1 核心思想

将 **KV chunk 作为 CXL-SSD 索引、移动、报告进度和传输到 GPU 的基本单元**，构建服务引擎（vLLM + LMCache）与设备之间的**双向共享接口**，形成跨层存储协同设计。

### 2.2 三大设计原则

| 原则 | 内容 | 对应挑战 |
|------|------|----------|
| **P1** | 通过轻量级共享数据结构暴露设备状态，实现跨层协调 | DRAM/NAND 划分仅在设备内可控，推理状态仅在主机侧 |
| **P2** | 使 KV chunk 成为设备可见的 I/O 单元 | CXL-SSD 无 chunk 概念，且逐层推理按层而非按 chunk 读取 |
| **P3** | 在有限设备 DRAM 下隐藏 NAND 延迟 | 设备 DRAM 相对 NAND 容量很小，多会话/张量并行/写路径竞争 |

### 2.3 共享数据结构（位于设备 DRAM 保留区，无锁）

- **Prefix Lookup Table**：chunk hash → 虚拟地址映射，并标记是否已加载到 DRAM。
- **Pin Map**：将 LMCache 的 pin 状态传递给设备，被 pin 的 chunk 在 CLOCK 淘汰中跳过。
- **Free Queue**：传递 chunk 删除操作。
- **Prefetch Queue**：LMCache 在 lookup 时将 chunk hash 入队，设备端交叉引用查找表判断是否已在 DRAM。
- **Prefetch Plan Pool**：仅用于逐层预取，每个活跃会话按 GPU rank 注册计划，记录预取进度。

### 2.4 基本 I/O 流程

- **写路径**：更新查找表 → 写入 chunk write buffer（CXL DRAM 写速、字节粒度）→ 达到容量阈值时 CLOCK 淘汰至 NAND → 更新元数据。
- **读路径**：查查找表 → DRAM 命中直接访问；DRAM 未命中则从 NAND 读入 chunk read buffer → 更新查找表。
- 支持 **CUDA 直接内存映射**（`cudaHostRegister`），允许从任意内存地址 DMA 到 GPU，无需经过主机 CPU DRAM。

### 2.5 Chunk 访问语义

- 以 **2MiB 大页**为最小 I/O 单元，支持多页 chunk。
- 淘汰时按 NAND 擦除块粒度对齐，chunk 的多个大页跨两个擦除块条带化；**KV 缓存可再生，因此擦除行中的活跃 chunk 直接丢弃而非迁移，仅发擦除命令，不做垃圾回收**。

### 2.6 两种预取方法

#### （1）计算异步预取（CAP）

- **提示协议**：LMCache 提交 chunk hash 作为 hint → 设备在查找表中解析 → 递增队列 HEAD 并 pin 住大页防淘汰 → 发起 NAND 读 → 读完成后更新查找表 → 对已预取到 DRAM 的 chunk 执行 DMA 到 VRAM 并 unpin。
- **窗口化 pin 与 DMA**：预取的 chunk 按固定窗口大小分批 pin 和 DMA，下一窗口在另一窗口 unpin 时启动，由 per-rank pin 预算决定窗口大小与深度。
- **非阻塞提交与调度**：将请求调度在 vLLM 的 `WAITING_FOR_REMOTE_KVS` 状态，提前分配 GPU KV 块；当两个窗口的 chunk 被 dispatch 后发出就绪信号，允许在其他会话计算期间主动 DMA。
- 所有交互均为对设备 DRAM 的小型 store 操作，**无系统调用、无中断、无大数据拷贝**。

#### （2）逐层预取

- **Chunk Major → Layer Major 转换**：chunk 按 chunk-major 布局存储（包含所有层），逐层访问需要 layer-major 视图；LM-CXD 在 DRAM 专用缓冲区中完成转换。
- **Lookahead DRAM Buffer**：指定 layer-major 区域兼作 n 深度前瞻缓冲区，让 NAND I/O 领先于层消费；预取深度、并发会话数和前缀长度共同决定缓冲区大小。
- **DMA 优化**：使用 `cudaMemcpy3DAsync` 的 strided descriptor 直接表达布局变化，避免额外转置操作，key/value 各一次。
- **Prefetch Plan 提交**：每个请求在调度推理时提交计划，记录 chunk hash、当前层预取状态和下一层预取目标，完成后移除。
