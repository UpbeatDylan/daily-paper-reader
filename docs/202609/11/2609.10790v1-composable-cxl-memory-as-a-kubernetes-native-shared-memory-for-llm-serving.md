## 摘要
我们提出了一种 Kubernetes 动态资源分配（DRA）驱动，使可组合 CXL 内存成为可调度的集群资源，并评估由此得到的共享内存层级在 LLM 服务中用于跨节点 KV 缓存复用的效果。该驱动按需组合 CXL 区域，将其在各参与主机上具体化为 DAX 设备，并以单个容器设备接口（CDI）名称注入 Pod，从而使不同节点上的 Pod 能够访问同一物理区域。面向 vLLM/llm-d 的共享内存连接器将该区域用作 KV 缓存层级，并将槽位目录嵌入共享介质内部，从而无需外部元数据服务。在一个配备 512 GiB CXL 设备和 Qwen2.5-7B-Instruct 的两节点集群上，当外部命中率为 95.4--99.5% 时，跨节点前缀复用将 TTFT 降低 5.5× 至 36.6×，而节点本地层级（GPU 前缀缓存、CPU-DRAM 卸载）则回退为完全重计算。共享差距定义为跨节点复用与同节点复用之间的延迟比，为 1--4%，表明在我们的测试平台上，跨节点复用相对于同节点复用仅带来很小的额外延迟。两个副本均运行完整引擎；该研究展示的是内存解耦，而非预填充/解码解耦。我们将其作为可行性研究而非性能评估来报告。

## Abstract
We present a Kubernetes Dynamic Resource Allocation (DRA) driver that makes composable CXL memory a schedulable cluster resource, and evaluate the resulting shared-memory tier for cross-node KV-cache reuse in LLM serving. The driver composes CXL regions on demand, materializes them as DAX devices on each participating host, and injects them into pods under a single Container Device Interface (CDI) name so that pods on different nodes access the same physical region. A shared-memory connector for vLLM/llm-d uses that region as a KV-cache tier with a slot directory embedded inside the shared medium, which eliminates the need for an external metadata service. On a two-node cluster with a 512\,GiB CXL appliance and Qwen2.5-7B-Instruct, cross-node prefix reuse reduces TTFT by 5.5$\times$--36.6$\times$ at an external hit rate of 95.4--99.5\,\%, while node-local tiers (GPU prefix caching, CPU-DRAM offload) fall back to full recompute. The sharing gap, defined as the latency ratio between cross-node and same-node reuse, is 1--4\%, indicating that cross-node reuse incurs little additional latency relative to same-node reuse on our testbed. Both replicas run full engines; the study demonstrates memory disaggregation rather than prefill/decode disaggregation. We report this as a feasibility study rather than a performance evaluation.

# 论文总结：可组合 CXL 内存作为 Kubernetes 原生共享内存用于 LLM 服务

## 1. 核心问题与整体含义

- **背景**：自回归 LLM 服务中 KV 缓存既带来加速也带来成本。以 Qwen2.5-7B-Instruct 为例，每个被注意的 token 留下 56 KiB KV，32K token 前缀即 1.75 GiB。多轮对话、RAG、Agent 工作流中大量共享前缀可通过前缀缓存跳过重算。
- **核心矛盾**：现有 KV 复用层级无法同时满足"大容量"与"可跨节点共享"两个属性：
  - GPU VRAM：最快但最小，且绑定单卡；
  - 主机 DRAM：大一个数量级但局限于单节点；
  - RDMA/对象存储：可共享，但每次复用都需经过传输协议与网卡。
- **缺失环节**：CXL 提供第四种选择——可组合内存设备可将区域同时映射到多台主机，字节可寻址、无传输层。但 **Kubernetes 缺少能表达该拓扑的资源类型**：Pangaea v2 仅按主机粒度接入，近期 CXL-KV 系统均假设区域已存在；没有可调度资源，共享 CXL 内存无法在租户间复用或在拆除时回收。
- **整体含义**：本文把"可组合 CXL 内存"做成 Kubernetes 一等可调度资源（DRA），并验证其作为 LLM 服务跨节点 KV 缓存共享层的可行性。作者明确定位为**内存解耦（memory disaggregation）而非 P/D 解耦**的可行性研究（feasibility study），而非性能评估。

## 2. 方法论

### 2.1 核心思想
- 用 Kubernetes DRA（`resource.k8s.io/v1`）驱动把 CXL 刀片容量广告为可调度资源，按需组合区域、在各主机具体化为 DAX 设备，并以**同一个 CDI 名称**注入不同节点上的 Pod，使跨节点 Pod 访问同一物理区域。
- 在 vLLM/llm-d 的 `OffloadingConnector` 之后实现共享内存 KV 层，**把槽位目录嵌入共享介质内部**，消除对外部元数据服务（Redis/etcd/RDMA 注册表）的依赖。

### 2.2 DRA 驱动关键设计
- **资源模型**：每个刀片发布一个 `ResourceSlice`，含单个设备与属性 `applianceId`、`bladeId`，容量为 `cxl_seagate_shared_mem_mib`。关键在于该 slice 设置 `NodeSelector` 匹配所有与该刀片连线的主机，而非传统的 `NodeName`；调度器因此可在任意连通主机上放置消费者，代价是无法表达比"已连接"更细的局部性偏好。
- **区域大小通过 annotation 传递**：`capacity-mib`、`share-count`、`qos` 写在 `ResourceClaim` 注解上，因为 `DeviceRequest` 只携带设备类与 CEL 选择器、不携带数量。后果：调度器只挑刀片、不挑字节，容量不会在分配时扣减，仅在 30 秒发布周期刷新，**无调度端容量核算与超卖保护**。
- **按需组合生命周期**（Allocate→Compose→Materialize→Inject→Free）：
  1. 等待消费者 Pod 绑定到节点（最多 30 s）；
  2. 各 DaemonSet 副本通过 `owner` 注解的 CAS 竞争选举唯一 owner；
  3. owner 先加 `free-memory` finalizer，确保中途删除的 claim 不会在释放刀片容量前消失；
  4. 从注解读取容量/共享数/QoS，按端口拓扑构造候选主机列表，调用 `ComposeMemory`；
  5. 对每个端口经 Redfish 调用 `cxl-host` 守护进程，创建本地 DAX 设备并写 CDI spec；
  6. 把 CDI 设备名 patch 进 `ResourceClaim.Status.Devices`。
- **单 CDI 名跨节点**：同一区域由 `allocationId` 标识，各主机独立具体化（DAX 索引可能不同），但 CDI 设备名即 allocation UUID，处处一致；Pod 无论落在哪台节点都解析为指向该区域的本地字符设备。
- **主机侧具体化**：CXL 1.1/2.0 走 sysfs DAX split 切子设备（必要时先加 pad 对齐），CXL 3.x 带 DCD 则直接向内核驱动请求容量扩展；每个 allocation 一个子设备实现物理共享池内的按分配隔离。`PrepareResourceClaims` 最多轮询 90 s 等待 CDI 名出现（因组合是带外进行）；`Unprepare` 为空操作，内存由控制器在 claim 删除时释放。
- **生命周期与拆除**：拆除元数据三重持久化（内存、claim 注解、claim 设备状态），配合 finalizer 实现"插件重启后仍可 free-on-delete"。`FreeMemory` 连续失败 5 次后仍移除 finalizer，宁可有容量泄漏（可见且可带外恢复）也不留无法删除的 claim。两个刻意的失败行为：具体化失败非致命（组合仍成功，该节点 Pod 无设备启动）；刀片断电后 fabric manager 不自动重发现状态，需人工重新同步。

### 2.3 共享内存 KV 层
- **映射**：C++ 引擎 `open` DAX 设备后 `mmap(MAP_SHARED)`，并 `madvise(MADV_RANDOM)` 抑制预读；可选 offset 支持多租户分区。DAX 无页缓存，映射即设备内存。
- **自描述布局**：`MagicHeader | LayoutHeader | config.json | SlotBitmap | SlotKeys | SlotCRCs | DataSlot...`。Magic（"LLMDXL"+版本字节）标识是否已格式化；LayoutHeader 记录槽大小、槽数与目录区结束位置；首个映射未格式化区域的进程负责初始化，后来者直接附着——**无格式化步骤、无协调者、无启动顺序要求**。槽大小由引擎 block 几何推导，槽数由区域大小推导。
- **区内目录**：KV block 以 token 内容哈希命名，CXL 层取 vLLM offload-key 基名前 16 个十六进制字符作为 64 位 slot key；槽索引 = `key % num_slots`，线性探测。三个数组实现目录：占用位图（`atomic<uint64_t>`）、并行 key 数组、每槽 CRC32 数组。
  - 写入：位图字上 CAS（acq_rel）后发布 key 与 CRC；
  - 读取：从哈希位置探测，仅当"位已置位 ∧ key 匹配 ∧ CRC 校验通过"才报命中，以 acquire 序加载；
  - 释放：先清 key 与 CRC，再清位。
  - **key 数组不可省略**：早期仅用位图的版本在区域非空后对每次查询都报命中，整批数据作废——"位图不是目录"。CRC32 进一步捕捉位翻转、部分写与一致性边界情况。
- **数据通路（主机暂存，非零拷贝）**：store 将 GPU block 拷入线程本地 staging buffer、同步 CUDA 流、获取槽、`memcpy` 到区域、发顺序一致 fence；load 反向执行。**GPU 从不直接 DMA 到/从 CXL**。
- **一致性**：跨节点正确性依赖 DAX 映射上的硬件 CXL.mem 一致性；作者将其标注为效度威胁而非已证性质，仅提供行为学证据。
- **实现坑点**：vLLM 0.23 在 `PYTHONHASHSEED` 未设置时用 `os.urandom()` 播种 block-hash 链，两个引擎对相同 token 导出不同哈希，跨实例查找**静默全 miss**，产生看似合理的零命中率；共享区域的每个副本必须设置相同 `PYTHONHASHSEED`。

## 3. 实验设计

### 3.1 测试平台与场景
- **计算节点**：2× 单路 AMD EPYC 9254（24c/48t）、128 GB DDR5、1× NVIDIA L4（24 GB），Kubernetes v1.35.7，两节点以 100 GbE ConnectX-6 Dx RoCEv2 直连。
- **CXL 设备**：Seagate 可组合内存设备的 FPGA 原型刀片，两个主机端口各跑 PCIe Gen5 x16 上的 CXL 1.1，1 TiB 可组合资源（8×128 GiB DDR4-1866 2DPC）；实验组合 512 GiB 以避开 1 TiB 地址边界的 AMD BIOS 内存空洞。
- **软件与模型**：vLLM v0.23.0 + llm-d，每节点一个副本、TP=1；Qwen2.5-7B-Instruct（bf16，56 KiB/token）。
- **场景**：每 session 发两个共享长前缀的请求——`req1 = SHARED + Q1 → 副本A`（写入 KV），`req2 = SHARED + Q2 → 副本A（same）或副本B（cross）`。cross 臂隔离共享内存效应：副本 B 从未见过这些 token，节点本地层级无法服务。

### 3.2 Benchmark 与对比方法
- 自建 harness，客户端经 SSE 流式观测 **TTFT**（首字节到首生成 token）；命中率取自 vLLM `external_prefix_cache_{queries,hits}` 计数器。
- **4 个层级配置**：
  - **T0** 无复用（重算下界）；
  - **T1** GPU VRAM 前缀缓存（`--enable-prefix-caching`，节点本地）；
  - **T2** CPU DRAM 卸载（native backend，32 GB，节点本地）；
  - **T4** 共享 CXL 区域（本文方案，OffloadingConnector + CXL backend + read_write）。刻意跳过 T3 为未来 RDMA 层级预留。
- **网格**：4 层级 × 2 臂（same/cross）× 4 前缀长度（标称 2K/8K/16K/32K，中位数 2054/8173/16282/32694 token）× 20 session × 3 重复 = **1920 个请求对**，每格 n=60。前缀长度经 tokenizer 校准，正文由带种子模板语法生成。
- **有效性控制**（每格执行）：
  1. 无提示泄漏：req1 命中率须 ≈0，实测各层 ≤0.2%，32/32 格通过 5% 阈值；
  2. 无假命中：独立控制运行对从未存储的 key 在 12298 次查询中 0 命中，排除 §3.3 的仅位图缺陷；
  3. 区域新鲜：除非恰好一个副本记录 initialize、另一个记录 reuse，否则 T4 运行中止。
- **偏置界定**：两节点不完全匹配、两臂各自 prompt 集不同。用 T0 同时度量二者：其 cross 臂中位 TTFT 在 2K/8K/16K/32K 分别比 same 臂低 1.4%/3.6%/4.5%/4.6%。因 cross 臂天然更快，T1/T2 在 cross 臂的塌陷是**保守**的；所有 cross/same 比值带 ≤5% 的系统性偏置，cross 臂内的层级间比较不受影响。
- **对照基线**：论文自带 RoCEv2 直连 fabric 表征（1.13 μs / 12.25 GB/s，98% 线速）作为参照，但**未运行哈希键 RDMA KV 池作为 pooled baseline**（列为 v2 工作）。
