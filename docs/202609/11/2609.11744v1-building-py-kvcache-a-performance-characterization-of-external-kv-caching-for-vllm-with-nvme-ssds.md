## 摘要
前缀缓存可通过复用先前计算得到的键值（KV）状态，降低长上下文 LLM 请求的首 token 时间（TTFT），但对于短前缀或快速 GPU，重新计算可能比从外部缓存加载更快。我们使用合成工作负载、长上下文基准和生产轨迹，在 GPU、CPU 和 NVMe 层级上刻画了 vLLM 中的这一权衡，并发现缓存性能不仅取决于设备带宽，还取决于传输粒度、中间内存使用，以及传输何时进入请求调度。这些发现促成了 py-kvcache：一种 vLLM KV Offload 连接器，具备异步直接 I/O、有界共享暂存和调度器感知的预加载，可在请求仍在等待时启动磁盘读取，与计算重叠。在 80k token 时，py-kvcache 从磁盘加载比 LMCache 快 2.0 倍，其中预加载贡献了 1.34 倍。在同时启用 GPU、CPU 和磁盘缓存时，它比 LMCache 快 1.23 倍，并且与原生 vLLM KV Offload 实现相差约 4% 以内。LongBench 和 SCBench 表明，这些优势可扩展到不规则前缀链和多轮工作负载。百炼（Bailian）轨迹回放可在较弱 GPU 上改善 TTFT，但在 H100 上，平均请求低于盈亏平衡点，仅靠 GPU 内存就能保留足够的前缀。因此，外部 KV 缓存应被视为一种取决于具体配置的准入决策。py-kvcache 实现可在以下网址获取：https://github.com/atlarge-research/py-kvcache。

## Abstract
Prefix caching can reduce the time to first token (TTFT) of long-context LLM requests by reusing previously computed key-value (KV) states, but for short prefixes or fast GPUs, recomputation can be faster than loading from an external cache. We characterize this tradeoff in vLLM across GPU, CPU, and NVMe tiers using synthetic workloads, long-context benchmarks, production traces, and find that cache performance depends on transfer granularity, intermediate memory use, and when transfers enter the request schedule, not only on device bandwidth. These findings motivate py-kvcache, a vLLM KV Offload connector with asynchronous direct I/O, bounded shared staging, and scheduler-aware preloading, which starts disk reads while requests are still waiting, overlapping with compute. At 80k tokens, py-kvcache loading from disk is 2.0x faster than LMCache, with preloading contributing 1.34x. With GPU, CPU, and disk caching enabled, it is 1.23x faster than LMCache and within approximately 4% of the native vLLM KV Offload implementation. LongBench and SCBench show that these benefits extend to irregular prefix chains and multi-turn workloads. Bailian trace replays improve TTFT on a weaker GPU, but on an H100 the average request falls below the break-even point and GPU memory alone retains enough prefixes. External KV caching should therefore be treated as a setup specific admission decision. The py-kvcacheimplementation is available at: https://github.com/atlarge-research/py-kvcache.

# 论文总结：Building py-kvcache — 使用 NVMe SSD 的 vLLM 外部 KV 缓存性能表征

## 1. 核心问题与研究动机

- **背景**：长上下文 LLM 推理中，Transformer 注意力随上下文长度呈二次增长；KV 缓存（Key-Value Cache）可避免重复计算，但随上下文长度、批大小、模型宽度与层数线性膨胀（如 Llama 3.2 3B 每 token 需 112 KiB，80k 上下文即约 8.75 GiB），很快超出 GPU VRAM。
- **外部 KV 缓存的诱惑与陷阱**：现代 NVMe SSD 每 GB 成本远低于 GPU VRAM/DRAM，且共享文件系统可提升命中率；但**缓存命中并非必然带来收益**——它把 GPU 预填充计算替换为缓存查找、磁盘/主机内存读取、CPU↔GPU 传输与调度同步开销。对短前缀、低命中率或快速 GPU，重计算反而更快。
- **核心研究问题**：不是"外部 KV 缓存能否工作"，而是 **"何时应该使用它"**。现有系统提供了存储/检索机制，却配套"每次前缀命中都视为胜利"的固定策略，缺少判断查找是否自偿的准入策略。
- **整体含义**：外部 KV 缓存应被视为一种**与部署环境相关的准入决策（setup-specific admission decision）**，其收益取决于传输粒度、中间内存使用，以及传输何时进入请求调度——而非仅取决于设备带宽。

## 2. 方法论

### 2.1 核心思想
- 通过代码路径追踪（code path tracing）与系统表征，定位 TTFT 关键路径上的开销来源，进而设计一个"关键路径优化"型外部 KV 缓存。
- 设计四原则：① 用普通文件系统布局实现简单部署与跨 vLLM 实例共享；② I/O 路径适配大块连续 KV 对象，避免过多工作线程协调；③ 显式限制中间 CPU 内存；④ 缓存策略硬件/负载感知，低于盈亏平衡点则绕过外部复用。

### 2.2 关键技术细节（py-kvcache）
- **存储接口选择**：最终采用普通文件 + O_DIRECT + io_uring（通过 liburing Python 绑定，v2026.3.30）。曾尝试 xNVMe/SPDK（需解绑内核驱动、不符合文件系统共享目标）、GPUDirect Storage/KvikIO（在本配置下更慢）后放弃。因 KV 对象远大于 1 MiB，Python 实现也能打满 SSD 带宽。
- **架构分离**：调度器侧 Manager 负责查找与 prepare_load/prepare_store/preload 计划（只传紧凑计划、不搬数据）；worker 侧 Handler → TransferCoordinator → 单线程 IoReactor 负责实际数据搬运。
- **共享文件系统布局**：沿用 llm-d 的分层哈希寻址路径；写入先落到唯一临时文件，完成后以**硬链接**原子发布最终哈希名（首次写入者胜出），读者只打开最终名，保证条目"要么不存在要么完整"。
- **异步传输与有界暂存**：KV 按块（实验中 256 token 块，Llama 3.2 3B 约 28 MiB/块）一文件；由**可配置 I/O 深度**而非线程数控制并发；单一连续对齐的 pinned CPU staging pool，load/store/preload 共用；可选的 LRU/ARC 保留使其兼作 DRAM 缓存。加载时先异步 openat，读完成后立即排入 CPU→GPU 拷贝，同一 reactor 迭代内就绪的映射融合为单次 `swap_blocks_batch` 启动；存储走反向流水线。
- **调度器感知预加载**：为 vLLM fork 增加有界 `on_preload_candidates` 回调，Manager 查看等待队列的有界前瞻窗口，在请求被调度前就把磁盘读入 staging pool；请求执行时直接加入在途读或认领已暂存块，关键路径上只剩 CPU→GPU 提升。
- **预加载从属规则**：先服务就绪的需求读、再新需求 load/store、最后才做投机预加载；预留等于 I/O 深度的槽位给前台；需求到达时可关闭并重排队预加载；相同前缀共享一次读与引用计数槽位。
- **盈亏平衡门控**：每个节点/模型离线标定一次，产出各来源层级的最小可复用前缀长度阈值；服务时不测量不拟合。若加载预测成本高于重计算，Manager 拒绝加载，让 vLLM 重算。

### 2.3 公式与判定流程（文字说明）
- **每 token KV 字节数**：`layers × 2 × KV heads × head dim × datatype size`。
- **缓存是否值得**：设 D 为总文档 token 数、P 为缓存前缀 token 数、f(x) 为冷 TTFT（全量计算）、g(x) 为命中 TTFT，则当 `g(P) + f(D−P) < f(D)` 时缓存才划算。
- **盈亏平衡带宽**：`max_io(D) = f(D) − (g(D) − tcopy(D))`，即用计算整篇文档的时间减去命中路径中非传输部分，得到可用于搬运 KV 数据的时间预算；再用文档 KV 字节数除以该预算，得到"全前缀命中才能打平重计算"所需的最低吞吐。

## 6. 主要结论与发现

- **缓存命中 ≠ 收益**：命中替代重计算的收益随文档增长（1k 时 2.2×，80k 时 32.8×），但存在盈亏平衡点。Snellius + Llama 3.2 3B + llm-d 下，8k 提示需 **77.8% 前缀复用**才能打平，80k 时降至 **7.8%**；最低带宽需求从 1k 的 23.2 GB/s 降到 80k 的 3.5 GB/s。
- **关键路径与粒度比带宽更重要**：Offload 与 LMCache 的 GPU↔CPU 带宽相近（均 24–26 GB/s，Snellius 上 54–56 GB/s），但 Offload 用更少、更大的传输并把 store 延迟到下一迭代与 forward 重叠，因而更快；小 I/O IOPS 与线程池替换对端到端 TTFT 无改善（KV 负载主要是 512 KiB–1 MiB 的大请求）。
- **中间内存策略可主导性能**：llm-d 最小 staging 分配过大导致数据放大（4.4 GB 有用 KV 触发约 10 GB 读写），修复后 TTFT 较 LMCache 低约 50%。
- **py-kvcache 性能**：磁盘单层下 80k 比 LMCache 快 **2.0×**（不含 preload 约 1.5×），preload 贡献 **1.34×（80k）/ 1.66×（40k）**；三级（GPU+CPU+磁盘）比 LMCache 快 **1.23×**（80k），距原生 vLLM KV Offload 约 **4%** 以内（40k 1.10×、80k 1.04×，10k 反超 1.12×）。
- **真实负载**：LongBench 比重计算快 6.02–7.43×、比 GPU 前缀缓存快 2.02–2.12×、比 LMCache 快 2.77–3.64×；SCBench 比 GPU 前缀缓存快 3.11×、比原生 offload 快 2.48×、比 LMCache 快 1.26×。Bailian 在弱 GPU（RTX 4000 Ada）上快 1.12–1.79×，但在 H100 上平均请求低于盈亏平衡点，纯 GPU 前缀缓存与 py-kvcache 相同。
- **有界暂存的重要性**：SCBench 中原生 vLLM offload 因并发 promotion 占满 CPU 池、反复驱逐，读盘 3.4 TB 且超 1,200 s 未完成；py-kvcache 有界 staging 仅读 85 GB、约 480 s 完成，最少只需 576 MB 空闲 CPU 内存。
- **总体判断**：外部 KV 缓存应作为依赖模型、GPU、SSD、可复用前缀长度与队列等待时间的准入决策；重计算应保留为合法的回退路径，而非视为缓存未命中失败。

## 7. 优点

- **视角新颖且实用**：把外部 KV 缓存重新定义为"关键路径优化 + 准入决策"，而非单纯的存储层级扩展，指出"更慢的来源有时反而产生更低 TTFT"。
- **方法论扎实**：以代码路径追踪为主线，跨 KV Transfer API 与 KV Offload API 两代接口，自研 simple-profiler 与 Web 追踪查看器，定位到 store 延迟、传输粒度、staging 分配放大等具体根因。
- **工程设计细致**：io_uring + O_DIRECT + 单 reactor 线程 + 可配置 I/O 深度；硬链接原子发布实现多实例共享的 first-writer-wins；共享 staging pool 统一 load/store/preload 并防死锁；预加载有界

- **预加载与从属调度规则清晰**：有界前瞻窗口 + 前台优先 + 可撤销并重排队 + 相同前缀引用计数共享，避免投机预加载挤占需求读，兼顾了吞吐与尾延迟。
- **共享文件系统设计务实**：以普通文件 + 硬链接原子发布换取跨 vLLM 实例、跨进程共享，不牺牲条目完整性，部署门槛低，且不依赖解绑内核驱动的 SPDK 类方案。
- **表征方法可复用**：盈亏平衡带宽 `max_io(D) = f(D) − (g(D) − tcopy(D))` 与"最小可复用前缀长度阈值"的离线标定思路，可迁移到其他存储层级（DRAM、远端缓存、网络文件系统）的准入决策。
- **对照公平且坦诚**：为 llm-d 自建直接 I/O fork、统一编排脚本、固定输出 1 token，并主动披露版本跨度与追踪级归因证据，结论定位克制。

## 8. 局限与不足

- **版本跨度大**：实验横跨 vLLM v0.16–v0.22，各对比系统的接口（KV Transfer API vs KV Offload API）与实现细节随上游演进，跨版本数值比较存在系统性风险，作者亦承认结论是"关于设计的证据"而非稳定排名。
- **硬件与负载覆盖面有限**：所有实验仅用单张 GPU，未涉及张量并行/流水线并行下的 KV 分片与跨卡聚合；SSD 仅两种企业级 PCIe 4.0/5.0 型号，未覆盖消费级 SSD、网络存储（NFS/对象存储）或远端 KV 池等更弱链路。
- **盈亏平衡门控依赖离线标定**：阈值按"每节点/每模型"标定一次，负载、并发、批组成或 GPU 频率变化时可能失效，论文未给出在线漂移检测或自适应重标定机制。
- **模型规模偏小**：主实验使用 Llama 3.2 3B 与 Qwen3 4B，KV 单 token 体积与计算强度均较小，结论向 70B/更大 MoE 模型迁移需额外验证（层数、KV heads、head dim 变化会同时改变两侧）。
- **输出固定为 1 token**：虽有利于隔离 prefill 与搬运开销，但掩盖了解码阶段与缓存交互、以及真实混合负载下的调度效应。
- **preload 与 CPU 层交互的边界条件**：预加载窗口大小、staging pool 容量与 I/O 深度的联合调参空间未系统展开，缺少灵敏度分析。
- **缺少成本/能耗维度**：仅以 TTFT 与吞吐衡量收益，未计入 SSD 磨损、功耗、CPU 占用与运维复杂度等总拥有成本因素。

## 9. 对实践的启示

- **先标定再启用**：部署外部 KV 缓存前，应针对目标 GPU + 模型 + SSD 组合测量最低可复用前缀长度阈值与所需带宽，低于阈值直接绕过，让 vLLM 重计算。
- **优先优化关键路径而非设备带宽**：把 store 移出关键路径、与下一迭代 forward 重叠；合并小块 I/O；保证传输粒度足够大（数百 MiB 级连续块）比换更快的盘更有效。
- **严格控制中间内存**：pinned staging pool 必须有界且共享，避免为"以防万一"而过度分配导致数据放大与池争抢；容量规划可按论文给出的数百 MB 量级起步。
- **调度器感知是必选项**：在请求被调度前完成磁盘读，使关键路径只剩 CPU→GPU 提升，可带来 1.3×–1.7× 的额外收益。
- **弱 GPU 更受益**：GPU 越慢、前缀越长，外部缓存的盈亏平衡点越易达到；在 H100 等强卡上，纯 GPU 前缀缓存可能已足够，此时外部缓存应退化为大容量场景的补充。
- **把重算当合法回退**：将缓存未命中视为"降级到计算路径"而非失败，是设计上更稳健的默认语义。

## 10. 总体评价

本文是一篇高质量的**系统表征与设计论文**，其核心贡献不在于提出一个新的 KV 缓存系统本身，而在于**把"是否使用外部 KV 缓存"形式化为一个可计算的准入决策问题**，并用严谨的代码路径追踪证据说明：TTFT 的主导因素往往是传输粒度、中间内存策略与调度时序，而非存储设备的原始带宽。盈亏平衡带宽公式与最低前缀复用率阈值给出了可直接落地的判据；py-kvcache 的实现（io_uring + O_DIRECT + 单 reactor + 有界共享 staging + 硬链接原子发布 + 调度器感知预加载）则展示了在给定约束下接近甚至追平原生实现的工程上限。其主要弱点在于硬件与模型规模的覆盖范围、跨版本可比性以及离线标定的自适应性，但这些问题大多被作者明确披露并作为后续工作方向保留。对于正在设计长上下文推理服务的工程师，本文提供了"何时该用、怎么用才划算"的实用指南，价值高于单纯报告加速比的同类工作。
