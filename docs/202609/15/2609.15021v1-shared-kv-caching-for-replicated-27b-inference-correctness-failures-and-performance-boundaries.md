## 摘要
共享主机内存缓存可以在请求于推理副本之间迁移时避免重复预填充。其有效性取决于正确的状态传输和丢失的前缀局部性。我们研究了两个共享 256 GiB LMCache 池的单 GPU 27B vLLM 副本。在采用已有的打包页补丁后，我们隔离出一个裸指针回退路径，它遗漏了对当前 CUDA 流的依赖。受控字节测试在施加延迟时失败，而在恢复依赖后通过；现有的混合分配器提供了一条可用的部署路径。全池分配检查和服务回归完成了验证。四组 OFF-ON-ON-OFF 对比在两个块对中包含了 768 个实测请求。在 128k 输入下，跨副本首内容 token 时间中位数从 31.715 秒降至 0.605 秒；在 256k 输入下，从 92.047 秒降至 0.790 秒。在初始上下文为 32k 和 128k 时，交替副本的六轮合成会话分别提升约 35% 和 45%，而固定放置几乎没有收益。本工程案例研究识别了实际验证步骤以及共享缓存能够带来收益的局部性条件。

## Abstract
Shared host-memory caching can avoid repeated prefill when a request moves between inference replicas. Its usefulness depends on both correct state transfer and lost prefix locality. We study two single-GPU 27B vLLM replicas sharing a 256 GiB LMCache pool. After adopting an existing packed-page patch, we isolate a raw-pointer fallback that omits the dependency on the current CUDA stream. Controlled byte tests fail under an imposed delay and pass when the dependency is restored; the existing mixed allocator provides a working deployment path. Full-pool allocation checks and service regression complete the validation. A four-block OFF-ON-ON-OFF comparison contains 768 measured requests within two block pairs. Median cross-replica time to first content token falls from 31.715 to 0.605 seconds at 128k input and from 92.047 to 0.790 seconds at 256k. Six-turn synthetic sessions alternating replicas improve by approximately 35% and 45% at initial contexts of 32k and 128k, while fixed placement shows little benefit. This engineering case study identifies practical validation steps and the locality conditions in which shared caching pays off.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：多轮推理请求常携带已在早前轮次处理过的大量上下文。同一副本可复用本地前缀状态，但请求被调度到另一副本时，该前缀需重新计算（重复 prefill）。由此产生一个实际部署抉择：通过放置策略保持请求局部性、提供跨副本共享状态复用路径，或两者结合。
- **工具背景**：LMCache 提供了跨请求与跨推理引擎搬运、复用 KV 缓存的机制；本文在固定部署中检验其实际执行。
- **两个核心问题**：
  - 如何验证共享状态传输路径的正确性——HTTP 200 或命中计数器并不构成完整性校验，缓存可能"看似可用"却返回错误状态。
  - 其性能究竟如何——亮眼的"冷 vs 热"对比可能掩盖一个竞争性替代方案：把会话保留在原 GPU 上（本地复用）。因此必须在测量性能前先确立正确性，并保留本地命中基线。
- **整体含义**：这是一篇工程案例研究，旨在为副本化推理服务中共享缓存的配置与评估提供具体的验证步骤和适用条件判断。

## 2. 方法论：核心思想与关键技术细节

- **系统拓扑**：单推理主机上部署一个外部网关与两个完整 vLLM 副本，各占一张 GPU，均执行 prefill 与 decode，共享一个 256 GiB 主机内存 LMCache 服务；每个副本保留自己的 GPU 前缀缓存。**这不是 PD 分离**，网关也不充当 KV 数据存储层。
- **模型与运行时**：Qwen3.8-27B-NVFP4，64 层（48 层 Gated DeltaNet + 16 层全注意力），隐藏维 5,120，全注意力头维 256、4 个 KV 头；vLLM 0.28.0 / LMCache 0.5.4 / PyTorch 2.13.0+cu129；张量并行 1，FP8 KV，HND 布局，启用前缀缓存。
- **混合状态语义**：此处"KV cache"包含可在共同前缀边界恢复的混合解码状态——全注意力贡献前序 K/V 页，Gated DeltaNet 贡献卷积与循环状态的边界快照。对齐（align）模式下，恢复需同时具备注意力前缀块与对应循环快照；仅注意力 kernel group 命中不足以恢复完整混合状态。
- **故障一：打包页兼容性**
  - 首次跨副本响应在 HTTP 200、25,088 外部命中 token 的情况下返回损坏文本。
  - 根因：逻辑全注意力块由多个打包 kernel 页组成（1,568 token 逻辑块跨 49 个 32-token 页），原处理识别 rank-5 注意力张量却遗漏 rank-4 打包表示，导致传输字节视图错误。
  - 修复：采用上游 packed-subpage 补丁（commit f180b9ff…），无额外本地改动。HND 是该补丁与 vLLM/FlashInfer 组合的配置特定要求，非 LMCache 通用要求。
- **故障二：可复现的流序错误**
  - 现象：相同 token 输入在 A 上冷算或本地复用得到 alpha=938639，B 外部命中 127,008 token 却返回 938624；新缓存 salt 强制零命中冷算后恢复正确。
  - 根因：评估镜像缺少 LMCache CUDA-ops 扩展，走 PyTorch 回退；其裸指针 `lmcache_memcpy_async` 分支调用 `cudaMemcpy(..., cudaMemcpyDefault)` 时未传当前流参数（`cudaMemcpyDefault` 是拷贝类型枚举而非函数名）。PyTorch 流池使用 `cudaStreamNonBlocking`，非默认流被排除在 legacy 默认流的隐式同步之外，主机端返回不代表生产者/消费者依赖已建立。
  - 受控探针：1 MiB D2H 探针调度延迟写入值 37 后调用回退，主机读到旧值 0；H2D 探针调度读取旧值 0 后回退写入 53，消费者读到 53；各报告 1,048,576 个不匹配字节（纯整数字节差异，非浮点或采样所致）。
  - 修复：显式设置 `--no-l1-use-lazy` 选择现有混合分配器及其 tensor-copy 路径（仅去掉 lazy 正向标志不够，因 CLI 默认 lazy）。
- **故障三：全池 pinned 分配**
  - 小规模混合分配器探针可成功 pin，但首个 256 GiB 服务分配回退为 pageable。
