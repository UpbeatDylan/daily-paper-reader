## 摘要
现代大语言模型智能体在持久工作空间中运行，其累积的历史记录可能超出GPU KV缓存容量和模型原生上下文窗口。现有系统通常将较旧的上下文压缩为摘要或稍后作为文本检索，要么丢失细粒度的执行证据，要么反复预填充模型已处理过的内容。我们提出KVMem，一种KV上下文虚拟化系统，将溢出的工作空间历史以分页KV状态的形式跨GPU内存、主机内存和NVMe进行保存。KVMem使用轻量级、模型原生的注意力空间索引来选择相关的历史块，并物化出受模型原生上下文窗口限制的、依赖于查询的执行视图。在涵盖多达一百万token历史的长上下文智能体基准（包括LongMemEval、MemoryAgentBench和AgentLongBench）上的广泛评估表明，与处理上下文溢出的实际标准——基于压缩的方法相比，KVMem通常能实现更高的任务效用和更高的推理效率。在DeepSWE长上下文测试中，使用Qwen3.8-27B，KVMem将任务成功率从仅压缩上下文管理的43.8%提升至48.4%。在我们本地部署评估中，KVMem在配备24GB RTX 5090笔记本电脑GPU的现成笔记本电脑上运行Qwen3.6/3.8-27B NVFP4和MTP，可虚拟化高达100万token的智能体工作空间——是模型原生256K token上下文窗口的四倍。在单会话设置中，KVMem生成约50 token/s，为本地智能体执行提供交互式响应。更广泛地说，通过将可寻址工作空间大小与大语言模型的原生上下文窗口解耦，KVMem为工作空间可增长至超出该窗口的长期运行智能体提供了一条实用路径。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

## 1. 核心问题与整体含义（研究动机和背景）

论文解决的问题围绕 LLM 智能体长期运行时的 "工作区上下文溢出" 这一核心痛点，背景链条如下：

- **问题根源**：现代 LLM 智能体在工作中不断累积任务本地化的历史数据，即所谓"持久工作区"——包括工具调用结果、文件读取内容、编辑记录、执行日志、用户反馈、中间产物等。**随着运行时间推移，这些累积历史最终会突破两道物理和模型层面的上下限：**
  - **GPU KV 容量上限**：即便历史长度没有超过模型原生上下文窗口，保留全部 KV 状态所需内存也远超单张 GPU 的可用显存；模型权重、推理缓冲区、预解码状态、KV 缓存需要共享显存。
  - **模型原生上下文窗口上限**：历史本身的 token 量最终超过模型支持的最大上下文长度（如 Qwen3.6-27B 为 256K tokens）。
- **现有方法的缺点（文本中心式溢出处理的固有缺陷）**：
  - **压缩（Compaction）**：将较早执行历史压缩为摘要。核心问题在于"提前决定未来的相关性"——给定一段被截断的历史，压缩算法在选择丢弃哪些细节前并不知道未来的任务需要哪些证据；这种**有损压缩无法保证对所有未来查询都保留必要信息**（论文用 H1≠H2 但 C(H1)=C(H2) 的不可区分性论证说明）。
  - **文本检索（Text Retrieval / RAG）**：虽能找回被压缩遗漏的细节，但**被检索回来的文本必须重新进行 prefill 计算**——即使模型在更早时间已经完整编码并处理过这些 token。每次历史文本的召回都变成一次新的 prefill 负载。
- **KVMem 的思路**：论文观察到这种高保真-高效率冲突并非"上下文溢出"的固有属性。当历史上下文离开活动窗口时，模型早已完成对其的 KV 编码；既然如此，与其丢弃或压缩这些已计算的状态，不如**把完整 KV 状态保留下来作为可分页寻址的"虚拟工作区"**。这使智能体的可寻址工作区规模可与物理 GPU 内存和模型原生窗口解耦。

因此，论文的核心贡献是提出一套 **KV 上下文虚拟化系统 KVMem**，将溢出工作区历史以分页 KV 状态形式存储在 GPU 内存、主机内存和 NVMe 三层存储中，并配合查询感知的工作集构造过程，使智能体在每步推理时只物化有限的、查询指向的执行视图。

## 2. 论文提出的方法论

### 2.1 系统抽象与形式化

系统将工作区历史中处理过的 KV 状态划分为多个固定大小（Bblk tokens）的逻辑块（logical blocks）。在此基础上它区分三个容量边界：

- **Bmodel**：模型的原生上下文窗口；
- **Bgpu**：GPU 内存约束下的最大 token 等价 KV 状态量；
- **Bm**：主机内存和 NVMe 中后备 KV 工作区的容量。

活动上下文预算定义为 Ba = min(Bmodel, Bgpu)。每当执行历史的累积量超过 Ba，就触发上下文溢出的处理。KVMem 的主要实现前提是，历史 KV 状态总量可以放入 Bm 大小的后备存储中——由于后备空间远大于活动预算，溢出处理的触发频率比传统压缩低得多。

核心优化目标是 **Fidelity (π)**（任务质量和状态保真）与 **Recovery Cost(π)**（更新和恢复历史工作集的开销）之间的平衡。

### 2.2 三大关键机制

KVMem 给出了针对三种设计挑战的对应解法：

**(1) Step-Level Memory Scheduling（步骤级内存调度）——解决"何时召回"**

- 观察依据：论文分析了 OpenHands SWE-bench Lite 的 8 条 rollout，发现 agent 步骤内相邻滑动窗口的 KL 散度平均为 0.070 bits，而在步骤边界处的 KL 散度平均为 2.59 bits（差距 37.3×）。这暗示 agent 对历史注意力的分布在步骤内部相对稳定，而在步骤之间会急剧变化。
- 具体策略：**每个智能体步（agent step）只更新一次历史工作集**。更新时机固定为当前步 prefill 完成之后、解码开始之前；解码过程中保持所选工作集固定，仅在其尾部追加新生成 token 的 KV。当下一 agent
  步开始时，才开启新一轮"历史注意力重估"。
- 实际执行时必须注意到：由于 KVMem 的检索需要以当前查询（query）的向量为基础，而查询向量只有在 prefill 完成后才能获得，因此 KVMem 在更新工作集后会重新在当前步上下文上执行一次 prefill（恢复 checkpoint），再进行解码生成。

**(2) Query-Conditioned KV Retrieval（基于注意力空间的块级检索）——解决"检索什么"**

- 论文观察到，模型对历史上下文的自注意力十分稀疏——平均每个窗口包含了 103.1 个历史块，但 **top-8 块捕获 66.5% 的历史注意力**，top-16 块捕获 77.0%。这说明有效的召回不需要把大部分工作区都物化到 GPU 上。
- 核心载体是从模型自身的 attention 空间导出的紧凑 **Mean-K 索引**：
  - 对每个 32-token 的逻辑块，在 prefill 时去掉 RoPE 位置编码，保留每层每个 KV head 下位置无关的 K 向量，对其取均值作为块的检索表示：

  
$$\bar{k}_{l,b,g} = \frac{1}{|b|} \sum_{i \in b} \tilde{k}_{l,i,g}$$


  - 索引即由所有历史块的这些逐 head、逐层的 Mean-K 向量组成。
- 在每次召回时，KVMem 用当前查询的位置无关 Q 向量与所有候选块的 Mean-K 向量做缩放点积，并**跨候选块执行 softmax** 使分数在统一的注意力量级下可比：

  
$$R_b = \sum_{m} \text{mean}_{l,h} \ \text{softmax}_{b' \in C} \left( \frac{q_{l,m,h}^{\top} \bar{k}_{l,b',g(h)}}{\sqrt{d}} \right)_b$$


  - ReLU？不；最终只选择得分最大的块，且默认策略会保留"注意力汇点（sink）"和"最近区块"，剩余预算按 Rb 从高到低排布。
- 完整索引体量巨大，不适合整段常驻 GPU，因此 KVMem 在**主机内存保存完整 Mean-K 索引**，retrieval 时把选定的固定大小瓦片（tile）暂存 GPU 进行打分；对跨瓦片的分数，在宿主侧维护全局 softmax 归一化。这样保证检索的 GPU 内存占用只取决于设置好的瓦片大小而非历史总长度。

**(3) Tiered KV Management（分层 KV 管理）——解决"如何可靠物化"**

- 核心概念：将历史 KV 仓库与 GPU 执行视图分离开来：
  - **仓库视图（repository view）**记录所有历史块的持久副本位置（GPU 临时页、主机内存、NVMe）；
  - **执行视图（execution view）**，即当前 agent 步骤在紧凑注意力窗口内的逻辑布局。
- 执行视图通过**页表映射**把非连续物理页映射到逻辑上按时间顺序排列的紧凑窗口；物理页不搬移、不打散，利用 page-table aliasing 实现复制无关的组装。
- 位置完整性的关键在于对 RoPE 的处理：block 的原始 K 向量只在原始逻辑位置上有效；KVMem 保存**无 RoPE 的"裸 K"副本**作为持久存储中的权威项，每当块被重新放置在新的紧凑位置时，就基于裸 K 重新施加 RoPE (即 "re-RoPE")。已驻留 GPU 且仍被复用的块，若只发生紧凑位置偏移，则采取有效的 delta re-RoPE 处理，但为了防止 FP8 / NVFP4 等低精度反复修改导致累积误差，系统设置了动作计数上限——超过后强制从裸 K 重建一次。
- 三个互补优化：
  - **Proactive Stage-Out（主动换出）**：将旧块从 GPU 下盘操作从工作集切换的关键路径中移除。prefill 的 chunk n 完成后立即把对应已完备块的 KV 以异步方式复制到主机内存；后台任务继续将不必需的部分持久化到 NVMe。这样"工作集迁移"时刻到来时，旧 GPU 页可即刻被回收，过渡开销极低。
  - **Retrieval-Aware Hierarchical Reuse（识别命中的层级复用）**：相邻 agent 步骤的选中块集合高度重叠。KVMem 把工作集迁移分解为保留块、换入块和换出块三部分；凡在 GPU 页池中仍然命中的块可直接复用物理页（避免 H2D 传输）。同时命中主存缓存有更高的优先级；淘汰算法不仅看最近使用（LRU），还考虑累积检索频次，即**权衡频率+最近性**避免经常被召回但只是暂时不用的块反复落到 NVMe。
  - **Packed and Pipelined KV Rematerialization（打包+流水线重建）**：把分散在主机内存或 NVMe 的"源 KV 块"聚合成连续主机缓冲区，经批量 H2D 传输到 GPU 暂存区，再由 GPU 内核散射到目的页并施以 re-RoPE。这一过程采用了双缓冲和 CUDA event-based synchronization，使 CPU gather (batch n+1)、H2D transfer (batch n)、GPU scatter/re-rope (batch n−1) 并行流水化。V 不依赖位置信息，可以直接随裸 K 并行传输而无需额外变换。

## 3. 实验设计

### 3.1 受控基准实验

- **LongMemEval-S**（问答应答场景，需在带时间戳的多会话交互历史中检索证据；历史总长约 115K tokens）
- **MemoryAgentBench**（包含准确检索、测试时学习、长期理解、冲突消解四类任务的增量记忆对话；历史规模 103K–1.44M tokens，评估聚焦 >256K 字段）
- **AgentLongBench**（在受控环境 rollouts 中的长期 agent 任务，轨迹长度从 32K 到 4M token）
- **DeepSWE v1.1**（仓库级软件工程长时任务，含功能验证器）

所有受控基准（前三项）统一以**可重放的历史轨迹**方式评测，使不同上下文管理策略面对完全一致的历史内容。

### 3.2 对比方法

- **Full Context**：完整历史驻留在活动上下文中（仅当历史 < 模型原生窗口时可用）
- **Sliding Window**：只保留最大预算内的最近上下文
- **Compact-only**：溢出历史压缩为纯文本摘要
- **Compact+RAG**：另设外部文本库，检索后将历史文本块重新插入 prompt
- **KVMem（本文方法）**：KV 分页 + 检索

所有方法在 QW3 后端上运行，拥有相同模型、解码参数、提示词等，除上下文管理策略不同外完全一致；各非 Full Context 方案的**可用活动上下文预算完全相同**（32K/64K/100K 视场景而定）。

- **消融实验较弱**。论文方法机制设计相当多（如步骤级计划 vs. 更细粒度、不同检索粒度和不同 re-RoPE 频率），但对三大组件的消融（即去掉主动换出、去掉层级复用、关闭量化对 re-RoPE 的重建频率）没有给出完整的实验报告。此外，对 32-token 默认块的依据、tile 大小对延迟与索引精度的影响也缺少系统对比。实验充分性总体中等偏上——对效用和扩展性的比较足够；对设计空间的单点效果验证不足。
