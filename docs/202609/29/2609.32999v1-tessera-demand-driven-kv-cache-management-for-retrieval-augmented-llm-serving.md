## 摘要
RAG 和基于检索的智能体记忆都会将检索到的内容注入 LLM 提示中，分别以文档块和召回的记忆记录形式。相同内容可能在不同请求中、不同提示位置或不同前置上下文之后重复出现，从而无法通过传统前缀缓存实现复用。我们的表征分析发现，在智能体记忆工作负载中，在匹配前缀之外重复出现的记录占注入记忆 token 的 70% 以上。可组合的 KV 复用方法能在这些情况下实现复用，但在线服务引入了一个管理问题：重复单元的 KV 状态可能尚未存在、可能已被逐出，或可能位于另一个节点上。我们提出 Tessera，一种解耦式服务系统，将检索作为 KV 复用的控制平面。通过在模型执行前暴露所需的上下文单元，检索使 Tessera 能够将当前需求与检索历史、KV 驻留情况和生成负载结合起来，以协调缓存管理与请求路由。生成节点会并发准备本地已缓存、远程已缓存以及缺失的状态，同时将新计算出的状态保留在请求关键路径之外。在 RAG 和智能体记忆工作负载中，在相同请求速率下，Tessera 相比 SGLang 和带 EPIC 的 LMCache 将平均 TTFT 最多降低 3.6 倍，并在基线饱和的请求速率下仍维持低 TTFT，同时达到与底层组合策略相当的答案质量。

## Abstract
RAG and retrieval-based agent memory both inject retrieved content into LLM prompts, as document chunks and recalled memory records, respectively. The same content can recur across requests at different prompt positions or after different preceding contexts, preventing reuse through conventional prefix caching. Our characterization finds that records recurring outside the matching prefix account for over 70% of injected memory tokens in agent-memory workloads. Composable KV-reuse methods enable reuse in such cases, but online serving introduces a management problem: a recurring unit's KV states may not yet exist, may have been evicted, or may reside on another node. We present Tessera, a disaggregated serving system that makes retrieval the control plane for KV reuse. By exposing the context units needed before model execution, retrieval allows Tessera to combine current demand with retrieval history, KV residency, and generation load to coordinate cache management and request routing. Generation nodes concurrently prepare locally cached, remotely cached, and missing states, while retaining newly computed states off the request's critical path. Across RAG and agent-memory workloads, Tessera lowers mean TTFT by up to 3.6x over SGLang and LMCache with EPIC at matched request rates, and sustains low TTFT at rates where the baselines saturate, while matching the answer quality of the underlying composition policy.

## 1. 核心问题与研究动机

- **共同输入结构**：RAG 从知识库检索文档块，基于检索的智能体记忆召回历史交互/观测记录。两者都把"独立选取的文本片段"与任务指令、查询组合成一个 prompt，本文将这些片段统称为**上下文单元（context unit）**。
- **核心痛点**：同一上下文单元会在不同请求中重复出现，但位置不同、前置上下文不同。由于 KV 状态依赖绝对位置（RoPE 旋转）和全部前序 token，**传统前缀缓存（prefix caching）在第一个分歧点即失效**，必须重新 prefill。
- **量化动机（第 3 节表征）**：在两个智能体记忆负载中，落在"匹配前缀之外"的重复记忆 token 占注入记忆 token 的 **73.9%（LoCoMo）与 76.3%（τ2）**；83.2% / 80.8% 的请求其记忆 token 中至少一半属于非前缀重复；在完整 prompt 层面，非前缀重复仍占 LoCoMo 的 31.5–44.9%、τ2 的 33.1–53.8%，且在每个 stream 中占匹配前缀之外 token 的多数。
- **已有工作的缺口**：可组合 KV 复用方法（PromptCache、CacheBlend、EPIC、TurboRAG、KVLink 等）解决"如何定位与组合"的算法问题，但在**在线服务**场景下不保证状态在再次被检索时可用——状态可能从未算过、已被逐出、或位于其他节点。
- **三大在线挑战**：
  - **挑战 1**：缓存管理与请求路由相互耦合——保留位置决定谁可复用，路由决定需求落在哪；按缓存局部性路由会压垮热点节点，纯按负载路由则放弃复用。实验显示把同一总容量拆成 8 份节点本地缓存，命中率下降约 **5×**。
  - **挑战 2**：一个请求可能同时含缓存命中与缺失单元，串行准备会把传输与 miss-prefill 延迟都压到关键路径上；阻塞调度器又会拖慢无关请求。
  - **挑战 3**：保留新算状态只惠及未来请求，却与当前请求争夺 host 内存、注册缓冲与 NIC 带宽（如 Qwen3-32B，16-bit KV，每 token 每 rank 占 64 KiB；4 GPU 共享单 NIC 时每 token 需移动 256 KiB）。
- **核心洞察**：**检索在模型执行前就暴露了请求所需的上下文单元**，因此检索层天然可充当 KV 复用的控制平面——与检索历史、KV 驻留、生成负载结合后，可在派发前决定缓存保留与路由。
- **阶段速率悬殊**（200 请求 2WikiMQA 实测）：CPU 向量检索 14.4K req/s、RDMA 传输 7.15 req/s、GPU prefill 仅 0.76 req/s，跨越四个数量级，支撑"检索/存储/生成独立配置"的解耦设计。

## 2. 方法论

### 2.1 总体架构（解耦三池）

- **Retrieval Pool（控制平面）**：执行检索、识别上下文单元；综合检索历史、KV 驻留目录、生成负载，选定生成节点并产出**逐单元计划（per-unit plan）**。
- **KV Pool（共享存储）**：RDMA 可访问的共享内存，跨生成节点扩展复用；Retrieval Pool 管理驻留元数据与空间分配，生成节点直接读写 payload。
- **Generation Pool（执行）**：每节点运行 LLM 服务引擎 + pinned host memory 中的上下文单元缓存；并发执行"本地拷贝 / 远程拉取 / 独立 prefill"，就绪后组合并继续生成；授权状态在关键路径外异步保留。
- **请求流程**：检索 → 识别单元 → 选节点 + 出计划 → 并发准备状态 → 组合并生成 → 异步回写。

### 2.2 关键机制

- **稳定上下文单元标识**：在每个共享范围内，由**token 序列 + 服务配置**派生身份，与位置和周围上下文无关，使检索需求与缓存状态可跨请求对齐同一单元。
- **逐单元计划（Per-Unit Plan）**：在选定节点、拿到节点缓存快照（重新验证本地可用性）后才最终确定。计划含两个**彼此独立**的字段——`preparation`（本地命中 / 从 KV Pool 拉取 / 从文本计算）与 `retention`（保留在本地 / 回写共享 / 两者 / 都不）。因此**当前请求的可用性不依赖是否选择保留**。
- **存储块（Blocks）**：单元长度不一，两级缓存均以**至多 B token 的定长块**存储；n token 占 ⌈n/B⌉ 块，块不必相邻，共享池中可分散在不同内存节点。准入/逐出以**整个单元**为粒度，块仅用于容量核算与数据传输；**所有块写完才可读**。
- **可复用形态**：保留的是"**RoPE 之前的 keys + values**"，两级缓存存储与传输的都是这一形态，从而可用新的偏移量重新施加 RoPE。

### 2.3 检索感知的缓存与路由（对应挑战 1）

- **复用价值评分**（结合近期与累积检索频率）：
  - `s(u,t) = w_r · f_W(u,t) + w_ℓ · f_∞(u,t)`
  - `f_W` 为最近 W 个请求中检索到 u 的次数，`f_∞` 为累积次数；固定 `w_r = 1`，`w_ℓ = 0.05`（所有实验固定）。
  - **W 不由人工调参**，而是取"最近若干请求的检索单元刚好填满缓存"的请求数，由缓存容量与平均每请求单元数推导得出。
  - 两级缓存用同一评分规则但作用于不同请求流：共享缓存用全部节点的检索记录，本地缓存只用路由到该节点的请求。
- **准入与逐出**：分数达到阈值 θ 才成为候选；默认首次检索不保留（避免一次性访问占用容量）；容量不足时按分数升序考察驻留单元，仅当能释放出**严格更低分**单元的空间时才准入；需求衰退的单元因近期贡献消失而被更高频单元替换。
- **缓存感知路由**：先限定在"在途请求数与最轻负载节点相差不超过 1"的节点集合内，再在其中选**持有该请求上下文单元本地块最多**者，平局按更低负载、再按轮转（round-robin）打破。共享缓存命中不影响该排序（任何节点都可访问）。负载约束防止热点本地缓存把请求全吸到同一节点。
