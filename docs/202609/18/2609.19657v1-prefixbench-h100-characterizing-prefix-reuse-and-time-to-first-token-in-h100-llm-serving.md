## 摘要
重复的提示前缀在 LLM 服务负载中日益普遍，出现在系统提示、模板化的检索增强生成流水线、智能体框架以及多轮对话中。诸如 vLLM 和 TensorRT-LLM 等现代推理运行时提供了跨请求复用先前计算的 KV 缓存状态的机制，然而，前缀复用在何时能实质性提升当代加速器上的服务性能、又在何时其收益受限于调度、缓存粒度、并发度或内存压力，仍不清楚。本文提出 PrefixBench-H100，一个可复现的基准与测量框架，用于刻画单块 NVIDIA H100 上的前缀复用。PrefixBench-H100 将受控的合成轨迹与对话式、检索式工作负载相结合，并在匹配的工作负载条件下评估两种广泛使用的 LLM 服务运行时。该基准变化共享前缀长度、后缀多样性、请求到达模式、并发度、输出长度和缓存配置，同时采集首 token 时延、token 间时延、端到端时延、吞吐量、缓存命中统计、GPU 内存使用量以及选定的性能剖析轨迹。PrefixBench-H100 的目标不是引入新的缓存算法，而是揭示前缀复用在 H100 级 LLM 服务中的实际运行包络。该研究识别出前缀复用能显著降低首 token 时延的区间，以及缓存压力侵蚀这些收益的区间，同时表明缓存有效性本身在很大程度上对并发度和输出长度不敏感；剩余的跨运行时差异产生于缓存之上，即调度层。

## Abstract
Repeated prompt prefixes are increasingly common in LLM serving workloads, appearing in system prompts, templated retrieval-augmented generation pipelines, agent frameworks, and multi-turn conversations. Modern inference runtimes such as vLLM and TensorRT-LLM provide mechanisms for reusing previously computed KV-cache state across requests, yet it remains unclear when prefix reuse materially improves serving performance on contemporary accelerators and when its benefits are limited by scheduling, cache granularity, concurrency, or memory pressure.   This paper presents PrefixBench-H100, a reproducible benchmark and measurement framework for characterizing prefix reuse on a single NVIDIA H100. PrefixBench-H100 combines controlled synthetic traces with chat-style and retrieval-style workloads, and evaluates two widely used LLM serving runtimes under matched workload conditions. The benchmark varies shared-prefix length, suffix diversity, request arrival pattern, concurrency, output length, and cache configuration, while collecting time-to-first-token, inter-token latency, end-to-end latency, throughput, cache-hit statistics, GPU memory usage, and selected profiling traces.   The goal of PrefixBench-H100 is not to introduce a new caching algorithm, but to expose the practical operating envelope of prefix reuse for H100-class LLM serving. The study identifies the regime where prefix reuse provides substantial first-token latency reductions and the regime where cache pressure erodes them, while showing that cache effectiveness itself is largely insensitive to concurrency and output length; the cross-runtime differences that remain arise above the cache, in the scheduling layer.

# PrefixBench-H100 论文中文总结

## 1. 核心问题与整体含义

- **研究动机**：重复提示前缀在 LLM 服务中越来越普遍，例如系统提示、RAG 模板、Agent 框架和多轮对话。vLLM 与 TensorRT-LLM 都已默认支持前缀缓存/KV 缓存复用，但“在 H100 上何时真正加速、何时收益受限”缺乏系统测量。
- **背景变化**：前缀缓存最初由 PagedAttention 在 A100 时代提出，当时 KV 内存是稀缺资源；而 H100 NVL 拥有 94 GB HBM3，KV 容量大幅提升，原有“缓存稀缺”假设可能已经改变。
- **核心问题**：论文不追问“前缀复用是否有效”，而是追问“瓶颈是否已从缓存层迁移到缓存之上的调度层”，以及前缀复用的实际操作包络在哪里。
- **整体含义**：PrefixBench-H100 是一个可复现的基准与测量框架，用于刻画单卡 H100 上 vLLM 与 TensorRT-LLM 的前缀复用行为，为运行时选择、调度调优和容量规划提供依据。

## 2. 方法论

- **核心思想**：
  - 不提出新的缓存算法，而是把两个生产级运行时当作黑盒，在相同负载、相同请求序列下进行头对头测量。
  - 通过受控合成轨迹与真实 RAG 模板轨迹，分离“缓存有效性”与“调度层差异”。
  - 以“前缀工作集 / KV 容量比”作为控制缓存压力区间的核心变量。

- **关键技术细节**：
  - 同一套 JSONL 工作负载，通过 OpenAI 兼容 `/v1/completions` 端点驱动两个运行时。
  - 使用单个异步 Python 负载生成器 `load_gen.py`，支持 burst（全量到达）和 fixed-rate（均匀间隔）两种到达模式。
  - 合成重复前缀轨迹：请求形式为 `⟨共享前缀⟩ ◦ ⟨唯一后缀⟩`，可独立控制共享前缀长度、后缀长度、输出长度、不同前缀数、请求数，并保证按 Qwen2 tokenizer 精确 token 化。
  - RAG 模板轨迹：长系统提示 + 8 个检索文档之一 + 8 个查询模板之一，用于验证合成结论在更真实后缀多样性下是否成立。
  - 指标采集：TTFT（p50/p95）、端到端时延、输出吞吐、请求吞吐、前缀缓存命中率、峰值 HBM、Prometheus `/metrics` 增量、Nsight Systems 代表性 trace。
  - 缓存命中率归一化：
    - vLLM：`prefix_cache_hits_total / prefix_cache_queries_total` 增量。
    - TensorRT-LLM：`usage.prompt_tokens_details.cached_tokens / prompt_tokens`。
    - 两者统一为“输入 token 中由缓存服务的比例”。
  - 缓存压力分析中引入解析“无驱逐命中率上限”：`1 - np/N`，其中 `np` 为不同前缀数，`N` 为请求数，用于区分“驱逐”与“重访次数差异”。

- **算法/流程说明**：
  - 先生成请求轨迹并写入 JSONL。
  - 负载驱动器按 burst 或 fixed-rate 发出请求。
  - 每个 cell 前后抓取运行时指标，计算增量。
  - 对同一 cell 分别运行 reuse-on 与 reuse-off，或不同 `tokens_per_block`、不同 KV 容量上限、不同模型规模/架构，形成对照。
  - 最后用统一 notebook 离线复现所有图表，无需 GPU。

## 3. 实验设计

- **数据集/场景**：
  - 合成重复前缀轨迹：控制前缀长度、后缀长度、输出长度、前缀数量、请求数量。
  - 真实 RAG 风格模板轨迹：模拟检索增强生成服务。
  - 模型：
    - Qwen/Qwen2-7B-Instruct（BF16，7.6B，32K 上下文，主模型）。
    - Qwen2.5-32B-Instruct（用于模型规模导致的 KV 容量收缩实验）。
    - Mistral-7B-Instruct-v0.3（用于跨架构泛化验证）。

- **Benchmark 内容**：
  - PrefixBench-H100 开源 artifact：基准代码、102 个 JSON per-cell 原始结果、合并 CSV、所有图表、`analysis.ipynb`。
  - 完整复现约 3 GPU 小时。
  - 通过 OpenAI 兼容 API 统一驱动两个运行时，确保看到相同 prompt 和请求调度。

- **对比方法/配置**：
  - vLLM 0.21.0 + PyTorch 2.11.0（CUDA 13.0）。
  - TensorRT-LLM 1.2.1 + PyTorch 2.9.1（CUDA 12.8），主要使用 PyTorch 后端。
  - TensorRT-LLM engine 后端单 cell 对照。
  - reuse-on vs. reuse-off。
  - TensorRT-LLM `tokens_per_block ∈ {32, 64, 128}`。
  - KV 容量上限：`num_gpu_blocks_override=3520` 或 `KvCacheConfig.max_tokens=56320`。
  - 输出长度 `{32, 128, 512}`。
  - 并发度 `{1, 4, 8, 16, 32}`。
  - 固定速率 `{1, 4, 8, 16} QPS`。
  - 前缀长度 `{0, 512, 1024, 2048, 4096, 8192}` 等。

- **四类主 sweep**：
  1. 顺序复用：并发 1，扫描共享前缀长度，建立 TTFT 收益上界。
  2. Burst 并发：
