## 摘要
可复用的前缀键值（KV）缓存在大语言模型（LLM）服务中可能超出GPU内存容量。内存语义闪存层级以SSD为后端提供容量，并包含有限的快速层，但逻辑KV命中并不一定已准备好供GPU取用。按需暂存会暴露SSD延迟，而立即暂存则可能在检索开始前很久就预留快速层容量。我们提出TempoKV，一种时序感知的资源提交层，它将提前获知复用与获取暂存资源分离。TempoKV将可复用KV命中记录为仅含元数据的声明，并在运行时估计的距检索时间降至使KV驻留并受保护免遭逐出所需的存储估计时间时，才请求提交。这些估计会适应运行时进展与暂存状态，而提交仍受可用受保护容量约束。我们在由SSD支持的CXL内存设备上，于vLLM和LMCache中实现了TempoKV，且不改变请求调度。在两个模型和三种前缀缓存比例下，与立即暂存相比，TempoKV将每请求的受保护快速层字节时间减少63-91%，同时保留提前暂存的大部分服务收益。在快速层容量扫描中，当容量从100 GiB降至25 GiB时，输出吞吐量和p95首token时间（TTFT）几乎不变。与未修改的LMCache的Device-DAX L1配置相比，TempoKV将p95 TTFT最多降低48.0%，并将输出吞吐量最多提升27.8%。

## Abstract
Reusable prefix key-value (KV) caches can outgrow GPU memory in large language model (LLM) serving. A memory-semantic flash hierarchy offers SSD-backed capacity with a limited fast tier, but a logical KV hit is not necessarily ready for GPU retrieval. Demand staging exposes SSD latency, whereas immediate staging can reserve fast-tier capacity long before retrieval begins. We present TempoKV, a timing-aware resource-commitment layer that separates early knowledge of reuse from the acquisition of staging resources. It records reusable-KV hits as metadata-only claims and requests commitment when the runtime-estimated time until retrieval falls to the storage-estimated time needed to make KV resident and protected against eviction. These estimates adapt to runtime progress and staging state, while commitment remains subject to available protected capacity. We implement TempoKV in vLLM and LMCache on an SSD-backed CXL memory device without changing request scheduling. Across two models and three prefix cache ratios, TempoKV reduces protected fast-tier byte-time per request by 63-91% versus immediate staging while retaining much of the serving benefit of advance staging. In a fast-tier capacity sweep, output throughput and p95 time to first token (TTFT) remain nearly unchanged as capacity decreases from 100 to 25 GiB. Compared with unmodified LMCache's Device-DAX L1 configuration, TempoKV reduces p95 TTFT by up to 48.0% and increases output throughput by up to 27.8%.

## 1. 核心问题与整体含义
- **背景**：LLM 服务中，可复用前缀 KV 缓存会超出 GPU HBM 容量，因此需要下沉到主机内存、SSD 或内存语义闪存层级中。
- **内存语义闪存**：以 SSD 提供大容量，以有限 DRAM/快速层作为缓存；例如 SSD-backed CXL Type-3 内存设备。
- **核心矛盾**：逻辑上的 KV 命中并不等于 KV 已准备好供 GPU 取用。命中对象可能仍在 SSD，需要先暂存到快速层并防止被逐出。
- **现有问题**：
  - **按需暂存（Demand）**：等到 GPU 检索时才从 SSD 搬运，暴露 SSD 延迟。
  - **立即暂存（Immediate）**：命中即提交资源，虽可隐藏延迟，但会过早占用有限快速层容量。
  - **队列排名/提前通知**：队列位置只表示顺序，不表示距检索的绝对时间；提前知道复用并不等于必须立刻预留容量。
- **整体含义**：TempoKV 将“提前获知 KV 可复用”与“获取暂存资源”解耦，目标是既隐藏 SSD 暂存延迟，又避免不必要的快速层受保护容量占用。

## 2. 方法论
### 2.1 核心思想
- TempoKV 是一个**时序感知的资源提交层**，用于决定 SSD-to-fast-tier 暂存何时提交。
- 命中先记录为**仅元数据的 staging claim**，不发起 I/O、不预留受保护容量。
- 当运行时估计的**距取用时间（TTU）**降至存储侧估计的**距就绪时间（TTR）**时，才请求提交暂存资源。
- 提交仍受存储侧有效性检查和可用受保护容量约束。

### 2.2 架构组件
- **Runtime Adapter**：估计 TTU，报告 staging claim，查询 claim 就绪状态。
- **TempoKV Controller**：结合 TTU 与 TTR 决定提交时机、管理 claim 状态与重规划。
- **Storage-Side Staging Provider**：估计 TTR，控制暂存、保护和容量检查。
- **运行时/存储侧边界**：运行时无需了解存储内部；存储侧无需重建请求执行。

### 2.3 关键时间估计
- **TTU（Time-to-Use）**：
  - 估计距 fast-tier-to-GPU 检索开始的时间，而非模型消费 KV 或产生首 token 的时间。
  - 基于 active batch、请求执行进度、调度顺序、前方运行/排队请求、校准执行成本、输出长度预测等。
  - 输出长度估计来自最近完成请求；对已生成 n token 的请求，剩余输出取已完成长度 N>n 的 N-n 均值。
  - TTU 随运行时状态变化而修订。
- **TTR（Time-to-Ready）**：
  - 估计若现在提交，matched KV 变为 resident 并受保护所需时间。
  - 基于已知快速层驻留、排队/进行中暂存工作、有效暂存服务速率。
  - 排除提交前等待和后续 GPU 检索；容量可用性单独检查。
  - 通过 metadata-only 投影暂存队列；只为既未驻留也未被现有暂存覆盖的对象增加 SSD 读取。
  - 并发操作共享有效聚合服务速率；TTR 由最后一个必需对象变为 resident 且 protected 的时间决定。

### 2.4 提交与重规划
- 定义估计 laxity：\(\hat L_c(t)=\hat{TTU}_c(t)-\hat{TTR}_c(t)\)。
- 当 \(\hat L_c(t)\le 0\) 或运行时请求检索时，claim 变为 eligible。
- eligible 只是允许尝试提交；provider 还需检查对象有效性、快速层驻留、额外受保护容量。
- 容量不足时 claim 保持 `PLANNED`，不暂存、不保护，且不阻塞其他 claim。
- 提交顺序可能不同于请求顺序：TTU 更长但 TTR 更大的 claim 可能更早 eligible。
- claim 状态：`PLANNED → STAGING → STAGE_READY → TRANSFERRING → RELEASED`。
- 已提交 claim 不因后续时序更新撤销；共享 KV 对象会被合并暂存和容量预留，避免重复 SSD 读取和重复容量占用。
- 若未提交 claim 在检索时无法获得保护，则退回普通 demand retrieval 路径；该选择与提交互斥。

### 2.5 实现
- 扩展 vLLM 与 LMCache；保持 vLLM 请求调度策略，复用 LMCache 前缀查找与 GPU 传输路径。
- 存储侧 provider 基于 XCENA MX1P CXL Type-3 内存设备，集成到 LMCache 的 DAX-backed L1 cache。
- 使用设备已有 range-management API 做 staging 与保护，以 pin/unpin 管理受保护范围。
- 控制器结合事件驱动更新与 50 ms 周期 tick。
