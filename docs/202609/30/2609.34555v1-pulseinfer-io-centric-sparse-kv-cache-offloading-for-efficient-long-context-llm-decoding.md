## 摘要
长上下文 LLM 服务日益受限于解码阶段，其中庞大的 KV 缓存限制了批大小，并导致 GPU 利用率不足。稀疏 KV 缓存卸载通过将大多数历史 KV 块存储在 CPU DRAM 中，并仅按需召回选中的块，从而扩展有效容量。然而，我们发现现有卸载系统将瓶颈转移到了 CPU-GPU 召回 I/O：召回量在不同层、解码步和请求之间差异很大，而按头稀疏选择会将召回碎片化为许多小的 PCIe 传输。本文提出 PulseInfer，一个以 I/O 为中心的稀疏 KV 缓存卸载系统。PulseInfer 通过可中断的逐层调度隐藏可变的召回延迟，通过 IO-Adaptive Offloading Admission 自适应调整卸载决策，并利用 SoloHead 稀疏选择与 gather-scatter I/O 引擎合并碎片化传输。在 SGLang 上实现后，PulseInfer 将解码吞吐量较 SGLang 提升至多 4.7 倍，较现有最佳卸载基线提升至多 2.6 倍，同时将 TPOT 降低至多 76%，并保持近乎无损的准确率。

## Abstract
Long-context LLM serving is increasingly bottlenecked by decode, where large KV caches limit batch size and underutilize GPUs. Sparse KV cache offloading expands effective capacity by storing most historical KV blocks in CPU DRAM and recalling only selected blocks on demand. However, we find that existing offloading systems shift the bottleneck to CPU-GPU recall I/O: recall volume varies widely across layers, decode steps and requests, while headwise sparse selection fragments recalls into many small PCIe transfers.   This paper presents PulseInfer, an I/O-centric sparse KV cache offloading system. PulseInfer hides variable recall latency with interruptible layer-wise scheduling, adapts offloading decisions with IO-Adaptive Offloading Admission, and coalesces fragmented transfers using SoloHead sparse selection and a gather-scatter I/O engine. Implemented on SGLang, PulseInfer improves decode throughput by up to 4.7x over SGLang and 2.6x over the best existing offloading baseline, while reducing TPOT by up to 76% and preserving near-lossless accuracy.

# PulseInfer 论文深度总结

## 1. 核心问题与整体含义（研究动机与背景）

- **长上下文解码的内存瓶颈**：随着上下文窗口扩展至数十万甚至百万 token，推理成本重心转向解码阶段（可占端到端 90% 以上）。KV 缓存大小随上下文线性增长，导致 GPU 显存仅能容纳少量并发请求，解码成为**内存容量瓶颈**，严重限制批大小与吞吐。
- **稀疏 KV 缓存卸载的思路**：将大部分历史 KV 块放入 CPU DRAM，仅在 GPU 保留摘要（digest）与热块，解码时按需召回被选中的重要块，从而扩展有效 KV 容量。
- **瓶颈转移**：卸载把瓶颈从 GPU 容量转移至 **CPU–GPU 召回 I/O**。PCIe 有效带宽比 HBM 低 1–2 个数量级，尤其在小型传输下更差。同步召回系统（ArkVale、PQCache）GPU 利用率仅约 35%，即便一层提前预取的 InfiniGen 也仅约 45%。
- **两大 I/O 病理**：
  - **召回量动态多变**：召回 token 数随解码步、层、请求、批组成变化，呈右偏长尾分布；不同层中位召回量差异可达 5×；请求长度分布随时间漂移（Mooncake、ServeGen 轨迹跨三个数量级）。
  - **召回粒度过于细碎**：逐头独立选择导致大量小规模、离散的 PCIe 传输（典型配置下单头单层仅 8 KB），PCIe 5.0×16 下有效带宽仅约 6 GB/s，同时逐头 digest 占用可观显存。
- **整体含义**：论文主张以 **I/O 为中心** 重新设计卸载系统，将召回 I/O 视为一等可调度事件，通过“隐藏、控制、合并”三条主线解决瓶颈。

## 2. 方法论：核心思想与关键技术细节

### 2.1 总体设计（Hide / Control / Coalesce）
- **Hide**：可中断逐层调度（IRQ），将请求分为**普通批**（KV 常驻 GPU）与**卸载批**（KV 存于 CPU），在层粒度交错执行。
- **Control**：IO-Adaptive Offloading Admission（IOAA），动态搜索最优普通/卸载批划分。
- **Coalesce**：SoloHead 稀疏选择 + gather-scatter I/O 引擎，合并碎片化召回。

### 2.2 可中断逐层调度（IRQ）
- **OS 中断类比**：CPU 进程阻塞等待 I/O 时，OS 调度其他就绪进程，收到 I/O 完成中断后再恢复原进程。
- **执行流程**：卸载批到达第 m 层时先做稀疏选择，提交缺失块的召回请求，然后**让出 GPU**；调度器切换到普通批继续执行；普通批在每层边界检查召回是否完成，未完成则继续下一层，完成后切回卸载批执行注意力与 FFN。
- **两个关键性质**：
  - **重叠深度（overlap depth）自适应**：由实际 I/O 完成时间决定，而非固定一层。
  - **普通批与卸载批 I/O 隔离**：短请求不再受长请求召回 I/O 的队头阻塞（图 3 显示混合批下 <8K 请求 TPOT 增加 5×）。
- **半同步中断检测**：同步检测需频繁 CPU–GPU 同步，损害 GPU 流水线；异步检测会导致切换延迟。IRQ 折中方案：仅同步等待普通批当前层的**注意力 kernel 完成**，在 FFN 仍在执行/排队期间检查 I/O 完成并决定下一任务，兼顾高利用率与及时恢复。

### 2.3 IO-Adaptive Offloading Admission（IOAA）
- **吞吐量模型**：设普通批大小 $B_n$、卸载批大小 $B_o$、重叠深度 $m$，则
  $$\text{Throughput} \propto \frac{m}{m+1}B_n + \frac{1}{m+1}B_o$$
  由于 $m \geq 1$，普通批权重更大；但增大 $B_o$ 可释放显存、提高总批大小，同时会增大 $m$。
- **准入问题**：对 n 个等待请求，共有 $2^n$ 种分配。IOAA 建模为二叉搜索树，每个节点决定一个请求的去向。
- **两条剪枝规则**：① 超出剩余显存预算的分支立即剪枝；② 长度单调性规则——较长请求进入普通批后，较短请求不再考虑卸载。30 个等待请求时平均仅访问 **3.16 个节点**。
- **重叠深度离线剖析**：$m = \lceil t_{io}/t_{layer} \rceil$，$t_{io}$ 随 $B_o$ 近似线性增长，$t_{layer}$ 随 $B_n$ 变化平缓。IOAA 在离散 $(B_o, B_n)$ 网格上离线剖析，运行时插值估计。

### 2.4 SoloHead 稀疏选择
- **动机**：注意力头分化为**检索头**（关注中段语义丰富 token）与**流式头**（关注 sink/局部 token，常驻 GPU 无需召回）；IMPRESS 发现检索头间 token 重要性排序 Jaccard 重叠常超 0.8。
- **Middle Attention Mass（MAM）**：对每个 query head $q$，$\text{MAM}_q = \sum_{i \in \text{middle}} A_q(i)$；KV 头 $h$ 的 MAM 为其映射的所有 query head MAM 均值。
- **策略**：每层仅保留 MAM 最高的一个检索 KV 头的 block digest，由它选择 top-$k$ 块，**所有 KV 头共享该块集**。将逐头传输转为逐层/逐 token 传输，消除逐头 digest。
- **准确性度量**：逐层 KL 散度 $D_L = \text{KL}(p_{full}, p^L_{sparse})$。对比 headwise、average、SoloHead、SoloHead-reversed 四种策略，SoloHead 接近 headwise，而 reversed 最差，验证 MAM 有效。

### 2.5 Gather-Scatter I/O 引擎
- 将 DRAM 中散落的召回块**gather 到连续 pinned CPU staging buffer**，用**单次大 DMA** 传输到 GPU staging buffer，再用轻量 scatter kernel 写入 GPU KV 缓存。
- 额外 CPU/GPU 拷贝运行在 DRAM/HBM 带宽上，远快于碎片化 PCIe 传输。传输 >512 块时有效带宽比线程化 `cudaMemcpyAsync` 高 2× 以上。

### 2.6 实现要点
- 基于 **SGLang** 实现，约 **9K 行代码**。
- **两级调度器**：外层按解码步调整批组成，内层在层边界做协作式上下文切换，保存当前层索引、中间激活与前向元数据。
- **零同步 I/O 提交**：用共享 UVM buffer 存 ready flag 与选中块索引，专用 CPU 轮询线程检测后异步提交召回任务，使主推理线程无需等待召回任务构造与提交。

## 6. 主要结论与发现

- **吞吐**：较 Vanilla（SGLang）提升 **1.5×–4.7×**，较最佳卸载基线提升 **1.1×–2.6×**；输入越长增益越大（14B 上 Vanilla 从 324 降至 81 tok/s，PulseInfer 仅从 488 降至 380 tok/s）。
- **延迟**：较 InfiniGen TPOT 降低 **16.0%–76.4%**（1.19–4.23× 更低）；但相对 Vanilla 平均 TPOT 增加 2.2×，是有意的吞吐-延迟权衡。
- **短请求隔离**：<8K 请求 TPOT 仅增 1.5×，而现有卸载基线增 6.7–8.3×。
- **GPU 利用率**：接近 Vanilla（约 95%），召回 I/O 几乎被完全隐藏。
- **批大小**：总批大小达 Vanilla 的 4.7×。
- **精度**：近乎无损，Qwen-3 两个模型上甚至略优于全注意力；reversed-MAM 配置显著掉点，验证 MAM 的有效性。
- **鲁棒性**：PCIe 带宽降至 0.4× 时仍快于 Vanilla，而 InfiniGen 仅在满带宽下追平 Vanilla；GPU 显存增大时 PulseInfer 持续获益，InfiniGen 因 I/O 受限不获益。

## 7. 优点

- **问题洞察深刻**：将召回 I/O 明确刻画为“动态量 + 碎片化”两大病理，用图 4–8 的实测数据支撑，动机扎实。
- **跨层协同设计**：算法层（SoloHead）+ 调度层（IRQ、半同步检测）+ 准入层（IOAA）+ 引擎层（gather-scatter、零同步提交）形成完整闭环，而非单点优化。
- **OS 中断思想的成功迁移**：把可变 I/O 延迟隐藏问题转化为调度问题，避免了对 I/O 时长的预测依赖。
- **MAM 指标设计巧妙**：利用模型结构性头分化（跨数据集稳定），可离线一次性选定，且与 I/O 合并目标天然契合；反向验证实验增强了说服力。
- **轻量且可落地**：IOAA 平均仅访问 3.16 节点，约 9K 行代码基于 SGLang 实现，工程可行性强。
- **实验维度丰富**：合成+真实轨迹、多模型、消融、敏感性（显存、PCIe 带宽）齐备，结论有较强支撑。

## 8. 不足与局限

- **应用场景受限**：仅针对 PD 分离部署下的**解码实例**，跳过 prefill，未验证与 prefill 阶段、连续批处理、投机解码等机制的交互。
- **离线 profiling 依赖**：IOAA 的重叠深度模型需针对每个模型-硬件组合离线剖析 $(B_o, B_n)$ 网格，迁移到新平台需重新 profiling，且未讨论 profiling 成本与插值误差影响。
- **SoloHead 的泛化风险**：MAM 头选择离线一次性完成，论文仅在 Qwen-3 系列上验证；对头分化不明显或非 GQA 架构的模型，共享 top-k 是否仍保持精度未知。
- **精度评估覆盖有限**：仅 LongBench，未覆盖推理、代码、多轮 agent 等长上下文主流场景；thinking budget 固定 2048，未探索不同预算下的表现。
- **公平性存疑**：基线均为自行复现，未给出调优细节；缺少多次运行方差、置信区间与统计显著性检验。
- **收益不均衡**：MiniMax M2.5（4 GPU TP 并行）增益明显小于 14B，说明聚合召回带宽会

说明聚合召回带宽会成为新的约束——4 GPU 张量并行下，每张卡各自发起 PCIe 召回，单卡有效带宽被分摊，隐藏 I/O 的难度上升，因此该系统对**单机单卡/少卡**场景的收益更显著，跨节点、跨卡扩展的 I/O 聚合策略尚未展开讨论。

- **CPU 侧开销未充分量化**：零同步提交依赖专用 CPU 轮询线程，gather-scatter 又引入额外的 DRAM→pinned buffer→GPU 两级拷贝。这些操作虽然不占用 PCIe 的“碎片化”路径，但会消耗 CPU 核、DRAM 带宽与 staging buffer 显存/主存；论文未报告 CPU 利用率、pinned 内存占用及该开销在极端批大小下的饱和点。
- **调度公平性与 SLO 保障缺位**：IRQ 的核心收益是保护短请求免受队头阻塞，但论文以平均 TPOT 与分组 TPOT 呈现，未给出尾延迟（P99）或面向 SLO 的准入控制策略。当普通批长期占据 GPU 时，卸载批可能出现饥饿，IOAA 仅按吞吐建模，未显式引入公平性约束。
- **半同步检测的成立条件**：该方案依赖“FFN kernel 执行/排队时间足以覆盖 I/O 完成检测窗口”。在极小模型、极小批或 FFN 被高度优化的情形下，窗口可能不足，导致切换延迟回升甚至退化为异步检测的抖动；论文未做该边界条件的敏感性分析。
- **稀疏预算固定**：默认 2,048 token（16 sink + 128 local + 1,904 中段）为全局固定配置，未讨论按层、按请求或按难度自适应调整预算，也未分析预算大小与精度/吞吐的连续权衡曲线。
- **块级 top-k 的粒度误差**：block size = 16 意味着召回以块为单位，边界处的重要 token 会被整块纳入或整块丢弃；论文用逐层 KL 与端到端精度间接验证，但未分析块大小对精度与 I/O 量的直接影响。
- **能耗与成本维度缺失**：作为服务系统论文，未报告每 token 能耗、DRAM 访问能耗或单位吞吐的硬件成本，而这恰是卸载方案与“直接扩显存/扩卡”方案对比时的关键决策依据。

## 9. 总体评价与启示

- **定位**：PulseInfer 是一篇典型的**系统与算法协同**工作，其价值不在于提出某个单点新算子，而在于识别出稀疏 KV 卸载中被长期忽视的**召回 I/O 病理**，并给出一套自洽的“隐藏—控制—合并”解法。它把“预测 I/O 何时完成”这一难题转化为“让 GPU 在等待期间做别的事”的调度问题，思路简洁且鲁棒。
- **方法论启示**：
  - 将 **OS 中断/协作式调度** 语义引入 GPU 推理循环，是隐藏可变长 I/O 延迟的通用范式，可迁移到权重卸载、专家卸载（MoE offloading）等场景。
  - **结构性先验（头分化）** 往往比在线估计更廉价可靠：MAM 只需离线一次标定，却能换来逐头 I/O 到逐层 I/O 的数量级粒度下降，说明“少算一点、算得准一点”在系统优化中常优于“算得更多”。
  - **准入控制作为一等公民**：IOAA 把批组成选择形式化为可剪枝的搜索问题，并用极低的节点访问量（3.16）换取自适应，提示调度器不必追求全局最优，剪枝后的启发式已足够。
- **适用边界**：最适合**单机、单卡或少卡、长上下文、解码为主、请求长度高度异构**的在线服务；在纯短上下文、显存充裕或跨节点张量并行的场景中收益递减。
- **对后续研究的开放问题**：
  1. 与 prefill、chunked prefill、投机解码、prefix caching 的协同；
  2. 面向 SLO/尾延迟的公平准入与抢占策略；
  3. 多卡/多节点下召回 I/O 的聚合与全局调度；
  4. 自适应稀疏预算与块粒度的联合优化；
  5. 跨模型家族的 MAM 头选择泛化性（非 GQA、MLA 等注意力变体）。
- **一句话总结**：PulseInfer 证明了在稀疏 KV 卸载系统中，**把召回 I/O 当作可调度事件而非必须等待的延迟**，是突破长上下文解码内存墙的一条高性价比路径，其 1.5×–4.7× 的吞吐提升与近乎无损的精度，为后续“以 I/O 为中心”的推理系统设计提供了可复用的范式与工程基线。
