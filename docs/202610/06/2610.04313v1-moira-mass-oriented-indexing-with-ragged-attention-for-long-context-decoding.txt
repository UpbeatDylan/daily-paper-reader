# MOIRA: Mass-Oriented Indexing with Ragged Attention for Long-Context Decoding 

Dich Nhat Minh Nguyen Tran Dang Duong Nguyen 

# Abstract 

Long-context decoding is limited by memory bandwidth, because every output token reads the KV cache of every layer. Sparse decoding reduces this cost by reading only part of the KV cache. We observe that the number of pages a query needs varies widely across KV heads, layers and steps. Fixed budgets are simple, but they are sized for demanding cases and tuned per workload; adaptive budgets follow this variation more flexibly, but existing designs pay for it with extra selection cost or training. At the kernel level, FlashAttention-3 (FA3) and FlashInfer are designed for rows of similar length: with page lists whose length differs per KV head, they pad the lists, which forfeits much of the sparse saving, leave thread blocks unbalanced, or rely on a host-side plan that runs outside the CUDA graph. We propose Moira, a training-free sparse decode path in vLLM whose budget adapts per KV head and per layer. For every request, layer, KV head and step, a coverage rule keeps the smallest set of pages whose estimated attention mass reaches a fraction γ. A new kernel, self-planning attention, lets each thread block derive its own share of the work from the list lengths, so the whole decode step stays inside the CUDA graph. On an H200, at RULER’s 128k context, Moira with γ=0 .99 matches dense accuracy while reading about 30% of the pages and reduces the time per output token (TPOT) by 2.2–2.5 × relative to dense FA3; with γ=0 .98 it reduces TPOT by 2.7 × and stays within the noise of dense. Under high serving load it raises throughput by up to 51%. These results suggest that a budget adapted per head and layer, paired with a kernel that keeps such budgets inside the CUDA graph, makes sparse decoding both flexible and fast. 

# 1 Introduction 

Long-context decoding is limited by memory bandwidth: ev-ery output token reads the KV cache of every layer. Existing work reduces this cost by reading only part of the KV cache at each decode step, and falls into two groups. Fixed-budget methods , such as Quest (Tang et al., 2024) and the trained sparse attention of recent production models (DeepSeek-AI, 2025; Lai et al., 2026; Qiu et al., 2026), read the same number of tokens, the budget , for every head and every step. 

Adaptive-budget methods let the budget vary with the query: Twilight (Lin et al., 2025) selects tokens per query head with top-p, FFD (Liu et al., 2026) keeps the blocks whose score, estimated from a low-bit copy of the keys, exceeds a threshold, and Elastic Threshold Attention (Haris et al., 2026) uses a learned threshold. However, the budget that is actually needed varies widely across KV heads, across layers and across steps (Figure 1). A fixed budget cannot follow this variation: it must be sized for the hardest case, so most heads over-read, and it must be re-tuned for each workload. Adaptive methods already let the budget vary per head, layer and step, but they pay for it elsewhere: Twilight selects per query head and plans its lists on the host, FFD scans a low-bit copy of every key at every step, and Elastic Threshold Attention requires training. On the kernel side, the selected pages are read by decode kernels such as FlashAttention-3 (FA3) (Shah et al., 2024) and FlashInfer (Ye et al., 2025), which are built for rows of similar length. When each KV head has a list of its own length, they either pad the lists, which forfeits much of the sparse saving, read the exact lengths but leave thread blocks unbalanced, or balance them with a host-side plan that must run outside the CUDA graph before every step. In this paper, we propose Moira (Mass-Oriented Indexing with Ragged Attention ), a training-free sparse decode path inside vLLM (Kwon et al., 2023) that addresses both limita-tions. First, Moira applies a coverage rule : for every request, layer, KV head and step, it keeps the smallest set of pages whose estimated attention mass reaches a fraction γ, and one fused kernel evaluates the rule. Second, a new kernel, 

self-planning attention , lets each thread block derive its own share of the work from the list lengths in device memory, so the whole decode step stays in vLLM’s CUDA graphs. On an H200 at 128k, Moira with γ=0 .99 matches dense accuracy on RULER (Hsieh et al., 2024) with 27–33% of the page reads and reduces the time per output token (TPOT) by 2.2–2.5 × relative to dense FA3. arXiv:2610.04313v1 [cs.AI] 3 Oct 2026 MOIRA: Mass-Oriented Indexing with Ragged Attention 

Our contributions are: • A coverage rule for per-head, per-layer budgets. We show that the number of pages a query needs varies across KV heads, layers and steps, and that one cover-age rule follows this variation across models, context lengths and tasks with γ fixed across them, whereas a fixed budget must be re-tuned for each case or profiled per KV head on the target model (Sections 2.2.1, 5.5.1 and 5.5.2). This rule is our main contribution. • A kernel that keeps such budgets in the CUDA graph. 

Existing decode kernels pad lists of different lengths, leave thread blocks unbalanced, or balance them with a host-side plan. Self-planning attention balances them on the GPU, so the rule runs inside vLLM’s CUDA graphs without padding or a host plan (Figure 2, Sec-tion 3). • System and evaluation. # 2 Background and Motivation 

2.1 Background 

2.1.1 Decode attention in a paged serving engine 

Each decode step generates one token per request, whose query attends over the request’s whole KV cache. With grouped-query attention (GQA), G query heads share one KV head, so the unit of work is a row : one (request, KV head) pair whose keys and values are read once for all G

query heads. Four requests on Llama-3.1-8B (8 KV heads) give 32 rows per step. vLLM (Kwon et al., 2023) stores the KV cache in fixed-size pages (64 tokens here); each request’s pages are listed in a block table, through which the kernel reads its rows. These 32 rows are far fewer than the 132 streaming multipro-cessors (SMs) of an H200. To fill the GPU, decode kernels cut long rows into chunks, one per thread block, and merge the partial results through their log-sum-exp ( split-KV , or Flash-Decoding (Dao et al., 2023; Hong et al., 2024)). The cut requires a plan : which chunk of which row each thread block processes. FA3 (Shah et al., 2024) builds this plan on the GPU from the shape of the batch; FlashInfer (Ye et al., 2025) builds it on the host, in plan() , from the length of each request. A decode step lasts a few milliseconds, so host launch cost matters; vLLM captures the step once as a CUDA graph 

and replays it at every step, which re-launches the captured kernels without host involvement. Host work that depends on the current step, such as FlashInfer’s plan() , cannot be part of the graph: it must run before every replay, or be removed.

2.2 Motivation 

2.2.1 The budget must adapt per KV head and per layer 

The needed budget varies across layers, KV heads and steps. We record C⋆(0 .95) at every decode step of 60 Long-Bench requests on Llama-3.1-8B and Qwen3-4B, for every layer and KV head (Figure 1). On Llama-3.1-8B a row needs 21.6% of the context on average to keep 95% of the mass: 68% in the first layer but only 9% in several others (Fig-ure 1a). The coefficient of variation (CV, standard deviation over mean) of the page count is 0.61 across layers, 0.74 across the KV heads of one layer at one step, and 0.53 across the steps of one (layer, KV head). Totals over all layers vary much less (CV 0.13–0.18 across KV heads, requests and steps): the variation appears at the granularity of (layer, KV head), which is where the budget must be set. 

Fixed budgets over-read. A fixed budget must cover the rows that need the most. With the smallest budget that lets 90% of the rows keep 95% of the mass, a single token count shared by all rows reads 2.38 × the coverage set (Figure 1b). One set per KV head is the right granularity. If every KV head of a layer reads as many pages as its longest head, page reads double, from 21% to 42% of the dense cache over a batch of 32 requests (Figure 1c). Selecting per query head, as Twilight does, needs 1.51 × the pages at the same output error, because the G query heads share one KV head and every page any of them selects must be read. 

The budget should therefore be chosen per (request, layer, KV head, step), from the attention mass averaged over the query heads of the group. This is the coverage rule of Section 3.2. 

2.2.2 Existing kernels forfeit the savings 

With an adaptive per-head budget, each row’s page count is known only on the GPU, within the step, after selection. A suitable kernel must (i) read only the selected pages, (ii) di-vide the work evenly among thread blocks, and (iii) need no host involvement within the step, so that it can run inside a CUDA graph. Figure 2 shows that every existing kernel misses at least one condition. 

Padding reads pages that were not selected. A rectangu-lar grid gives every row enough thread blocks for the longest row and pads the rest; the padding is read like real pages, so sparse attention is as slow as dense (Figure 2a). Power-of-two buckets reduce the padding but remain 1.4 × slower than reading exactly the selected pages (Figure 2b). Both miss (i). 

Exact lengths are not enough. FA3’s varlen mode takes a length per row and reads only the selected pages, but its split scheduler does not balance rows of different lengths: thread blocks of long rows finish last while the others sit idle (Figure 2c). At equal total work, FA3 slows by 23–32% as row lengths spread. FA3 misses (ii). 

Balance planned on the host does not fit the step. Flash-Infer cuts every row into equal chunks, balancing the load (Figure 2d), but computes this plan on the host from the row lengths. With adaptive lists the lengths change at every layer and step, so the host must fetch them from the GPU and re-plan each time; at 32k ×16 the plan alone costs 2.4 × the kernel time and cannot be part of a CUDA graph. FlashInfer misses (iii). 

Planning from past steps overflows. One could instead reserve thread-block slots per row at capture time, sized from earlier steps. But lengths change between steps: with slots sized from the previous step, 40% of the rows overflow, and a safety margin that cuts the overflow to 2.4% reserves 1.77 × the needed slots, so the kernel again does extra work.

# 3 Design 

Moira replaces vLLM’s FA3 decode attention with four kernels that run in sequence at every layer (Figure 3), each over all rows b of the step: Step 1 (Estimate ) approximates the attention mass of each page from a small summary, without reading the keys (Section 3.1); Step 2 (Select ) keeps the fewest pages that cover a fraction γ of the mass and writes each row’s page list (Section 3.2); Step 3 (Attend ) reads exactly the pages in the list, with the work spread evenly over the thread blocks (Section 3.3); Step 4 (Merge ) combines the partial results of each row. Select chooses a budget per request, layer, KV head and step; Attend partitions the work on the GPU without the host; Estimate keeps the cost of selection small relative to the reads it saves.

# 4 Implementation 

Integration with vLLM. Moira is a Python module of Triton kernels, loaded into vLLM 0.30 through an import hook. It replaces the decode attention of the FA3 backend and changes neither the model code nor the KV cache lay-out. The kernels address vLLM’s bfloat16 (bf16) KV cache through its tensor strides as an array [page, KV head, 64 tokens, 2D], so they work with both memory layouts that vLLM supports: token-major (NHD, the default) and head-major (HND). 

Decode steps and mixed steps. In a pure decode step, FA3 is skipped entirely: the four Moira kernels run instead and are captured in vLLM’s full CUDA graph. In a mixed step ,where some requests are prefilling and others are decoding, Moira handles the decode rows and FA3 still handles the prefill rows. So that FA3 does not recompute the decode rows, Moira passes FA3 a copy of the step metadata in which the sequence lengths of the decode rows are zero; FA3 skips them and computes the prefill rows exactly as dense vLLM does.

The KV capacity that vLLM reports is therefore almost un-changed: it differs by only 0.06% (Llama-3.1-8B: 840,320 vs. 839,808 tokens; Qwen3-4B: 802,368 vs. 801,920). Plac-ing the summaries inside the KV cache would reduce the capacity by 1.6%. 

Correctness checks. At γ=1 , Moira matches FA3 to within one bf16 unit in the last place (ulp), CUDA-graph replay is bit-identical to eager execution, and the page lists of Select match a float32 reference of the rule on 64/64 test rows; Appendix B gives the details. 

# 5 Evaluation 

Our experiments are driven by the following research ques-tions (RQs): 

RQ1. How does Moira compare with prior methods? We compare accuracy and latency at 128k with dense attention, Quest, Twilight and FFD. 

RQ2. Does an adaptive budget beat a fixed one? We keep the estimator and kernels of Moira and replace the coverage rule by fixed, proportional and profiled budgets at equal reads. 

RQ3. Does the kernel keep its speed when page lists differ in length? We vary the spread of row lengths at a fixed mean and compare Attend with FA3, padding, bucketing and FlashInfer. 

RQ4. How much faster is a whole decode step? We mea-sure TPOT in vLLM from 8k to 130k tokens and break one step into kernels. 

RQ5. Does Moira raise throughput in online serving? 

We serve LongBench prompts in a closed loop at increasing concurrency. 

5.1 Datasets 

• RULER-13 (Hsieh et al., 2024) at 128k (13 tasks × 20 documents): long-context retrieval (RQ1). • AIME 2024+2025 (60 problems × 8 samples, t=0 .6,top-p 0.95, top-k 20, at most 32,768 generated tokens): long reasoning (RQ2). • LongBench (Bai et al., 2024) (21 tasks, 4,750 samples): shorter prompts. Its documents also supply the timing prompts: batches of 8k ×32 to 130k ×4 tokens (RQ4) and two serving sets of 4k–126k tokens (RQ5). 

5.2 Evaluation metrics 

• Accuracy : the benchmark score; differences from dense are tested with a paired bootstrap (95%). • Token KL : KL divergence of a method’s token distri-bution from dense on teacher-forced dense answers. • Page reads : fraction of KV pages read relative to dense, counted on the GPU. Quest and Twilight count reads in tokens and FFD in 128-token blocks, so for them we compare accuracy and time only. • Latency : TPOT , the time per output token (in serving, the median over requests); Attn , the selection plus atten-tion time of one decode step; Host , the CPU planning time per step. • Throughput : output tokens per second during serving. 

5.3 Baselines 

Dense FA3 (vLLM’s default) and dense FlashInfer; Quest (Tang et al., 2024) with a 36,864-token budget (Quest-36k); Twilight (Lin et al., 2025) with a 36,864-token Quest pre-filter and top-p 0.85 (Twilight-36k); FFD (Liu et al., 2026) with its default δ=7 , each with its authors’ code on the same H200 (Quest through Twilight’s implementation of its rule). Moira uses γ=0 .98 unless noted, with every layer and KV head sparse.

# 6 Discussion 

This section examines in more detail how Moira spends its budget in a real run. 

6.1 Where does the budget go? 

In the AIME run of Moira ( γ=0 .98 , Qwen3-4B-Thinking), the mean fraction of pages kept per (layer, KV head) ranges from 3.7% to 92%. Layers 0–3 keep 56–74% of their pages, the sparsest layers about a quarter, and within one layer the KV head that reads the most keeps a median of 4.0 × as many pages as the one that reads the least (up to 16.6 ×). The estimator thus reproduces, in a real run, the variation that Figure 1a shows for the oracle sets. 

6.2 Why do fixed budgets fail on long reasoning? 

We group the 60 AIME problems by the median length of their eight dense solutions: 23 are shorter than 16k tokens, 22 longer than 24k, and 15 in between. On the 23 short prob-lems, every arm of Table 2 except proportional top-k solves every sample. On the 22 long problems, Moira reaches 42.0% (dense 40.3%), while every static budget scores lower: fixed K 31.8–36.4%, profiled K 34.7–38.6% and propor-tional top-k 17.6%. A few under-budgeted steps lengthen the reasoning and push it past the length limit. Problem II-5 of AIME 2024 shows this most clearly: dense solves 6 of 8 samples with a median of 31.5k tokens and Moira 7 of 8, while proportional top-k truncates all 8 samples and both profiled budgets truncate 6. 

# 7 Threats to Validity 

Internal validity. Prior methods run with their authors’ code and kernels on the same GPU, with the settings of Section 5.3; Quest’s rule runs as implemented in Twilight’s code. Quest and Twilight do not run inside vLLM, so we compare them by Attn and Host only. FFD’s TPOT is mea-sured in its own runtime, whose cost outside attention may differ from vLLM’s, and with prompts cut to equal length because its cache holds one length per batch. FlashInfer c

runs inside the CUDA graph with one plan made for rows of full width, our wiring, since planning at every step is not possible there. The FA3 c and FlashInfer c rows use vLLM’s head-major (HND) KV-cache layout, under which Moira is 0.3 ms slower than in the default token-major (NHD) layout; Table 1 reports Moira under the same layout. With every page kept, Moira reproduces dense FA3 (token KL 0.0003; Appendix B). 

Construct validity. Page reads are counted on the GPU for every (request, layer, KV head); Quest and Twilight select to-kens and FFD 128-token blocks, so against them we compare accuracy and time rather than reads. Timings are medians of repeated runs on an otherwise idle GPU with dense and sparse arms interleaved, and accuracy differences are tested with a paired bootstrap by document or by problem. 

External validity. We evaluate 4B and 8B models from two families with a bf16 KV cache on one H200, under vLLM 0.30. On larger models the GEMMs take a larger share of the step, so the speedup will be smaller. Quantized KV caches, tensor parallelism and latent attention are not covered, serving is measured in a closed loop only, and Moira saves bandwidth, not capacity: the full KV cache stays resident. 

# 8 Related Work 

Fixed budgets. Quest (Tang et al., 2024) bounds the logits of each page with a per-channel key box and keeps a fixed token budget. CompKV (Huang et al., 2026) estimates each block’s mass from the mean and variance of its keys, the same approximation as mvar, but keeps a fixed number K

of blocks and compensates for the dropped ones with the block mean. InfiniGen (Lee et al., 2024), ShadowKV (Sun et al., 2025), MagicPIG (Chen et al., 2025), RetrievalAt-tention (Liu et al., 2025) and RetroInfer (Chen et al., 2026) predict or retrieve important tokens, often with CPU offload; The Sparse Frontier (Nawrot et al., 2025) evaluates these trade-offs. Production sparse attention is trained: DeepSeek Sparse Attention (DeepSeek-AI, 2025), MiniMax Sparse At-tention (Lai et al., 2026) and Qwen3.8-Next (Qiu et al., 2026) learn an indexer and keep about 2,048 tokens per query, so their kernels never see variable lengths. Moira needs no training and makes the budget an output of the selection. 

Adaptive budgets. Twilight (Lin et al., 2025) applies top-

p to Quest’s candidates per query head, attends through FlashInfer with a host plan() per layer and step, and uses a uniform budget in its end-to-end evaluation. Tac-tic (Zhu et al., 2026) splits requests into FlashInfer sub-requests. SeerAttention-R (Gao et al., 2025) thresholds a learned block gate per KV head but pads to the longest se-lection, and PSA (Zhou et al., 2025) grows its budget with a host loop per layer. Double-P (Ni et al., 2026) uses hier-archical thresholds, SpotAttention (Ahmad & Yun, 2026) applies top-p to a learned selector, and Elastic Threshold Attention (Haris et al., 2026) trains its thresholds; a hybrid CPU–GPU design (Yao et al., 2026) selects per head across PCIe; vAttention (Desai et al., 2026) bounds the error statis-tically. FFD (Liu et al., 2026) is the closest systems design: its fused Triton kernels need no index lists, scan a 2-bit copy of every key (Section 5.5.1), and are captured in a CUDA graph by its own runtime. None of these methods runs in-side the CUDA graphs of a serving engine; Moira brings MOIRA: Mass-Oriented Indexing with Ragged Attention 

per-KV-head budgets there at low cost. 

Per-head KV eviction. Ada-KV (Feng et al., 2025), HeadKV (Fu et al., 2025), DuoAttention (Xiao et al., 2025), LServe (Yang et al., 2025b), KV-Compress (Rehg, 2024) and HARD-KV (Yang et al., 2026) set per-head budgets once after prefill, offline, or every 128 steps (HARD-KV, inside vLLM’s CUDA graphs), mostly on padded grids; H2O (Zhang et al., 2023), StreamingLLM (Xiao et al., 2024) and SnapKV (Li et al., 2024) evict tokens without looking at the current query. They change what is stored; Moira changes what is read, at every step. 

Decode kernels. Flash-Decoding (Dao et al., 2023; Hong et al., 2024) and Lean Attention (Sanovar et al., 2025) split long sequences across thread blocks. FlashAttention (Dao et al., 2022; Dao, 2024; Shah et al., 2024) chooses splits on the GPU from the batch shape, and FlashInfer (Ye et al., 2025) balances ragged lists with a host plan. Our kernel derives an equal-cost partition from per-row lengths in device memory. 

# 9 Conclusion and Future Work 

Sparse decode pays off most when the budget follows the query and the kernel follows the budget. Moira selects pages per (request, layer, KV head, step) with a coverage rule and attends over the ragged lists with a self-planning kernel inside vLLM’s CUDA graphs. On an H200 at 128k, with 

γ=0 .99 it matches dense RULER accuracy with 27–33% of the page reads and reduces TPOT by 2.2–2.5 ×; on synthetic batches of 8k–130k tokens it lowers TPOT by 1.38–2.69 × at 

γ=0 .98 , raises serving throughput by 45–51% under high load, and on long reasoning it matches dense with about 40% of the reads. Several directions remain open. On a quantized KV cache (Liu et al., 2024; Hooper et al., 2024), every page shrinks while the rule reads fewer pages, so the two savings multiply. Under latent attention (DeepSeek-AI et al., 2024), the rule would select pages of the shared latent cache. Esti-mated page masses could tell an offloading system such as ShadowKV (Sun et al., 2025) which pages to keep on the GPU or prefetch. Applied to a block of queries, the rule extends to speculative decoding (Sadhukhan et al., 2025), which verifies several draft tokens at once; applied to learned scores, it would make trained sparse attention (Yuan et al., 2025) adaptive. A device-side plan for FlashInfer and a port to SGLang (Zheng et al., 2024) are engineering work.

# A Design Details 

This appendix complements Section 3. 

Estimator choice. We compare page-mass estimators by the token KL to dense when every layer decodes sparsely (Llama-3.1-8B, 60 LongBench requests). With the exact (oracle) mass, top-p at 0.95 keeps 23.9% of the pages at a KL of 0.00348. An int4 copy of the keys comes close to the oracle (24.1% kept, KL 0.00343) but reads an extra 15.6% of the keys. mvar at 

γ=0 .98 keeps 37.1% at a KL of 0.00441, and at γ=0 .995 keeps 61.7% at 0.00095. Estimators that use only the key mean fail on heads that concentrate attention on a few scattered tokens: one KV head of layer 2 accounts for almost all of their KL, because with the mean alone the mass of such a page is underestimated by a factor of e5–e7, against about e3 with the variance term of Eq. (2). 

Why pages are not sorted. In a prototype that preceded the final module, the coverage rule implemented with a PyTorch sort cost 66 μs per layer at a 6.6k context and erased most of the gain: the whole pipeline was 1.47 × faster than dense attention, against 3.18 × for the attention kernel alone. Fusing selection into one kernel ( Select , Section 3) raised this to 2.56 ×.

Kernel configuration. Estimate runs several thread blocks per row (at least four per SM over the batch), each covering 64 pages, and writes the summary of the current page as soon as a new token fills it, so a decode step needs no separate summary kernel. For batches of at most 64 rows, Select uses 8 warps per thread block instead of 4; the batch size is fixed per CUDA graph, so this choice is fixed as well. Attend uses 4 warps and 3 pipeline stages and processes one 64-token page per loop iteration. We tried and discarded two variants: fusing Merge into Attend (the last thread block of each row merges all partials) makes every row wait for its last-arriving thread block, and programmatic dependent launch between the kernels changed TPOT by +1 .5% , −1.2% and +1 .4% at 8k, 32k and 130k, with no clear benefit. 

# B Correctness Checks 

This appendix expands the correctness paragraph of Section 4. We check three properties. (1) When every page is kept ( γ=1 ), Moira computes dense attention exactly. Its output differs from FA3 by at most one bf16 ulp ( 3.9 × 10 −3), that is, one bf16 rounding step at this magnitude. CUDA-graph replay matches eager execution bit for bit, and in mixed steps the prefill rows are bit-identical to FA3. (2) That difference is comparable to the difference already present in dense attention. In greedy generation of 256 tokens on 12 prompts, Moira at γ=1 and dense produce identical outputs on 4/12 prompts, while dense at two different batch sizes is identical on 5/12. Every first divergence falls on a token whose top-2 logits are only 0–0.25 apart, where rounding error alone can change the choice. (3) The kernels select the right pages. The page lists of Select match a float32 reference implementation of the rule on 64/64 test rows at γ=0 .98 . TPOT is measured end to end with CUDA graphs on eight RULER 128k prompts per model (two batches of four prompts, 200 decode steps, median of five runs per batch). Dense, Moira, FA3 c and FlashInfer c run in vLLM; the last two replace only the attention call of Moira and read the same page lists. FA3 treats each (request, KV head) as a varlen sequence over vLLM’s head-major (HND) cache layout and builds its split metadata in every layer. FlashInfer is planned once per batch shape with every row at full width, and at every step device code writes the real index arrays into the planned buffers. FFD runs in its own runtime (Hugging Face with full CUDA graphs, Llama only), on the same prompts cut to equal length (first 256 and last tokens), because its cache holds one length per batch. Quest: slow because of the kernel, page-hungry because of the rule. Quest differs from Moira in two places. The first is the kernel: Quest’s rule selects pages per query head and attends with FlashInfer’s paged kernel (CUDA-core kernel in both arms below). On our page sets at 128k, FlashInfer with one list per query head takes 8.30 ms, against 4.89 ms with one list per KV head, before a 2.16 ms host plan. The kernel of Moira removes this cost for any rule, Quest’s bound included (Section 3.5). The second is the rule. On Llama-3.1-8B, γ=0 .98 matches the accuracy of Quest-36k with only 19.6% of the pages, while Quest’s budget corresponds to about 27.4%. On our kernel these two read levels cost 4.73 and 6.43 ms per step, so the rule alone makes attention 1.36 × faster at equal accuracy. With both differences combined, Quest’s own path takes 22.0 ms, 1.4 × dense attention (Table 1). 

FFD: slow because it scans every key. FFD keeps 12.5% (Llama-3.1-8B) and 21.2% (Qwen3-4B) of the 128-token blocks on RULER, yet its fused kernel is only 1.20 × and 1.08 × faster than dense, and on Llama-3.1-8B its measured TPOT equals dense (18.8 vs. 19.0 ms). The reason is that at every step it scans the 2-bit copy of all keys, so its cost barely falls with the number of kept blocks: even at 2% kept it is only 1.36 × faster, and at 8k ×32 it is slower than dense at every kept fraction (Figure 7). Across batch shapes, FFD runs at 0.82–1.25 × the speed of FA3, whereas the attention path of Moira is 

1.70–4.19 × faster than FA3 (Table 4). 

Twilight: slow because it selects per query head. Twilight’s selection chain takes 12.71 ms per step, because its kernels treat GQA as 32 independent heads (8.72 ms with an 8-head port). Attention adds 2.02 ms, and the host plan takes 6.96 ms outside any CUDA graph. Selection and attention alone take 14.73 ms, close to dense attention (15.59 ms); with the host plan, 21.69 ms, against 4.73 ms for Moira at γ=0 .98 .
