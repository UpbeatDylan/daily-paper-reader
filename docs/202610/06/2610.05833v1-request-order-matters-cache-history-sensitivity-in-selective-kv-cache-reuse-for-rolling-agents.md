## 摘要
长期运行的智能体反复调用 LLM，同时保留其大部分文档窗口、逐出旧文档并追加新文档。这些滚动更新破坏了精确前缀缓存，并促使采用带选择性重计算的非前缀 KV 缓存复用。我们表明，带选择性重计算的持久 KV 缓存复用可能具有历史依赖性：在我们的滚动智能体工作负载中，同一未更改的提示可能因此前处理的请求不同而产生不同答案。在匹配的 5% 重计算预算下，文档对齐的重计算将跨请求顺序的答案变化从 CacheBlend 的 token top-k 策略的 69.0% 降低到 26.1%。当每个提示在不同前序请求序列之后被评估时，文档对齐的重计算相比 token top-k 将相对于完整预填充的保真度提高 34.5–52.5 个百分点，而两种策略均实现了约 5.7 倍的中位 TTFT 加速。我们的消融研究表明，在我们的滚动智能体工作负载中，连续性是与稳健选择性重计算相关的主要因素。

## Abstract
Long-running agents repeatedly call an LLM while retaining most of their document window, evicting old documents, and appending new ones. These rolling updates break exact prefix caching and motivate non-prefix KV-cache reuse with selective recomputation. We show that persistent KV-cache reuse with selective recomputation can be history-dependent: in our rolling-agent workload, an unchanged prompt can produce different answers depending on the requests processed before it. At a matched 5% recomputation budget, document-aligned recomputation reduces answer variation across request orders from 69.0% with CacheBlend's token top-$k$ policy to 26.1%. When each prompt is evaluated after a different sequence of preceding requests, document-aligned recomputation improves fidelity to full prefill by 34.5-52.5 percentage points over token top-$k$, while both policies achieve approximately 5.7$\times$ median TTFT speedup. Our ablation study shows that, in our rolling-agent workload, contiguity is the main factor associated with robust selective recomputation.

## 1. 核心问题与整体含义

- **研究动机**：长时间运行的智能体（rolling agents）会反复调用 LLM，并持续维护一个滚动文档窗口：保留大部分旧文档、淘汰最旧文档、追加新文档。这种更新会破坏精确前缀缓存，因为保留文档的位置和前置上下文发生变化，无法直接复用原有 KV 状态。
- **技术背景**：为降低 prefill 延迟，系统采用非前缀 KV-cache 复用与选择性重计算。CacheBlend/LMCache 的 token top-k 策略会加载可复用 token 的缓存 KV，并按当前 key 与缓存 key 的偏差，选择少量 token 重算。
- **核心问题**：当 KV 缓存状态跨请求持久存在时，选择性重算可能具有**历史依赖性**。同一未变提示，可能因此前处理的请求顺序不同，遇到不同缓存历史，从而产生不同答案。
- **整体含义**：选择性 KV-cache 复用不应只在“干净缓存 + 孤立请求”下评估，而应放在持久缓存生命周期的闭环服务场景中评估。请求顺序、调度交错和缓存历史本身会成为影响输出保真度与稳定性的变量。

## 2. 方法论

- **核心思想**：在固定重算预算下，比较“散点式选择高偏差 token”与“连续区间式重算”的效果。论文主张，重算少量连续区域可能比重算大量分散的高偏差 token 更稳健。
- **基础偏差指标**：对每个可复用 token \(i\)，计算当前 key 与缓存 key 的 L2 偏差：
  \[
  d_i = \|K_i^{current} - K_i^{cached}\|_2^2
  \]
  偏差越大，表示该 token 的缓存状态与当前上下文差异越大。
- **预算规则**：对 \(N\) 个可复用 token 和重算比例 \(r\)，选择：
  \[
  k = \max(1, \lfloor rN \rfloor)
  \]
  个 token 进行重算。选中位置使用当前提示下的 KV，未选中位置保留加载的缓存 KV。
- **CacheBlend token top-k**：默认策略选择 \(d_i\) 最大的 \(k\) 个 token。其问题是 token 独立排序，重算区域可能分散在数百个不连续片段中。
- **Span-level 选择性重算**：候选连续区间 \(S_j\) 的平均偏差为：
  \[
  \rho_j = \frac{1}{|S_j|}\sum_{i \in S_j} d_i
  \]
  通过平均偏差而非总偏差排序，避免长区间仅因长度大而占优。
- **四种 span 策略**：
  - **Single-window**：选择总偏差最大的连续 \(k\)-token 窗口。
  - **Fixed-chunk**：将可复用提示划分为等长 span，允许跨文档边界，按平均偏差优先选择。
  - **Random-document**：使用文档边界定义 span，但随机排序，忽略偏差。
  - **Document-aligned**：使用文档边界定义 span，按平均偏差 \(\rho_j\) 排序，优先选完整 span；若预算有剩余，则从最高排名剩余 span 中选择总偏差最大的连续窗口，最终恰好选 \(k\) 个 token。
- **算法流程文字说明**：
  1. 加载可复用 chunk 的缓存 KV；
  2. 在 selection layer 计算每个可复用 token 的当前-缓存 key 偏差；
  3. 根据策略在固定预算 \(k\) 下选择重算位置；
  4. 选中位置用当前提示重新计算 KV，未选中位置保留缓存 KV；
  5. 后续层沿用同一组选中位置，不再重新排序。
- **研究对比**：主实验比较 token top-k 与 document-aligned；消融中引入 single-window、fixed-chunk、random-document，以分离“连续性”“文档边界”“偏差排序”的贡献。

## 3. 实验设计

- **模型与系统**：

  - 解码：贪心解码，temperature=0，固定随机种子；

  - 为测量 LMCache 的非前缀复用路径，禁用 vLLM prefix cache。

  - 数据包含 8,995 条真实记录，覆盖 15 只美国股票；

  - 792 条 FNSPID 新闻标题；
  - 688 条 SEC EDGAR 文件标题；

  - 每个 LLM 调用前，窗口淘汰 1 个旧文档，保留 83 个文档，追加 1 个新文档；

- **Benchmark 形式**：
  - 同一批请求以五种顺序处理：chronological、三个 fixed-random、reversed；
  - 每个请求提示不变，只改变进入服务系统的顺序，从而改变持久缓存历史；
  - 每种“策略 × 顺序”组合都从空 LMCache 开始，跨请求保留缓存，且不同运行不共享状态。
- **对比方法**：
  - Full prefill；
  - Token top-k，5% 重算；
  - Document-aligned，5% 重算；
  - 消融：single-window、fixed-chunk、random-document、document-aligned、token top-k。
- **评价指标**：
  - **Answer variation**：在五种请求顺序的所有 10 个两两比较中，答案不一致的比例；
  - **Fidelity**：与 full prefill 答案完全一致的比例；
  - **TTFT**：请求级中位数、P95 及相对 full prefill 的加速；
  - **Selection fragmentation**：选中重算区域的中位段数；
  - **Captured deviation**：选中 token 携带的总偏差占比。
- **控制实验**：
  - 500 请求的 cache-reset 控制：每个请求前重置缓存；
  - 独立重复 chronological 顺序，验证答案可精确复现；
  - 请求逐个发出，排除 batch composition 影响。
