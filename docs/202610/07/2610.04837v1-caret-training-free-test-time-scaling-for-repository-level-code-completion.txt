Abstract —Retrieval-augmented generation (RAG) dominates repository-level code completion: it retrieves cross-file context (R), then decodes one greedy completion (G). Existing work mainly focuses on retrieval and stops there. We argue both stages can be improved together, with generation in particular gaining from test-time scaling. We present C ARET , a training-free method. For R, C ARET routes among retrieval contexts using the agreement among its own samples, cascading to an alternative context when the samples scatter. For G, it samples candidates over a cached prompt prefix, so the long retrieved context is encoded once rather than once per sample. It then selects the final completion by reverse-context likelihood: a correct completion makes the code after the cursor more probable, so the same model grades its own candidates by reading ahead. Across CrossCodeEval, RepoEval-Line, and RepoEval-API with six code models (1.1B to 7B, four families), C ARET improves exact match in all 18 combinations by 10.8 points on average over greedy decoding and 5.3 over self-consistency@10. Token-level compute stays near 1.45 times one generation (measured wall-clock 1.3– 2.9 times, growing with generator size). Improving retrieval and generation together yields more accurate code than improving retrieval alone, at a budget that stays close to a single pass. 

Index Terms —code completion, retrieval-augmented genera-tion, test-time scaling, large language models 

I. I NTRODUCTION 

Repository-level code completion asks a language model to complete code in a file using knowledge of the whole repos-itory; we study its most frequent granularity, the next line or API call at the cursor. The correct answer often depends on identifiers, signatures, and call patterns defined elsewhere in the project [1–3]. A model that sees only the current file misses these cross-file dependencies. Missing context, rather than limited model capacity, is the dominant failure mode [1]. The central problem is therefore supplying the right evidence from the repository before the model decodes. Current approaches to repository-level code completion mainly concentrate on what to retrieve. Retrieval-augmented generation (RAG) assembles cross-file evidence into the prompt through iterative lexical retrieval [2], dataflow analy-sis [4], code graphs [5], learned retrievers [6], and multi-source fusion [7, 8], then decode once with greedy search. However, 

whole-pipeline optimization from retrieval to generation remains underexplored , especially the generation stage. This motivation is further supported by our motivating study in Section II-E. To address this, we propose C ARET , which improves both stages of the pipeline under one inference budget. Figure 1 sketches the pass. For retrieval and routing (R) , C ARET 

reads the agreement among its own samples (the fraction matching the modal candidate) and re-samples from an al-ternative retrieval context only when agreement is low. For 

generation (G) , it scales test-time compute by sampling over a cached prompt prefix, which encodes the long retrieved context once rather than once per sample, and reranks the distinct candidates by their reverse-context likelihood blended with vote frequency, skipping scoring when agreement is already high. The same small model performs every step, with no second model, training, or labels. The central problem is to raise accuracy while keeping the cost increase within a reasonable range. Sampling many candidates and scoring them is the standard way to raise accu-racy [9, 10], but each extra sample re-encodes the prompt and verifier-based selection adds a scoring pass per candidate [11– 13]; on the long repository prompts here, naive sampling multiplies an already heavy cost, and reported multi-pass methods reach up to 1.9 times one generation (Section II). CARET ’s cached prefix and skip-and-deduplicate rules hold this increase to a small factor, and Section II shows that test-time selection already helps without any retrieval, at little extra cost. Thorough evaluation shows that C ARET improves all 18 model–benchmark combinations over greedy decoding and over self-consistency@10 [9], by +10 .8 and +5 .3 EM on aver-age, the best accuracy among the reproduced baselines under a common prompting and budget protocol. Our strongest gener-ator, DeepSeek-Coder-6.7B, reaches 47.74 EM on RepoEval-API and 43.88 on RepoEval-Line with C ARET , above every retrieval baseline by +7 .6 and +9 .4 EM. A. Repository-Level Code Completion 

Repository-level completion is defined by where the evidence comes from (other files of the repository), not by how much is completed. We study its line and API-invocation granu-larity [1, 2]: the completion an IDE offers inline at every pause, where the request rate is highest and the latency budget tightest [14], and where a single reference line is a reasonable proxy for correctness because a statement admits far fewer equivalent forms than a function body. Function-level completion is a different regime, with longer outputs, weaker agreement, and execution-based metrics; we return to it in §VI. A task instance is a tuple (Xl, X r , R, y ). The left context Xl

precedes the completion point in the current file, the right context Xr follows it, R is the set of remaining repository files, and y is the reference completion. A generator M, a pretrained code language model [15–17], produces a candidate 

ˆy. Correct completions often hinge on identifiers, signatures, and usage patterns defined in other files, so prompting with the current file alone performs poorly [1, 3]. The standard remedy is retrieval augmentation: a retriever maps (Xl, R) to a token-budgeted base context C, and the completion is decoded as 

ˆy ∼ M (· | C ⊕ Xl), where ⊕ denotes prompt concatenation. Three public benchmarks instantiate this task, each instance shipping all four tuple components. CrossCodeEval (Python) contains 2,124 line-completion tasks constructed so the target needs cross-file information [1]. RepoEval-Line contains 1,600 line-completion tasks, and RepoEval-API 687 API-invocation tasks over 8 repositories [2, 18]. The primary metric is exact match (EM) of the first non-comment generated line against the reference; edit similarity (ES) [19] is secondary. One property of the setting recurs below. The right context 

Xr is available at completion time: mid-file completion is the common case in these benchmarks and in fill-in-the-middle training [20], and every instance ships Xr . Under the causal prompting we adopt for all six generators, Xr never enters the prompt: an available but unused signal. 

B. Retrieval-Augmented Generation 

Repository-level retrieval-augmented generation (RAG) im-proves what goes into the base context C. RepoCoder retrieves iteratively, feeding a draft completion back into the next retrieval round [2]. DraCo follows dataflow to pull in the definitions a completion will use [4], and GraphCoder retrieves over a code context graph [5]. RLCoder trains a retriever with reinforcement learning [6], while RLPG and CoCoMIC learn prompt-proposal or import structure [21, 22]. Fusion methods such as RepoFuse and CodeRAG merge several sources into one prompt [7, 8]. The cost profile is uniform across this line: each method spends its entire budget before decoding, assembles one C, commits to it for every task, and decodes once. Even RepoCoder’s iterations only refine retrieval, and fusion still merges its sources into a single prompt. A second line decides whether to retrieve at all. Repoformer trains a gate that skips retrieval when the model is already con-fident [18], and Self-RAG, FLARE, SKR, and Adaptive-RAG learn similar policies for when or how much to retrieve [23– 26]. These trained gates decide retrieval timing. We instead decide which retrieved context to trust, training-free and post hoc: the decision uses the samples a context produces, not a learned predictor of the context. 

C. Test-Time Scaling 

Test-time scaling (TTS) spends budget after the prompt is fixed: sample N candidates, then select one. Self-consistency draws several samples and selects by majority voting [9]; we refer to this baseline as self-consistency@10. Repeated sampling scales coverage with N [10, 27]. For code, can-didates are selected through generated tests, execution-based clustering, or minimum-Bayes-risk decoding [28–30], through trained verifiers [11, 12], or through Coder-Reviewer reverse reranking that scores a candidate by how well it regenerates the prompt [13]. These selectors are domain-general and blind to the retrieval context. They are also expensive: sampling costs about N times one generation, and a reranker adds a further pass per candidate. We are aware of no instantiation for repository-level completion that exploits the retrieval context during selection. TTS selection does not, however, depend on retrieval to work. We tested this on zero-shot prompts with no retrieved context: the prompt holds only the in-file left context, and the selector grades candidates against the in-file right context 

Xr . Sampling plus selection beats both greedy decoding and majority voting. On RepoEval-Line EM rises from 27.62 (greedy) to 32.25 (selection), on RepoEval-API from 25.33 to 27.66, against an oracle@10 of 40.31 and 34.35. The API case isolates the gain: majority voting there (24.60) falls below 

greedy, yet the reverse-context verification (RCV) selector (Section III) lifts the same pool above greedy. The improve-ment comes from the selector rather than from sampling luck or vote count. What C ARET adds to this line is not sampling or reranking as such but three specific rules and their combination: agree-ment among a model’s own samples is used as a routing signal across retrieval contexts rather than only as a selection signal; the code after the cursor, which every completion instance ships but causal prompting ignores, is turned into a training-free verifier by scoring the reverse likelihood with the same small model; and a fast path plus distinct-only scoring keep the whole pipeline near one generation’s token budget. Self-consistency [9] selects but does not route; best-of-N with a trained verifier [11] and forward-likelihood reranking rank candidates by how plausible they are, not by whether the file still reads coherently after them; coding agents can look up definitions and revise, but at a per-request latency far from the interactive budget of inline completion. The trade-off is concrete: accuracy rises with modest extra cost as candidates are sampled and selected, while spending more does not always help. RepoCoder’s iterative retrieval sits near 2× the budget without a matching gain, and exhaustive scoring of every sample adds little over scoring distinct candidates only. The open question is whether RAG and TTS can be combined so that the accuracy gains of TTS survive at near single-pass cost. 

D. Cost Model 

To compare methods that spend different budgets, we report 

relative cost : the total LLM forward compute per task (prompt encoding, decoding, and scoring tokens) divided by that of one greedy retrieval-augmented generation, written as a multiplier. Retrieval is excluded; every retrieval-augmented method pays it once per task, independent of N .The intuition is simple. The expensive part of a retrieval-augmented generation is encoding the long retrieved prompt. Prefix caching encodes it once and reuses it, so the N short continuations we sample add only a little on top of one greedy generation rather than N times its cost. Scoring is cheaper still: each reverse-context scoring pass is a single forward pass over a truncated context, a small fraction of one generation. A sample-then-select method therefore decomposes into a cheap sampling term and an even cheaper scoring term. Relative cost is the average number of base contexts sampled per task times 

csamp , the cost of one N -sample batch from a context, plus the average number of distinct candidates scored times crcv , the cost of one reverse-context scoring pass. Both unit costs are small in practice. Drawing a full N -sample batch costs only about 1.1 times one greedy generation, because the long retrieved prefix is encoded once and the N

short continuations ( ≤64 tokens each) decode from the cached KV: csamp ≈ 1.1 rather than N ×. One reverse-context scoring pass, a single teacher-forced forward pass over a truncated context, costs only about 0.054 of a generation: crcv ≈ 0.054 .Section III instantiates this accounting for C ARET , and Sec-tion V reports measured token-level and wall-clock multipliers. The model assumes the shared prefix is cached across the N

samples; without caching, each sample re-encodes the prompt and the realized cost is higher (Section VI). This accounting also sets the bar the method must clear. Across the self-consistency and reranking baselines above, reported test-time overhead reaches up to 1.9× one generation: drawing many samples and scoring every one is what makes TTS expensive. Keeping the gain while staying near single-pass cost is the design target of C ARET .

Observation 3 (G): Majority voting is a weak strategy, a new selector is required. Let the agreement a of a pool be the fraction of its N samples equal to the modal candidate after normalization. Agreement predicts correctness sharply (Fig. 2(c)): when a ≥ 0.9 the modal candidate is correct on 72–89% of tasks, but when a ≤ 0.2 on only 2–8%. One free statistic thus diagnoses both a failing context (very low a) and a settled task (very high a). Calibration does not make the modal candidate a good answer, though. Vote frequency alone recovers little of the headroom and even falls below greedy on CrossCodeEval, because several distinct yet plausible candidates split the vote and the most common form is often wrong [9, 13, 28]. Selection needs evidence stronger than the count: the still-unused right context is a free verifier, since a correct completion should make the following code more probable. Together, these three observations motivate CARET ’s pipeline (Section III): a router that picks a context per task, sampling that surfaces the answer, and a selector that reads the right context to choose it. III. M ETHODOLOGY 

A. Overview 

CARET runs one training-free pass over the two stages of the pipeline, laid out left to right in Fig. 3, with small code models only and no training or labels: the generator samples the candidates, and a fixed 1.3B scorer (the generator itself in our primary setting) verifies them. In retrieval and routing (R) , given the repository and the cursor, C ARET assembles two base contexts from complementary families and treats one as primary; it samples N candidates from the primary, reads their agreement, and consults the alternative only when agreement is low, routing to whichever pool the samples agree on more (Fig. 3(a), Section III-B). In generation (G) , each consulted context is sampled in one cache-aware batch, the long prefix encoded once, the short continuations decoded from the cached state, and on the routed pool C ARET emits the modal candidate when agreement is high enough, otherwise scoring the distinct candidates by having the same model read the code after the cursor and blending that reverse-context score with vote frequency (Fig. 3(b), Section III-C). The dashed paths in Fig. 3 are cost-saving shortcuts: consult the alternative only on disagreement, skip scoring at high agreement, and score only distinct candidates over truncated contexts. All hyperparameters are global across benchmarks and models (Section VI); the only per-benchmark choice is which context is primary. Cost follows the model of Sec-tion II-D. C ARET uses one structural and one lexical context, kept separate so the router can choose between them per task. Identifier-definition re-trieval runs an exact-match search ( grep ) over the repository for definitions and usages of cursor-adjacent identifiers the dataflow analysis leaves unresolved, including those in the right context when available. Call-site frequency hints annotate retrieved definitions with how often each API is invoked across the repository, surfacing representative call patterns. The recipe is base-agnostic: for API-invocation tasks a variant layers the same signals over a BM25 base, yielding a single fused-lexical context, distinct from the Concat baseline that concatenates the two families (Section IV). The lexical context is BM25 [2] sliding-window retrieval in the style of RepoCoder’s retrieval-and-generation baseline: repository files are split into overlapping fixed-size windows, the code before the cursor is the query, and the top windows go into the prompt. As Observation 1 found, the structural and lexical families solve largely disjoint task sets: each solves cases the other misses, and a per-task oracle over the two gains up to +6 .0 EM over either alone. Merging them into one prompt [7, 8] averages away the very per-task signal routing exploits, so C ARET keeps them separate and chooses between them per task. 

Agreement-gated cascade routing. CARET draws N samples from the primary base context and canonicalizes each to its first non-comment line. Over the resulting distinct candidates 

D = {c1, . . . , c m}, the vote frequency vi of candidate ci

is its share of the N samples, and the pool’s agreement is the modal share a = max i vi ∈ [1 /N, 1] . When primary agreement is low, more samples from the same context rarely help: at a ≤ 0.2 the modal candidate is almost never correct (Observation 3), typically because the needed symbol or usage is absent from the prompt. C ARET therefore spends the next unit of budget on a different context. If the primary pool’s agreement a1 ≥ τ , the cascade commits to the primary. Otherwise it draws N samples from the alternative base context and routes to whichever pool agrees more. The comparison is symmetric rather than a blind fallback: the primary still wins if the alternative scatters more. The gate τ keeps the alternative cheap, since the cascade falls through on a small fraction of tasks, so the expected number of sampled contexts per task stays close to one (Section II-D). The cascade is asymmetric, so the primary context is CARET ’s single per-benchmark choice. The choice is auto-matic: the order maximizing EM on a held-out 10% de-velopment split recovers the optimal order in every seed– benchmark combination we tried. The threshold τ doubles as insurance against a mischosen primary: a higher τ consults the alternative more often and recovers most of the lost accuracy (Section VI). Unlike adaptive-retrieval methods that 

train a when-to-retrieve policy [18, 23, 26], cascade routing is training-free: it reads a posterior signal of the generator to decide which context to trust. The cascade extends to an ordered list of K contexts by advancing while agreement stays below τ ; we discuss K in Section VI. 

C. Generation with RCV Selector 

Cache-aware sampling. Sampling is the step Observation 2 calls for: the pools already hold the answer far more often than greedy recovers, so the budget improves accuracy only if those samples are collected cheaply. Drawing N candidates is how CARET spends test-time compute (Section II); the difficulty is spending it without paying N × the cost of one generation. CARET samples each consulted context in one batch under causal prompting on C ⊕ Xl with nucleus sampling [31] and a short token cap (settings in Section IV). The long retrieved prefix is encoded once and shared; the N short continuations decode from the cached state, so a full batch costs a small constant over one greedy generation rather than 

N × (Section II-D). These same N samples yield both the routing signal above and the candidate pool below. 

Reverse-context verification (RCV) selector. Observation 3 shapes selection: agreement is a calibrated confidence signal, but vote frequency alone is a weak selector when distinct plausible candidates split the vote. C ARET ’s RCV selector reads the code after the cursor to break the ties, in three steps. 

Fast path. If the routed pool’s agreement satisfies a ≥ θ,CARET emits the modal candidate without scoring. High-agreement modal candidates are overwhelmingly correct (Ob-servation 3), so verification compute is better spent on harder tasks. 

Reverse-context likelihood. For the remaining tasks, vote frequency is too coarse: the pool holds several distinct yet plausible candidates with near-tied votes. C ARET breaks the ties by reading ahead. A. Research Questions 

We ask whether improving both stages of the pipeline, retrieval and routing (R) and generation (G) covering sampling and selection, raises accuracy at near single-pass cost. We answer three questions in Section V, each with the metric named below. 

RQ1: Does C ARET outperform state-of-the-art single-pass and test-time-scaling baselines, and does the gain transfer across the six generators? We answer it by exact match (EM), with edit similarity secondary (Section IV-C). 

RQ2: How does the cost of C ARET compare to state-of-the-art methods? We answer it by relative, time, and resource cost (Section IV-C). 

RQ3: How much do agreement-gated routing, cache-aware sampling, and the reverse-context verification (RCV) selec-tor contribute? We answer it by ablating each component on the reference generator. 

B. Benchmarks 

We evaluated CARET on the three benchmarks of Sec-tion II-A: CrossCodeEval (Python; 2,124 line completions) [1], RepoEval-Line (1,600 line completions), and RepoEval-API (687 API-invocation completions over 8 repositories) [2]. We used the official CrossCodeEval data and scripts, and Repoformer’s released splits of RepoEval [18]. 

C. Metrics 

Our primary metric is exact match (EM, %): the fraction of tasks whose first non-comment generated line exactly matches the ground-truth line [19]; edit similarity (ES, character-level Levenshtein [19]) is secondary. We confirm the significance of EM gains with per-benchmark McNemar tests on paired per-task EM against self-consistency@10 and paired-bootstrap 95% confidence intervals of ∆EM (10,000 resamples) [32]. For cost (RQ2) we report relative cost (total LLM forward compute per task in multiples of one greedy generation, Section II-D), time cost (wall-clock), and resource cost (peak GPU memory). 

D. Baselines 

We compared against seven single-pass configurations (zero-shot in-file, five retrieval-augmented methods, and one of our own) and one test-time-scaling method: (1) Zero-shot in-file: greedy completion from in-file context alone; (2) BM25: single-round sparse chunk retrieval (RepoCoder’s RG-1 [2]), also our lexical context; (3) RepoCoder: iterative retrieval– generation, published two-iteration setting [2]; (4) DraCo: dataflow-guided cross-file retrieval [4], underlying the dataflow component of our fused context; (5) GraphCoder: retrieval over code context graphs [5]; (6) CodeRAG: multi-path re-trieval fusion [8]; (7) Concatenated contexts (Concat): both context families in one prompt, i.e., the fused context plus the lexical context’s BM25 windows. This natural “use both contexts at once” alternative to routing is the greedy reference point for our headline gains. (8) Self-consistency@10: major-ity vote over N =10 samples from the concatenated-context configuration [9], the strongest test-time-scaling baseline at our sampling budget. For fair comparisons, we reproduced all baselines under identical conditions and the same input prompt-token budget, with identical decoding limits and post-processing. Numbers can therefore differ from the original papers (e.g., our Re-poCoder reproduction differs from RLCoder’s [6]); all com-parisons here are internal and mutually consistent (Section VI). GraphCoder’s released pipeline and graph database target its own RepoEval-Updated variant, built from different reposito-ries and task constructions. We reproduced its code-context-graph retrieval on CrossCodeEval, where it trails stronger baselines by over 16 EM, but did not port its graph database to our RepoEval splits, so GraphCoder appears only on Cross-CodeEval. 

E. Environment Hardware. All experiments ran on one machine: dual Intel Xeon Silver 4509Y CPUs (32 logical cores), 503 GB system RAM, and a single NVIDIA H100 NVL GPU with 96 GB memory (driver 590.48). Models ran under HuggingFace Transformers in bfloat16 with prefix caching. Time cost (wall-clock) and resource cost (peak GPU memory) in Section V-B are measured on this machine; relative-cost multipliers are computed from per-task counts of consulted base contexts and scored distinct candidates under the cost model of Sec-tion II-D. 

LLMs. We used six opensource LLMs from four families (1.1B–7B): DeepSeek-Coder-1.3B-base (primary) and DeepSeek-Coder-6.7B-base [16], SantaCoder-1.1B [33], StarCoder2-3B [34], StarCoder-7B [35], and CodeLlama-7B [36]. All are prompted left-to-right without fill-in-the-middle [20], so all methods consume identical prompts. SantaCoder-1.1B and StarCoder-7B, with 2048- and 8192-token context windows, are decoded at batch 1 with prompts truncated to their position limit. 

Hyperparameters. One global configuration serves all benchmarks and all six models, with no per-benchmark or per-model tuning. Sampling draws ten candidates ( N =10 )per consulted base context at temperature 0.8 and nucleus 

p=0 .95 [31], capped at 64 new tokens, keeping the first non-comment line; greedy baselines share the prompts and the length limit. A single routing threshold, a single selection-skip threshold, and fixed blend weights complete the recipe. The only per-benchmark decision is which member of each context pair the cascade consults first: CrossCodeEval starts from the fused context, RepoEval-Line from the lexical context, RepoEval-API from the fused-lexical context, with the other family as the alternative (the pure DraCo dataflow context for RepoEval-API). We picked this one bit on a held-out 10% development split of at least 30 tasks; across three random seeds per benchmark, all nine selections matched the full-benchmark optimum, so the split informs only this one bit. We report full task sets for comparability. The hyperparam-eter values appear in Section VI, and the routing sensitivity analysis in Section V-C. 

Selector. The RCV selector always uses DeepSeek-Coder-1.3B, even for larger generators, so C ARET stays training-free and keeps the selection cost at a reasonable level. Full infer-ence configurations, prompt budgets, and retrieval parameters are in the artifact. V. E VALUATION 

Improving both stages, retrieval and routing (R) and generation (G, which spans sampling and selection), raises repository-level completion accuracy at a small, bounded inference budget, and the gain holds across generators. C ARET pairs agreement-gated cascade routing on the retrieval side and cache-aware sampling on the generation side with the reverse-context verification (RCV) selector. We answer the three research questions of Section IV-A in turn: accuracy and gen-eralization (Section V-A), cost (Section V-B), and component attribution (Section V-C). Unless noted, the reference genera-tor is DeepSeek-Coder-1.3B [16] and the metric is exact match (EM; Section IV-C). The same DeepSeek-Coder-1.3B selector serves every generator without retraining. All baselines are self-reproduced under identical prompting, context budgets, and evaluation (Section IV). 

A. RQ1: Does CARET outperform state-of-the-art single-pass and test-time-scaling baselines, and does the gain transfer across the six generators? 

CARET is the best non-oracle method in every column of Table I: it improves all 18 model–benchmark combinations over greedy decoding and self-consistency@10 [9]. On all six generators it tops every retrieval baseline (BM25, RepoCoder, CodeRAG, DraCo, and GraphCoder) in every benchmark. The six generators span four model families and 1.1B–7B parameters [16, 33–36], yet every run uses the same global hyperparameters ( N =10 , τ =0 .2, θ=0 .8, fixed blend weights) and one fixed DeepSeek-Coder-1.3B selector. 1.56 × on DeepSeek-Coder-1.3B and SantaCoder) but costs

Exhaustive scoring adds no accuracy the gated ∼1.45 × pipeline does not already reach. VI. T HREATS TO VALIDITY AND DISCUSSION 

The evaluation makes broad claims from one implementation and a single primary metric, so we set out its limits before drawing conclusions. We organize them as construct, internal, and external validity, then discuss the reasoning behind the global recipe. Two properties bound most of the risk: every method runs under the same prompts, budget, and decoding, and C ARET exposes no tuned knob beyond a single per-benchmark context choice, so the gains are hard to attribute to a selective harness or to hyperparameter fitting. 

A. Threats to Validity 

Construct validity. Exact match and edit similarity [19] measure surface agreement with a single reference rather than functional correctness; line and API-invocation granularity mitigates this, since a statement admits a narrow canonical form unlike function bodies [1, 2], and all methods share the same first-line normalization. The residual risk that EM gains may not map to practical benefit [14] is shared by every compared method. The relative-cost multiplier is itself a construct: it counts forward tokens and assumes prefix caching across the N samples; without caching, overhead is higher. The ∼1.45 × token multiplier is model-independent, but the realized wall-clock is not (Section V-B): it falls below the multiplier on memory-bound small generators and rises above it ( 1.9–2.9×) on compute-bound 7B ones, so we report both and release per-task counts to re-derive cost under any accounting. 

Internal validity. Reproduced numbers differ from published ones (our RepoCoder differs from RLCoder’s [6] through different data processing and prompts), so we compare only within our pipeline, with identical prompt budget, decoding, and scoring for every method. C ARET ’s global hyperparam-eters are fixed once for every model and benchmark; only the primary base context is per-benchmark, chosen on a 10% development split that picked the correct primary in nine of nine seed–benchmark combinations, and raising τ recovers most of a mischoice (Section V-C). Benchmark repositories may overlap pretraining data, but all methods decode from the same frozen models, so memorization could inflate absolute scores, not deltas. We report one sampling run; task-set sizes (2,124/1,600/687) and paired tests [32] mitigate a lucky run: against the primary-context self-consistency baseline, McNe-mar rejects equal accuracy and 95% paired-bootstrap EM-gain intervals exclude zero on all three benchmarks (Section V-A). 

External validity. Our main study covers Python. A sanity check on CrossCodeEval’s Java split [1] (2,139 line tasks, BM25 context, same hyperparameters) supports transfer of selection: sampling plus selection lifts the 1.3B reference from 16.27 EM (greedy) and 16.74 (self-consistency@10) to 19.17. Two qualifications hold: the scorer needed a 1,000-character left-context tail on Java, whereas Python tolerates dropping it entirely (Section V-C); and the fused context’s dataflow component is Python-specific, so routing was not exercised and other languages need their own dataflow extractors. Gran-ularity is a second limit: we studied line and API-invocation completion, while function bodies change both candidate diversity and metric validity. Generators span 1.1B–7B base models from four families; larger or instruction-tuned models may sample differently, though gains in all 18 combinations suggest the mechanisms are not model-specific. The selector assumes code after the completion point, the common case in these benchmarks, in fill-in-the-middle training [20], and in prior work [18]. It degrades gracefully as that context shrinks: a 32-token window costs 1.02 EM on RepoEval-API and 1.37 on CrossCodeEval and helps RepoEval-Line (Fig. 4). With no right context, selection falls back to vote frequency on the routed pool (33.99 →31.83 / 41.75 →34.94 / 43.52 →37.26 EM): above greedy on RepoEval-Line and API, below on CrossCodeEval, and below full C ARET everywhere, confirming that the right context drives the selection gains. 

B. Discussion 

Global hyperparameters. CARET fixes one recipe and reuses it across every model and benchmark: routing threshold 

τ =0 .2, skip gate θ=0 .8, blend weights 0.75/0.25, sample budget N =10 . The four values were set once on the ref-erence generator (DeepSeek-Coder-1.3B) and frozen before any other model was run, so the other five generators and the closed models are held out with respect to them. The surface is flat: sweeping θ ∈ { 0.6, . . . , 1.0} and the RCV weight w ∈ { 0.5, . . . , 1.0} offline on the stored candidate pools of the five non-reference generators, the default lies within 0.08 EM of the best cell averaged over 15 model– benchmark pairs and at most 0.87 EM below the per-pair optimum; θ mainly moves cost (scored share 0.24–0.29 ×), not accuracy. The only per-benchmark choice is which context is primary, a binary decision made on a 10% development split that picked the same order in all nine seed–benchmark cases; the development tasks are part of the reported test sets, and excluding them changes no comparison (§V-C). For a new repository without labelled completions the default is the fused structural context, which was primary on two of three benchmarks, and the cascade recovers most of the loss of a wrong choice (Fig. 4(a)). 

Completion granularity. CARET is built for line and API-invocation completion, and its mechanisms do not transfer un-changed to function bodies. On RepoEval-Function (455 tasks, DeepSeek-Coder-1.3B, ten samples at the same temperature), 96% of candidate pools contain no repeated candidate (9.85 distinct of 10), so agreement carries no signal for routing or for the fast path, and the sampled pool itself is worse than greedy decoding: the best of ten samples reaches 29.5 edit similarity against 48.4 for one greedy pass, and reverse-context selection over that pool (45.6) does not recover the gap. Function-level test-time scaling needs a different canonicalization (semantic rather than string agreement), a lower sampling temperature, and execution-based selection; we leave it to future work and restrict our claims to the line and API level. 

Number of base contexts and the sample budget. The cascade routes between K=2 base contexts, the sweet spot: a third adds only +0 .1 EM for +0 .2× compute, so the marginal context does not pay for itself. The sample budget 

N trades accuracy for cost steeply at first and then flattens. An N ∈ { 5, 10 , 15 } study shows accuracy saturating around 

N =10 (CrossCodeEval gains +1 .80 EM from N =5 to 10 but only +0 .14 to N =15 ; Fig. 4(c)), so we draw ten samples: enough to surface the answer and calibrate agreement, few enough to keep the budget near one greedy generation. VII. C ONCLUSION AND FUTURE WORK 

We presented C ARET , a training-free framework that improves both stages of retrieval-augmented completion: retrieval and routing (R), and generation (G). It allocates a small inference budget across them: retrieval feeds two base contexts, sam-pling draws candidates that agreement routes between them, and reverse-context likelihood selects the final line. Routing and selection read two signals the completion setting provides for free: agreement among the model’s own samples and the file’s right context. Under one global recipe, C ARET improves all 18 model–benchmark combinations across six generators (1.1B–7B) and three benchmarks by +10 .8 EM on average over greedy decoding and +5 .3 over self-consistency@10, at ∼1.45 × the token-level compute of one generation, with measured wall-clock from 1.3× on small generators to 2.9×

on 7B models. Future work includes other languages, function-level granularity, and learned routing signals. Agreement and reverse-context likelihood are language-agnostic, and only the dataflow context needs per-language tooling. DATA AVAILABILITY
