## 摘要
大型语言模型越来越常被用作语义算子，用于过滤、提取、排序、连接和转换非结构化数据。现有的语义查询处理系统调用以请求为中心的LLM服务系统，这些系统不了解查询计划，从而留下了大量性能优化的机会。本文引入了关系型LLM服务，这是一种抽象，使得LLM服务能够感知语义查询结构，同时保持查询语义和输出准确性。关键机会在于语义算子之间的流水线执行：当中间元组直接从上一个算子流向下一个算子时，它们的KV缓存状态可以被重用，而不是重新计算。我们提出了Kalypso，一个关系型LLM服务系统，它提供了语义查询计划的API，并使用一种自适应、内存感知的调度算法来执行这些计划。Kalypso解决了一个新的在线调度问题，其中流水线算子执行与GPU内存压力管理相结合，以在缓存被驱逐前重用服务引擎中的KV缓存状态。其调度器持续调整内存分配，以平衡上游并行性、下游进度和GPU利用率。我们的评估表明，与使用以请求为中心的LLM服务相比，Kalypso在各种工作负载下将查询完成时间提升了高达4.57倍，证明了查询感知的LLM服务可以显著提高语义查询执行的效率。

## Abstract
Large language models are increasingly used as semantic operators for filtering, extracting, ranking, joining, and transforming unstructured data. Existing semantic query processing systems invoke request-centric LLM serving systems that are unaware of the query plan, leaving substantial performance opportunities unused. This paper introduces relational LLM serving, an abstraction that makes LLM serving aware of semantic query structure while preserving query semantics and output accuracy. The key opportunity is pipelined execution across semantic operators: when intermediate tuples flow directly from one operator to the next, their KV-cache state can be reused instead of recomputed.   We present Kalypso, a relational LLM serving system that exposes an API for semantic query plans and executes them using an adaptive, memory-aware scheduling algorithm. Kalypso addresses a new online scheduling problem in which pipelined operator execution is coupled with GPU memory pressure management to reuse KV-cache state in the serving engine before eviction. Its scheduler continuously adjusts memory allocations to balance upstream parallelism, downstream progress, and GPU utilization. Our evaluation shows that Kalypso improves query completion time over baselines using request-centric LLM serving, with speedups up to 4.57x across diverse workloads, demonstrating that query-aware LLM serving can substantially improve the efficiency of semantic query execution.

# Kalypso: Relational LLM Serving – 论文总结

## 1. 核心问题与整体含义（研究动机和背景）
- **背景**：大语言模型 (LLM) 被广泛用作语义算子（过滤、提取、排序、连接等）来处理非结构化数据。现有语义查询处理系统 (SQPS) 将每个 LLM 调用视为独立请求，由请求中心的 LLM 服务系统（如 vLLM、SGLang）执行，但这些系统不了解查询计划结构，无法利用跨算子的 KV 缓存复用机会。
- **问题**：SQPS 通常采用“算子一次处理全部元组”的物化执行方式，导致中间结果完全物化后 KV 缓存被大量驱逐，下游算子被迫重新计算前缀，造成显著性能损失。GPU 内存压力下，前缀缓存命中率极低，端到端延迟骤升。
- **整体含义**：作者提出**关系型 LLM 服务** (relational LLM serving) 这一新抽象，使 LLM 服务层能够感知语义查询计划，通过流水线执行实现在线 KV 缓存复用，在不改变查询语义和输出精度的前提下大幅提升效率。

## 2. 方法论：核心思想、关键技术细节、算法流程
### 2.1 核心思想
- 让服务引擎感知查询计划，将算子组织为阶段和任务，按流水线方式执行：上游算子的输出元组立即传递给下游算子，共享的前缀 KV 缓存直接复用，避免重复预填充。
- 同时面临**在线调度难题**：必须在有限 GPU 内存下平衡上游并行度（避免饥饿）和下游进展（避免饱和），防止关键前缀被提前驱逐。

### 2.2 系统架构与 API
- **Kalypso 架构**：位于查询客户端（SQPS）和 LLM 引擎（vLLM）之间，包含查询解析器、调度器、KV 缓存管理器、内存估计器、死锁监视器等组件。
- **API**：SQPS 将语义算子实现为 UDF，必须声明三类属性：(1) 是否可流水线 (pipelining)；(2) 是否为谓词 (predicate，可过滤元组)；(3) 是否涉及笛卡尔积 (Cartesian product)。Kalypso 据此将查询计划划分为**阶段**（流水线内连续执行的一组算子）和**任务**（对单个元组执行一个阶段）。

### 2.3 自适应内存感知调度算法 (Algorithm 1)
- **基本流程**：调度器迭代扫描各阶段等待队列，仅在阶段有足够剩余内存预算时启动任务；任务完成后，若未被过滤且非最后阶段，执行笛卡尔积（或索引化笛卡尔积 ICP）生成子任务加入下一阶段队列；维护任务依赖图，仅在所有子任务完成后方释放父任务内存。
- **Rebalance 过程**：每个阶段维护低/高队列阈值（基于当前预算和最小预算计算），当队列长度低于低阈值时视为“饥饿”（下游缺乏输入），将内存从本阶段转移给上游阶段；当高于高阈值时视为“饱和”（等待任务过多），将内存从本阶段转移给最后阶段。初始预算仅最后阶段拥有全部可用内存，其他阶段为最小预算。
- **避免显式固定带来的死锁**：当检测到所有请求等待但无运行请求时，解除所有固定并切换为“虚拟固定”。

### 2.4 内存管理
- **令牌界限估计**：通过在线监控输出与输入令牌比率的 99 百分位数，为每个阶段设定保守的 token 上限。若请求超出则重新调度并扩大上限。
- **显式固定 vs 虚拟固定**：显式固定需要 LLM 引擎支持，通过约 200 行代码修改 vLLM 实现；虚拟固定依赖 LRU 策略和调度控制，性能接近显式固定。

## 3. 实验设计
- **数据集/场景**：四个差异化工作负载：
  - **FEVER**（事实验证）：1,000 条声明，结合 Wikipedia 搜索，单阶段（sem_map + index_search + sem_filter）。
  - **MEDEC**（医疗错误检测与纠正）：1,000 条患者记录，三算子单阶段（sem_filter + sem_map + sem_map）。
  - **BioDEX**（药物反应匹配）：500 篇文章与反应表连接，两阶段（sem_map + ICP + sem_filter）。
  - **ContractNLI**（合同蕴含）：607 份合同与 17 条假设，两阶段（sem_filter + Cartesian 乘积连接 + sem_map）。
- **基准方法**：
  - **Lotus v1.1.4**：支持级联（小模型代理 + Oracle 回退），算子一次处理全部元组。
  - **Palimpzest v1.5.3**：支持查询优化，但部分工作负载不支持（FEVER、BioDEX）。所有系统使用相同 Oracle 模型（Llama-3.3-70B-Instruct）和手动优化查询计划，以隔离服务层效果。
- **实现细节**：Kalypso 和基线均运行在 vLLM v0.13.0rc4 上，启用自动前缀缓存 (APC)，使用贪婪解码，温度 0。每个实验重复 3 次取平均值。

## 4. 资源与算力
- **硬件**：4× NVIDIA RTX Pro 6000 GPU（合计 96 GB HBM），AMD EPYC 9575F CPU（8 核），300 GB RAM。
- **模型与部署**：Llama-3.3-70B-Instruct 使用张量并行 (tensor parallelism) 分布到 4 个 GPU 上。默认 90% GPU 内存分配给 vLLM（约 190.6 GB KV 缓存容量）。论文未提及训练或微调，仅涉及推理服务。

## 5. 实验数量与充分性
- **数量**：共进行了四组主要实验：
  - 端到端延迟对比（所有工作负载 vs Lotus/Palimpzest）
  - 流水线 vs 阻塞执行消融（仅 Kalypso 两种模式）
  - 自适应调度 vs 静态固定比例调度（BioDEX、ContractNLI，分别在 0.9 和 0.6 内存利用率下各 5 个比例）
  - 虚拟固定 vs 显式固定对比
  - Token 界限敏感性（MEDEC 上固定预算扫描，含两个内存设置）
  - 内存压力测试（0.5~0.9 内存利用率共 5 个点）
- **充分性与公平性**：实验覆盖了不同算子组合、不同阶段数、不同元组大小（从数百到数千 token）的场景。Kalypso 与基线保持相同算子实现和 Oracle 模型，仅在服务层不同；对 Lotus 和 Palimpzest 的级联/推理努力做了合理禁用，保证了比较的公平性。消融实验清晰隔离了各机制（流水线、自适应调度、固定、token 估计）的贡献。实验设计较为充分，结论可信。

## 6. 论文的主要结论与发现
- Kalypso 在所有四个工作负载上均优于 Lotus 和 Palimpzest，端到端延迟加速比最高达 **4.57×**（ContractNLI vs Lotus），最低 **1.29×**（BioDEX vs Lotus）。LLM 调用次数与基线相近，说明加速来自执行效率而非减少调用。
- **流水线**是核心收益：相比 Kalypso 自身的阻塞模式，流水线加速比为 1.20×~1.83×。
- **自适应调度**优于任何静态比例分配，能自动适应工作负载特性（如选择性、扇出），避免饥饿或饱和。
- **虚拟固定**性能接近显式固定（差距<5%），可作为无需底层固定支持的普适方案。
- **Token 界限估计**比保守或极端小预算更优，Kalypso 的自动监测方法在两类内存压力下均达到最佳延迟。
- **内存压力鲁棒性**：随 KV 缓存容量从 190 GB 降至 38 GB，Kalypso 的延迟增长远小于基线（例如 MEDEC 增加 9% vs Lotus 44%），证明调度算法能有效保护复用前缀。

## 7. 优点
- **新颖的抽象层面**：首次提出“关系型 LLM 服务”，将查询计划信息引入服务层，与现有 SQPS 和 LLM 引擎兼容。
- **有效的在线调度算法**：同时解决饥饿与饱和动态平衡，算法实现清晰（Algorithm 1），通过队列压力反馈实现自适应。
- **轻量级内存管理**：虚拟固定避免了对底层系统的依赖；Token 界限估计基于在线统计，实用性强。
- **全面的实验设计**：涵盖多种工作负载、消融、压力测试、与成熟系统的对比，且控制变量严谨。
- **明确的开源/可复现性说明**：论文详细说明 vLLM 配置和确定性设置，有助于复现。

## 8. 不足与局限
- **查询计划限制**：仅支持**左深连接树** (left-deep plans)，未考虑更复杂的树形或总线形计划；阻塞算子（如聚合、Top-k）会打断流水线。
- **内存估计误差风险**：基于 99 百分位的监控可能在数据分布剧烈变化时失准，导致重试或并行度下降；论文未讨论极端尾部情况。
- **死锁处理较为初级**：仅通过检测无运行请求后全部解固定来恢复，可能丢失缓存状态，影响性能（实验中仅在压力测试出现，但未量化影响）。
- **未研究多查询并发与查询优化**：Kalypso 专注于单查询加速，没有评估多查询共享缓存或查询优化器自动选择计划的场景（Palimpzest 等已做此类工作）。
- **对代理模型支持有限**：仅在 Lotus 使用级联的工作负载中，Kalypso 未利用代理模型加速（为公平比较保持相同 Oracle 调用），但实际中可通过 API 支持，论文未充分评估。
- **实验偏差风险**：所有基线使用相同 vLLM 版本，但 vLLM 的自动前缀缓存本身有机制差异；且非确定性（greedy 解码仍有波动）可能引入一定偏差。
