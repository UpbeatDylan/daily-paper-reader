## 摘要
将大语言模型（LLM）推理的预填充和解码阶段分离到两组不同的节点上，在当今的LLM服务系统中被广泛采用。然而，这种架构对在租用云实例上进行自托管LLM部署带来了重大挑战，因为在分离节点之间传输巨大的键值（KV）缓存很容易使有限的节点间网络带宽饱和。在本文中，我们提出通过跨两个阶段选择性传输必要的KV缓存条目来缓解网络瓶颈。实现选择性KV缓存传输面临两个挑战，即预填充阶段的准确KV选择，以及解码阶段的高效KV获取。为了应对这些挑战，我们设计了SmartGen，一个KV缓存传输引擎，通过三条数据传输路径实现无缝的分离式LLM推理。具体而言，我们利用1）基于配置文件的主动传输路径，在预填充阶段识别并将必要的KV缓存条目推送到解码节点，2）并行按需传输路径，在解码阶段同时获取远程和本地的KV缓存条目，以及3）推测性传输路径，最终将所有KV缓存传递到解码节点。实验结果表明，与典型的全量KV缓存传输方法相比，SmartGen将到第二个令牌的时间（TTST）最多减少4.3倍，同时提供相当的后续解码性能和准确性。

## Abstract
Disaggregating the prefill and decoding stages of large language model (LLM) inference into two separate sets of nodes is widely adopted in today's LLM serving systems. However, such an architecture poses significant challenges for self-hosted LLM deployments on rented cloud instances, since transferring enormous key-value (KV) caches between disaggregated nodes can easily saturate the limited inter-node network bandwidth. In this paper, we propose to mitigate the network bottleneck by selectively transferring essential KV cache entries across the two stages. There are two challenges to achieve selective KV cache transfer, i.e., accurate KV selection during the prefill stage, and efficient KV fetching during the decoding stage. To address these challenges, we design SmartGen, a KV cache transfer engine that allows seamless disaggregated LLM inference with three data transfer paths. Specifically, we leverage 1) a profile-based proactive transfer path to identify and push essential KV cache entries to the decoding node during the prefill stage, 2) a parallel on-demand transfer path to simultaneously fetch remote and local KV cache entries during the decoding stage, and 3) a speculative transfer path to finally deliver all KV caches to the decoding node. Experimental results show that SmartGen reduces time-to-second-token by up to 4.3x compared with the typical full KV cache transfer approach while offering comparable subsequent decoding performance and accuracy.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：大语言模型（LLM）推理通常分为两个阶段——**预填充（prefill）** 和**解码（decoding）**。现代 LLM 服务系统普遍将这两个阶段**分离部署**到不同节点（P/D Disaggregation），以独立、灵活地分配资源，提升整体吞吐。
- **核心问题**：在分离式架构中，**KV 缓存（key-value cache）** 必须在推理请求期间从预填充节点传输到解码节点。对于在租用云实例上自托管 LLM 的用户而言，云实例的节点间网络带宽通常较低（如 10–35 Gbps），而 KV 缓存体积大且随序列长度、批大小和模型规模线性增长，从而**极易饱和网络带宽**，导致“阶段转换停滞”（stage-transition stall），显著增加**到第二个令牌的时间（TTST）**，损害用户体验。
- **量化严重性**：作者实验中，在阿里云 L20 GPU + 25 Gbps RDMA 环境下，传输 48K token 的 KV 缓存比预填充计算本身多花费 6.5× 时间；KV 缓存传输在极端情况下可占作业完成时间的 42.2%。
- **现有方案不足**：既有系统（Splitwise、DéjàVu 等）通过将 KV 传输与预填充计算重叠来隐藏延迟，但无法从根本上解决带宽瓶颈；HACK 采用量化压缩 KV 缓存，但会带来精度损失。
- **核心思路**：利用 KV 缓存的**动态稀疏性**——并非所有 KV 条目在解码阶段都同等重要，只选择并传输关键 KV 条目，即可大幅降低网络负担，同时保持模型精度。
- **两个关键挑战**：
  1. **预填充阶段准确识别重要 KV 条目**：主流稀疏注意力算法依赖解码阶段生成的 query 或 hidden states，预填充阶段无法获得这些信息；
  2. **解码阶段高效获取 KV 条目**：按需远程拉取会增加网络往返到关键路径，累积开销显著。

## 2. 论文提出的方法论

### 2.1 总体架构

SmartGen 是一个**重要性感知的 KV 缓存传输引擎**，将 KV 缓存条目分为三类，并设计三条互补的数据传输路径：

- **普遍重要（universally important）** 条目 → 基于 profile 的**主动传输**路径
- **上下文相关（context-dependent）** 条目 → **并行按需传输**路径
- **低重要性（less important）** 条目 → **推测式传输**路径

### 2.2 Profile-based Proactive Transfer（基于 profile 的主动传输）

- **关键观察（位置相似性）**：重要 KV 条目在输入序列中往往出现在**一致的位置区域**，且这一分布模式在不同数据集和不同提示长度下相对稳定。
- **离线 profiling**：
  - 在校准数据集上运行一轮推理，统计每个 KV 条目被 KV 选择算法选中的频率。
  - 将每层的 KV 缓存沿序列维度划分为 \(M\) 个 KV 块（block），计算每个块的重要度：
    \[
    I_{l,m} =
    \begin{cases}
    \infty, & \text{if } l = 0 \text{ or } 1 \\
    \frac{1}{|E(B_{l,m})|}\sum_{e \in E(B_{l,m})} S(e), & \text{if } 2 \leq l < L
    \end{cases}
    \]
    即前两层 KV 块始终被选；其余层按平均选中频率排序。
  - 根据预填充计算时间 \(T_p\) 和全量传输时间 \(T_t\)，计算可在预填充阶段重叠传输的 KV 块数量上限：
    \[
    K_r = M \cdot (L-1) \cdot \frac{T_p}{T_t}
    \]
    并在实践中将 \(K_r\) 裁剪到 \([2M, LM]\) 之间，保证前两层一定被传输。
- **在线传输**：每层 KV 缓存被 offload 到 CPU 内存时，SmartGen 将其分割为块，若该块位于 top-\(K_r\) 重要块中，则通过 **RDMA WRITE** 直接推送到解码节点的 KV 缓存池中。

### 2.3 Parallel On-demand Transfer（并行按需传输）

- **目标**：将远程 KV 获取的网络往返从关键路径中移除。
- **核心思想**：将 KV 索引分为本地和远程两部分，从而让**本地 KV 装载与远程 KV 获取并行执行**（两条独立数据通道）。
- **Mask-based Index Splitting（基于掩码的索引拆分）**：
  - 解码节点为每个注意力层维护一个 **int8 KV mask 矩阵**（形状 \(B \times N\)），记录每个 token 的 KV 状态：0 = padding、1 = 本地可用、2 = 远程存储。
  - 预填充节点推送 KV 块时，同时通过 RDMA WRITE 更新对应的 mask 值，并利用 doorbell batching 保证顺序一致性。
  - 在 GPU 上，通过轻量索引操作将 KV 选择算法输出的 KV index 拆分为 `local_index` 和 `remote_index`。
- **Reordering-based KV Gathering（基于重排序的 KV 聚合）**：
  - 利用注意力运算对 KV 沿序列维度的顺序不敏感（softmax(QK^T/√d)V 的结果不受 KV 顺序影响），将每行 KV 索引按 mask 值降序重排，使远程 KV 条目在每行中连续排列。
  - 解码节点可**逐行连续 RECV** 远程条目，并利用 RDMA NIC 的 **scatter 能力**将数据高效分发到目标行，大幅减少 I/O 次数（最多可达 20×）。

### 2.4 Speculative Transfer（推测式传输）

- **动机**：即使在并行按需传输下，远程获取的网络开销仍可能累积，无法完全隐藏。
- **关键观察**：在解码阶段，注意力计算期间 CPU 和 RDMA NIC 是空闲的（KV 索引生成后才开始 KV 获取，而 KV 获取与 FFN 重叠），因此可利用这些空闲资源进行后台传输。
- **实现方式**：每个注意力层开始时，解码节点通过 RDMA SEND 通知预填充节点网络空闲；预填充节点按重要度顺序发送剩余的 KV 块。为防干扰，每次发送的块数受限于**推测比例（speculative ratio）**，默认设为 10%，使所有剩余 KV 块约在 10 次解码迭代内传完，且几乎不影响按需获取。

### 2.5 适用范围与扩展

- 兼容多种 KV 选择算法（如 InfiniGen、HATA），统一使用 KV index 抽象。
- 支持定期重新 profiling 以适应负载变化；可分组按提示长度生成多个重要性矩阵。
- 可根据网络负载动态调整传输策略：高负载时采用选择性传输，低负载时自动回退到全量传输。
- 在无 GDR 的云实例上，可通过在 CPU 内存中维护 mask 和增加一次额外 host-to-device 拷贝来适配。

  - Profile-based 主动传输将 on-demand ratio 降低 38%（相比 sequential），TBT 改善 1.03–1.1×；
  - Parallel on-demand 传输将网络往返移出关键路径，TBT 改善 1.1–1.2×；
  - Speculative 传输在约 10 次迭代内完成剩余 KV 推送，TBT 进一步降低 1.2–1.3×。
- **精度保持良好**：SmartGen 的准确率与全 cache 基线基本持平（相对 92%–120%），而 HACK 仅达到 13%–77% 相对准确率，表明动态 KV 选择在长上下文任务中优于激进量化。
- **普适性强**：同时适配 InfiniGen 和 HATA 两种不同风格的 KV 选择算法，并在多种模型和带宽下表现稳定。

## 7. 优点

- **问题定位精准**：切中自托管云实例上 P/D 分离部署的网络带宽瓶颈，提出“选择性 KV 传输”这一新颖且正交于量化的优化方向，与 HACK 等方法互补。
- **思路清晰、系统设计完整**：将 KV 条目按重要性分三类，并用三条数据路径分别处理，覆盖预填充、解码前期和解码全程，逻辑完备。
- **工程实现细节扎实**：
  - 使用 mask 矩阵和门铃批处理（doorbell batching）保证状态一致性；
  - 利用注意力对 KV 顺序不敏感的特性进行重排序，结合 RDMA scatter 能力减少 I/O；
  - 提出推测式传输利用注意力计算期间的空闲网络，避免关键路径争用。
- **可扩展性好**：支持多种 KV 选择算法，可周期更新 profile，适应动态网络负载，且对无 GDR 的廉价实例也有适配方案。
- **实验维度较全面**：涵盖多模型、多任务、多带宽、多参数敏感性以及消融，并在物理服务器上补充验证，增强结论可信度。

## 8. 不足与局限

- **离线 profiling 依赖先验数据**：位置相似性假设基于校准数据集，若真实请求分布与校准集差异过大，或提示长度超出已覆盖范围（如 >16K），重要性矩阵可能失真；论文虽提到周期性更新和分组 profiling，但未详细评估这些机制的有效性。
- **场景规模受限**：实验批大小较小、输出长度仅 64 token，未验证大规模并发、长生成（如数百至数千 token）下的表现。
- **未与所有 SOTA 系统对比**：未对比 DistServe、Splitwise 等端到端系统的实际部署效果；HACK 对比时仅使用默认 int2 量化，未探讨量化参数变化的影响。
- **部分开销未完全消除**：在 15 Gbps 低带宽下，SmartGen 的 TTST 甚至高于理想值，原因是最初两层 KV 和元数据张量的传输也会饱和带宽，说明仍存在残余瓶颈。
- **精度评估粒度有限**：仅报告 LongBench 上的总体指标，未逐条分析失败案例，也未讨论不同任务类型（如摘要 vs. 代码）对 KV 选择的敏感性差异。
- **云环境不确定因素**：阿里云弹性 NIC 的带宽稳定性弱于物理 NIC，可能引入噪声；论文未报告多次重复实验的方差或置信区间。
- **成本与部署复杂度**：离线 profiling 需要额外推理轮次，且需要对现有推理系统进行多处修改（mask 矩阵、索引重排、RDMA 控制），实际采用成本未量化。
