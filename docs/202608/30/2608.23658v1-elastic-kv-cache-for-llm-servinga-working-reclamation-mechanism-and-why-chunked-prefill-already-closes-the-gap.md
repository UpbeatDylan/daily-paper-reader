## 摘要
LLM服务引擎在启动时一次性确定其键值(KV)缓存的大小，永久性地为最坏情况的预填充激活预留储备。在解码为主的阶段，该储备处于空闲状态，但无法将其交给KV池，因为它正是大型预填充所需的内存。我们探究这一储备是否可回收，并构建了一种机制来验证。我们的弹性KV缓存在解码期间将储备借给KV池，并在预填充之前归还，这由调度器对下一批次的一步前瞻视图驱动。它在CUDA虚拟内存路径上是纯用户空间的：每层将两个物理句柄映射到一个连续的虚拟范围内，因此注意力内核保持不变，无需驱动程序补丁。它在几毫秒内解除提交，并在几十毫秒内重新提交，可与CUDA图和前缀缓存配合使用，且从不触发内存不足事件。相同内存的静态提交是不安全的，会在预填充突发时崩溃，因此动态切换是必要的。在构建了该机制后，我们测试了它所依据的前提，并报告一个诚实的负面结果。只有在较小的预填充块大小严重损害预填充延迟时，它才有价值。在将长提示注入实时解码负载的受控实验中，该惩罚很小（块大小为8192和32768个令牌之间，中位首令牌时间相差约1%），因为预填充受计算限制，而解码每步每序列仅消耗约一个令牌。简单地降低max_num_batched_tokens比控制器能恢复更多的KV，且延迟几乎相同。储备在张量并行下也会稀释，从TP1时KV的16%降至TP4时的2.7%。我们精确地说明了回收储备仍然有帮助的情况，并将该机制作为可重用的用户空间弹性VMM分配器发布。

## Abstract
An LLM serving engine sizes its key-value (KV) cache once, at startup, permanently setting aside a reserve for the worst-case prefill activation. During decode-dominant phases that reserve sits idle, yet it cannot be handed to the KV pool because it is exactly the memory a large prefill needs. We ask whether this reserve is reclaimable, and build a mechanism to test it. Our elastic KV cache lends the reserve to the KV pool during decode and returns it before prefill, driven by the scheduler's one-step-ahead view of the next batch. It is pure userspace on the CUDA virtual-memory path: two physical handles mapped into one contiguous virtual range per layer, so the attention kernel is unchanged and no driver patch is required. It decommits in a few milliseconds and recommits in tens of milliseconds, works with CUDA graphs and prefix caching, and never triggers an out-of-memory event. A static commit of the same memory is unsafe, crashing on prefill bursts, which makes the dynamic toggle necessary.   Having built the mechanism, we test the premise it rests on and report an honest negative result. It only pays off if a small prefill chunk size badly hurts prefill latency. In a controlled experiment injecting long prompts into a live decode load, that penalty is small (median time-to-first-token differs by about 1% between chunk sizes of 8192 and 32768 tokens), because prefill is compute bound and decode consumes only about one token per sequence per step. Simply lowering max_num_batched_tokens recovers more KV than the controller does, at nearly equal latency. The reserve also dilutes under tensor parallelism, from 16% of KV at TP1 to 2.7% at TP4. We state precisely when reclaiming the reserve could still help, and release the mechanism as a reusable userspace elastic-VMM allocator.

## 1. 论文的核心问题与整体含义

- **研究背景**：LLM 服务引擎（如 vLLM）在启动时一次性确定 GPU 内存划分，其中 KV 缓存是稀缺资源，决定了并发请求数和最大上下文长度。为避免最坏情况下的预填充（prefill）激活内存超限，引擎会永久预留一部分显存（称为 prefill-activation reserve），这部分预留内存远大于实际稳定运行时所需。
- **核心问题**：在解码（decode）为主的阶段，这块预填充预留内存完全闲置，却无法交给 KV 池使用，因为它正是大型预填充步骤所需的确切内存。论文问：**这块预留内存是否可被回收利用？**
- **整体含义**：论文构建了一个"弹性 KV 缓存"机制，证明技术上可以安全回收该预留内存（动态切换而非静态提交），但进一步通过受控实验表明：**该机制在主流工作负载下收益甚微**——因为 vLLM 的分块预填充（chunked prefill）已经弥合了预填充延迟与 KV 容量之间的权衡缺口。这是一篇"工程可行但前提不成立"的诚实负面结果论文。

## 2. 论文提出的方法论

- **核心思想**：利用调度器"一步前瞻"的能力，在 decode-only 阶段将预填充预留内存借给 KV 池（增加可用 KV 块数），在下一个预填充步骤到来之前归还（释放内存），从而在保证不 OOM 的前提下扩大 KV 容量。
- **关键技术细节**：
  - **连续性约束**：vLLM 的 KV 缓存是每层一个连续张量，注意力内核通过单一基指针按 block id 索引。任何弹性方案必须保持每层一个连续虚拟地址范围，否则需重写注意力内核。
  - **双句柄单虚拟范围**：基于 CUDA VMM API（`cuMemCreate`、`cuMemMap`、`cuMemAddressReserve`），每层保留一个覆盖 base+elastic 的虚拟地址范围，由两个物理句柄支撑。base 句柄始终映射；elastic 句柄映射/取消映射虚拟范围顶部的子区域（按 2 MiB VMM 粒度对齐）。因虚拟范围不变、base 子范围保持映射，注意力内核无需任何修改。
  - **调度器控制**：通过 `max_num_batched_tokens` 对应的块池门控，elastic 块只在提交时发放；使用滞回（hysteresis）避免抖动。
  - **切换开销**：全量 3.09 GiB 预留（28 层）的 decommit 约 3–4 ms，recommit 约 24–30 ms（朴素方法约 180 ms），decommit（预填充前必须执行的方向）成本更低。
  - **兼容性**：与 CUDA graphs、prefix caching 兼容；生成结果在 commit/decommit 周期之间逐位一致。
  - **实现形态**：torch 可插拔分配器 + 块池门控 + 调度器边界控制器，纯用户空间实现，不需要驱动补丁。
- **静态提交为何不安全**：若将整块 3 GiB 预留静态并入 KV 池，能恢复容量（约 314K→370K tokens），但首次 62K-token 预填充突发即 OOM（该预填充需约 2.3 GiB 激活内存）。OOM 安全的静态上限仅约 1.2 GiB（约 6% 增益）。动态切换则能安全运行同样突发（先 decommit 4.4 ms，再预填充，后重新 commit）。
- **已知 bug**：大型预填充后的第一次 recommit 会 OOM，因为 torch caching allocator 持有已释放的预填充内存；需先调用 `empty_cache()` 再执行 `cuMemCreate`。

## 6. 论文的主要结论与发现

1. **弹性机制可行且必要**：动态切换能在毫秒级完成预留的借出/归还，零 OOM，且不修改注意力内核、不补丁驱动；静态提交不安全（在预填充突发时崩溃），因此动态切换是捕获全部预留的唯一方式。
2. **核心前提不成立**：小 chunk（8192）与大 chunk（32768）之间，前台长提示 TTFT 中位数仅差约 1%（4.97 s vs 4.91 s），最大 TTFT 差约 5%。原因在于：预填充是计算密集型（compute bound），分块只改变粒度不改变总工作量；decode 每步每序列仅约 1 token，即使 280 条序列同时解码也只占 8192 chunk 预算的约 3%，不足以饿死预填充。
3. **简单基线更好**：直接降低 `max_num_batched_tokens` 比弹性控制器恢复更多 KV（375K vs 364K tokens），且延迟几乎相同——弹性机制没有战胜平凡基线。
4. **张量并行稀释**：预留占 KV 比例从 TP1 的 16% 降至 TP4 的 2.7%（7B）；32B 模型在 TP4 下约 7.7%。大模型需要高 TP，而高 TP 下预留太小，该机制无利可图。
5. **适用场景极窄**：理论上仅当同时满足"低 TP、中小模型、长上下文、KV 稀缺、且小 chunk 确实严重拖累预填充吞吐"时，弹性缓存才可能有价值；论文在实验硬件上未能构造出这样的场景。
