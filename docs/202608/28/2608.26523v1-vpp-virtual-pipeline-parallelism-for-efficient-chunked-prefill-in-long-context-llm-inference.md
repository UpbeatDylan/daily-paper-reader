## 摘要
分块预填充流水线并行（CPP）是LLM推理中的一项关键技术。然而，等大小分块表现出不均衡的延迟，因为后面的分块需要关注更长的前缀KV缓存，产生更高的注意力成本，导致流水线气泡。现有方法通过动态分块调整大小来缓解这种不均衡（即动态CPP，DCPP），但我们的测量表明，这以调度开销换取负载均衡，在长序列上变得不利。在本研究中，我们提出了虚拟流水线并行（VPP），它保持分块大小固定，并通过虚拟阶段优化流水线布局。V形虚拟阶段遍历将每个分块昂贵的中间阶段与其邻居较轻的头尾阶段重叠，同时异步通信和流水线打包进一步减少通信停滞和跨请求的排空气泡。我们在vLLM-Ascend中实现了VPP，并在16个Ascend 910C NPU上对三个基于MoE的LLM进行了评估，序列长度最高达1M token。在长序列上，VPP相比DCPP将吞吐量提升了高达13.1%，在混合工作负载上提升了6.7%，同时在短序列上保持了性能。在512K-token的DeepSeek-V3.1预填充工作负载中，VPP将流水线气泡率从6.4%降至0.1%，与DCPP相比实现了98.0%的降低。

## Abstract
Chunked prefill pipeline parallelism (CPP) is a key technique for LLM inference. However, equal-size chunks exhibit imbalanced latency, as later chunks attend longer prefix KV caches and incur higher attention costs, leading to pipeline bubbles. Existing approaches mitigate this imbalance through dynamic chunk resizing (Dynamic CPP, DCPP), but our measurements show that this trades scheduling overhead for load balancing, which becomes unfavorable on long sequences. In this study, we propose Virtual Pipeline Parallelism (VPP), which keeps chunk sizes fixed and optimizes the pipeline layout through virtual stages. A V-shaped virtual-stage traversal overlaps each chunk's expensive middle stages with the lighter head and tail stages of its neighbors, while asynchronous communication and pipelined packing further reduce communication stalls and cross-request drain bubbles. We implement VPP in vLLM-Ascend and evaluate it on three MoE-based LLMs with sequences up to 1M tokens on 16 Ascend 910C NPUs. VPP improves throughput by up to 13.1% over DCPP on long sequences and 6.7% on mixed workloads, while preserving performance on short sequences. On a 512K-token DeepSeek-V3.1 prefill workload, VPP reduces the pipeline bubble ratio from 6.4% to 0.1%, achieving a 98.0% reduction compared with DCPP.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：随着 Agent 系统、多轮对话、工具调用等 LLM 应用的发展，推理工作负载的上下文长度不断增长，长上下文（可达百万 token）的 prefill 计算开销巨大，容易引发 Head-of-Line 阻塞、加速器利用率低、TTFT 延迟劣化等问题。
- **核心矛盾**：Chunked Prefill Pipeline Parallelism（CPP）将长提示词拆分为多个等大小分块，以分块为基本单元流经流水线各阶段。由于因果注意力机制，**越靠后的分块需要处理越长的前缀 KV 缓存，导致计算延迟近似线性增长**，从而产生严重的阶段间负载不均衡和流水线气泡。
- **现有方案不足**：动态分块（DCPP）通过实时估计和动态调整分块大小来均衡执行时间，但其代价是更细粒度的执行切分（kernel 数量、调度次数显著增加），在长序列下调度和算子碎片化开销会反超负载均衡收益；同时 DCPP 依赖成本估计，无法完全消除气泡。
- **深层洞察**：分块延迟的不均衡并非"无序扰动"，而是具有**近似线性的可预测增长规律**。作者认为这本质上是**流水线布局问题而非分块大小问题**——固定分块大小、通过虚拟阶段布局来匹配不均衡，比动态调整分块更高效。
- **整体意义**：VPP 提供了一种"布局调优替代动态调度"的新思路，避免了 DCPP 的运行时自适应复杂度和长序列下的碎片化开销，为长上下文推理的高效流水线并行提供了新的设计空间。

## 2. 方法论：核心思想、关键技术细节

### 2.1 核心理念
- 保持分块大小固定，将模型层划分为**多个虚拟阶段**（virtual stages），并以**V 形折返布局**映射到物理流水线 rank 上，使相邻分块的"重"中间阶段与"轻"头尾阶段在时间上重叠，从而吸收延迟增长带来的不均衡。

### 2.2 V 形虚拟阶段遍历（V-shaped traversal）
- 以 2 个物理 rank（pp0、pp1）、4 个虚拟阶段（s0~s3）为例：s0/s3 映射在 pp0，s1/s2 映射在 pp1，分块沿 s0→s1→s2→s3 的路径遍历（先去程再回程），形成 V 形。
- **公式化的负载匹配机制**：设第 k 个分块 Ck 的单阶段时延近似为 τk = (k+1)t（t 为第一个分块的单阶段时延）。pp1 执行 Ck 的中间两个阶段需约 2τk = 2(k+1)t；与此同时 pp0 可执行上一分块的尾阶段 s3/Ck−1（时延 τk−1 = kt）和下一分块的头顶阶段 s0/Ck+1（时延 τk+1 = (k+2)t），两者之和为：

  τk−1 + τk+1 = kt + (k+2)t = 2(k+1)t = 2τk

  即 pp0 与 pp1 的计算量在稳态下几乎完全匹配，从而消除由不等分块延迟引起的气泡。

### 2.3 异步通信与阶段重排（VPP-Async）
- 消除 V 形遍历中双向 rank 间同步 send/recv 的阻塞等待：通过将前一分块的尾阶段（s3/Ck−1）与下一分块的头阶段（s0/Ck+1）的执行顺序互换，使每个方向的通信在执行另一侧有用计算时异步发起，实现通信-计算重叠。

### 2.4 跨请求流水线打包（Pipelined Packing）
- 将下一个请求 R′ 的早期分块提前填入当前请求 R 尾部的 drain 窗口（时长约 (N+1)t），由于早期分块延迟最低（τ ≈ t），能自然适配逐渐缩小的尾部窗口，从而压缩跨请求的排空气泡。

### 2.5 系统实现
- 基于 vLLM-Ascend 实现，控制面（虚拟阶段调度器、循环布局层分配、流水线状态机）用 Python 实现，注意力与 MoE kernel 重用不改动。
- 采用双队列调度器（初始遍历队列 + 续行队列），支持折叠点零通信、非均匀层划分、异步任务句柄，以及两个交替的 HCCL 通信组避免双向传输死锁；单个开关即可开关 VPP。

  - DeepSeek-V3.1-Terminus（671B 总参，37B 激活，256 experts，MLA 注意力）

  - TP8+DCPP2：动态分块（vLLM-Ascend 推荐配置：最小分块 4096 token，平滑因子 1.0）

## 6. 主要结论与发现

- **DCPP 的局限性**：在 512K-token DeepSeek-V3.1 prefill 负载下，DCPP 相比 CPP 虽减少 47.0% 的气泡时间，但计算时间增加 10.48%、暴露通信增加 36.05%，最终 TTFT 反而劣化 4.65%；在长序列上动态调整的碎片化开销会反超负载均衡收益。
- **VPP 的端到端增益**：
  - 长序列（64K–1M）：相比 DCPP，吞吐最高提升 13.1%（DeepSeek），Qwen 上提升 3.7%–8.7%，GLM 上增益随序列变长而收窄（峰值 8.5% @64K）
  - 混合负载：相比 DCPP 吞吐提升最高 6.7%（DeepSeek），Qwen 上 0.8%，GLM 上 1.3%–1.6%
  - 短序列（4K–16K）：与 DCPP 基本持平（DeepSeek 上最高领先 10.8%），Qwen 上在小 chunk 时有 6.8% 退化（模型激活参数量小，调度开销摊销不足）
- **气泡消除效果显著**：512K DeepSeek 预填充负载下，VPP 将气泡率从 DCPP 的 6.35% 降至 0.14%（相对减少 98.04%）；启动等待从 1.85s 降至近乎为 0。
- **增益来源**：计算时间减少 10.11%（主要来自 Slice、MatMulV3 等算子碎片化开销的降低），气泡减少 98.04%，但暴露通信增加了 35.05%（AllGather 单次延迟增大），通信-计算重叠率从 0.05% 提升至 51.75%。
- **消融验证**：VPP-Async 相比 vanilla VPP 端到端延迟降低 3.13%，继续叠加流水线打包后累计降低 6.89%；气泡率从 11.0% → 8.3% → 2.4%；非重叠通信减少 48%。
- **Chunk size 规律**：非整除的 chunk size（如 24K）通常最优，因为最后一个较小的分块在 drain 阶段与前置计算重叠，减少尾部气泡；序列极短（64K）时小 chunk 更优。

## 7. 优点

- **问题洞察深刻**：将"不均衡的分块延迟"从需要动态消除的"问题"重构为可预测的"规律"，进而用静态布局去适配，角度新颖且规避了 DCPP 的固有开销。
- **方法设计精巧**：V 形遍历的负载匹配有清晰的数学推导（τk−1 + τk+1 = 2τk），不是启发式而是可证明的平衡机制；三个优化组件（V 形遍历 → 异步通信 → 跨请求打包）层层递进、职责清晰。
- **评测比较扎实**：多模型 × 多场景 × 多指标的评测矩阵较完整，chunk size 扫描保证了公平性，profiler 级性能分解使结论可追溯、可解释。
- **实现完整且开源**：在主流推理框架 vLLM-Ascend 中有真实可用实现，提供单开关切换，实用性高。
- **正视了方法代价**：论文明确量化了 VPP 在暴露通信上的增加（+35.05%）并解释了原因，未回避权衡。

## 8. 不足与局限

- **适用前提受限**：VPP 的平衡推导依赖"分块延迟随索引近似线性增长"这一规律，该规律在**稀疏注意力（如 GLM 的 DSA）模型下不再严格成立**，收益随序列增长明显收窄；若 MoE 未启用专家并行或前缀注意力占比下降，平衡也会退化。
- **流水线深度验证不足**：所有实验均使用 PP=2，未评估 PP=4/8 或更多物理 rank 时 V 形布局的实际效果；更深流水线下的通信模式、折叠点数量、打包策略的扩展性未知。
- **短序列存在退化风险**：在 Qwen3 这类小激活参数模型上，短序列场景可能出现最多 6.8% 的吞吐退化，说明调度开销在小模型、短请求下摊销困难，适用范围有限。
- **通信开销增加**：VPP 的暴露通信相比 DCPP 增加约 35%（主要是 AllGather 单次时延增大），虽然通过重叠改善了净效果，但在通信带宽受限或更大规模集群上仍存在隐患。
- **实验覆盖场景有限**：混合负载由单一数据集（GSM8K）合成，真实生产环境的请求到达模式、上下文分布更加复杂；也未涉及多轮对话、上下文续写（prefill + decode 混合）场景。
- **技术栈绑定**：实现和评测绑定华为 Ascend（CANN/HCCL/vLLM-Ascend），结论在 GPU/CUDA 生态上的一般性有待验证。
