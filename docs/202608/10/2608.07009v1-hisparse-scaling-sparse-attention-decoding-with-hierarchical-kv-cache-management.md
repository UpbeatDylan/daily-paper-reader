## 摘要
Top-k稀疏注意力使得长上下文LLM解码的计算成本变得低廉：每一步只需读取数千个选定的KV条目，而非整个上下文。然而，服务系统通常将整个KV缓存保存在GPU HBM中，以确保每个位置都可被选择，因此单个请求的内存开销仍随其完整上下文长度增长——解码在计算耗尽之前很久就遇到容量墙，而KV缓存超出HBM的上下文根本无法被服务。我们提出HiSparse，一种用于稀疏注意力服务的精确、与索引器无关的分层KV缓存。HiSparse将每个请求的完整KV历史保存在主机内存中，并通过一个小的、固定大小的GPU缓存来限制其解码内存占用；一个融合的CUDA内核在解码CUDA图内解析每一层的选择——命中检测、LRU替换和主机到设备的数据获取；对于跨层共享选择的模型，精确的逐层预取可将剩余未命中开销的大约一半隐藏。由于仅改变KV的放置位置，模型输出不变。HiSparse已合并到上游SGLang中，并在H200、B200和GH200平台上对三种稀疏注意力家族（DSA、NSA和Quest）进行了评估：在长上下文工作负载上，峰值生成吞吐量最高提升4.7倍，同时保持可比的每令牌延迟并减少高负载下的首令牌时间——而一个无IO的基准测试显示，解析机制本身没有增加可测量的每令牌成本，使得主机-设备IO成为有界驻留的唯一代价。

## Abstract
Top-k sparse attention makes long-context LLM decoding cheap to compute: each step reads only a few thousand selected KV entries rather than the full context. Serving systems, however, typically keep the entire KV cache in GPU HBM so that every position stays selectable, so a request's memory bill still grows with its full context length--decoding hits a capacity wall long before it runs out of compute, and a context whose KV cache exceeds HBM cannot be served at all. We present HiSparse, an exact, indexer-agnostic hierarchical KV cache for sparse-attention serving. HiSparse keeps each request's full KV history in host memory and bounds its decode footprint with a small, fixed-size GPU cache; a fused CUDA kernel resolves each layer's selections--hit detection, LRU replacement, and host-to-device fetches--inside the decode CUDA graph; and, for models that share selections across layers, exact layer-wise prefetching hides roughly half of the remaining miss overhead. Because only KV placement changes, model outputs are unchanged. HiSparse is merged into upstream SGLang and evaluated across three sparse-attention families (DSA, NSA, and Quest) on H200, B200, and GH200 platforms: it improves peak generation throughput by up to 4.7x on long-context workloads while preserving comparable per-token latency and reducing time-to-first-token at high load--and a no-IO oracle shows the resolution mechanism itself adds no measurable per-token cost, leaving host-device IO as the only price of bounded residency.

# HiSparse：通过分层KV缓存管理扩展稀疏注意力解码 —— 论文总结

## 1. 核心问题与整体含义
- **背景**：长上下文是大语言模型（LLM）的主流工作负载，但 KV 缓存随全文长度增长，服务成本高昂。Top-k 稀疏注意力（如 DSA、NSA、Quest）使每步解码只读取 k 个选定 KV 条目，计算成本大幅降低，现有服务系统却仍将完整 KV 缓存驻留在 GPU HBM 中以保证任意位置可被选中。
- **核心矛盾（容量墙）**：请求的 HBM 内存账单仍随全文长度增长，而实际读取量仅为 k。以 GLM-5.1 为例：128K 上下文需 13.09 GB KV 状态；1M 上下文请求需要超过 100 GB HBM，在权重驻留后根本无法被接纳。容量墙在计算耗尽之前就限制了解码批量与并发度，也限制了可服务的最大上下文长度。
- **整体含义**：注意力计算已稀疏化，但其“内存租金”仍是全文本。HiSparse 提出一个精确（exact）、索引器无关（indexer-agnostic）的分层 KV 缓存系统，将完整 KV 历史移到主机内存，GPU 只保留固定大小缓存，从而将“逻辑可用性”与“物理驻留”解耦，使解码 HBM 占用与上下文长度无关。

## 2. 方法论
- **核心思想**：利用稀疏选择的时间局部性——相邻解码步骤大量重复选择相同位置、相邻层选择相关位置——用 LRU 管理的小型 GPU 缓存命中大部分选择，未命中部分从主机批量获取，实现“HBM 为注意力实际读取的内容买单，而非可能读取的内容”。
- **两级层次结构**：
  - **主机 KV 池**（pinned DRAM）：存放权威的完整 KV 历史，可恢复任意逻辑位置。
  - **GPU 缓存**（每请求每层 B 个槽位，B ≥ k）：存放最近选中的 KV 记录，B 为服务配置参数，与上下文长度 Lctx 无关；页面表映射逻辑位置到缓存槽位或主机，LRU 元数据驱动替换，始终驻留 GPU。
- **请求生命周期**：四个阶段——(1) Prefill 写入主机池（压缩索引器状态仍驻留 GPU）；(2) 准入（按 B 而非 Lctx 预留空间）；(3) 逐层解码（先解析命中/缺失再运行注意力内核）；(4) 将新生成 token 的 KV 写穿透到主机池。
- **融合 RESOLVE 内核**（关键机制）：单次启动完成五个阶段——① 用选定位置构建共享内存哈希表；② 探测 GPU 缓存每个槽位、标记命中/可淘汰；③ 并行扫描选择受害者并更新 LRU；④ 通过 GPU 辅助 IO（ld.global.nc.v2.b64 向量化非一致性加载，借鉴 Strata）从 pinned 主机内存批量获取缺失记录；⑤ 发布物理槽位向量供注意力后端使用。内核捕获在 SGLang 解码 CUDA 图中，避免逐层多次启动。一次解析服务 DSA/NSA/Quest，类似软件管理的 TLB。
- **层间精确预取**：对共享索引的模型（如 GLM-5.2 的 IndexShare：21 个 anchor 层 + 57 个共享层），anchor 层解析时记录缺失计划（哪个主机记录进入哪个槽位），副流复制内核将该计划重放到共享层缓存中，与中间层计算重叠。共享层直接复用 anchor 的槽位表、跳过解析。对无共享索引模型尝试的推测性预取（用 ℓ 层选集预测 ℓ+1 层）几乎无收益。
- **替换策略**：每请求-层独立 LRU，命中项晋升到 MRU 端并高于新获取的缺失项，使一次性选择先被淘汰，累积具有跨步复用的位置。

## 6. 主要结论与发现
- **吞吐提升**：峰值生成吞吐最高提升 4.7 倍（Qwen3+Quest 在 200K 上下文）；GLM-5.1 在 32K 提升 3.1×、160K 提升 2.9×；DeepSeek-V4-Flash 在 32K 提升 2.1×（含 prefill）和 2.9×（仅解码）。收益全部来自批量增大而非单步加速。
- **延迟影响**：低并发下 TPOT 与基线相当（15.9 vs 16.0 ms），高负载下 TTFT 显著更低（如并发 64 时 171s vs 829s）。
- **局部性与缓存策略**：B=2k 的 LRU 平均缺失率 13.4%，优于 FIFO（17.2%）和随机（16.1%），接近 Bélády 最优（8.2%）；top-k-only 暂存缺失率达 30%；B=4k 时 LRU 缺失率降至 6.7%。
- **解析开销**：no-IO oracle 显示解析机制本身无额外每 token 成本，HiSparse 的全部 TPOT 开销等价于主机-设备 IO；GH200 的 NVLink-C2C 将 GLM-5.1 的 IO 组件从 112 μs 压缩至 29 μs。
- **预取效果**：精确预取在匹配并发下降低 TPOT 13–15%、提升吞吐 14–17%，达到 no-IO oracle 吞吐的 85%（1727 vs 2034 tokens/s）；无预取为 74%；剩余未隐藏 IO 中约 27% 是 anchor 层自身同步缺失的结构性下限。

## 7. 优点
- **精确稀疏注意力**：只改变 KV 放置位置，不改变选择、分数或输出，与模型无关，无需重训或修改模型。
- **索引器无关接口**：统一消费各索引器（DSA/NSA/Quest）发出的逻辑位置，一个内核服务所有家族，工程上已合入上游 SGLang（约 2200 行 Python + CUDA 内核头文件）。
- **系统设计完整**：从 LRU 缓存（利用局部性减少 IO 而非仅重叠 IO）、融合解析内核（避免逐层启动开销）、GPU 辅助 IO（碎片化读取接近链路带宽）到利用模型共设计的精确预取，形成闭环。
- **容量收益可双向使用**：同一机制既能转化为大批量高吞吐，也能转化为更小 HBM 部署或超 HBM 上下文的可行性（1M token 请求可由主机容量承载）。
- **客观性**：通过 no-IO oracle 明确界定 IO 是唯一代价；通过 Bélády 最优界定缓存策略提升上限；多平台传感器对比隔离了硬件影响。

## 8. 不足与局限
- **TPOT 额外开销**：当服务不处于容量受限状态（短上下文、低并发）时，HiSparse 无收益且需承担 7–8 ms/token 的暴露 IO（同步解析），只能通过关闭功能规避。
- **主机内存规模限制**：假设第二层远大于 HBM，但 Grace 类平台（GB200/GB300）上主机内存仅与 GPU HBM 相当甚至更小，容量乘数大幅缩水；NVMe/网络扩展会提高延迟成本。
- **预取依赖模型共设计**：推测性预取无增益，精确预取依赖 IndexShare 类跨层共享索引的模型特性，无法推广到无共享选择结构的模型。
- **实验缺口**：未做物理 PD 分离部署验证；未与 ESS、ECHO 等并发系统直接对比；未做超长上下文 + 极限并发的 TPOT 压力测试；B 值需静态配置，动态调节留作未来工作。
- **方向性偏差风险**：论文作者同时是 SGLang 上游维护者，HIsparse 与基线对比由其自身实现完成，虽通过公开基准和 oracle 设计增加客观性，但第三方复现验证仍有必要。
