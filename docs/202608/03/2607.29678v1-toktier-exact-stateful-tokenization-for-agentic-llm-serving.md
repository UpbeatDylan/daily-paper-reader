## 摘要
LLM服务系统会缓存提示词的KV状态，但大多数前端在每次调用时仍会对完整请求文本重新分词。这给编程智能体带来了成本，因为它们在每个小的工具结果后重新提交长记录，而重用很困难，因为即使一个短的追加也可能改变前一个序列末尾附近的词元边界。在来自两个智能体生态系统的153,951次调用中，平均每次调用追加约1.4K字符，只有1.0%-3.6%的调用会以百万级字符的上下文启动或重建会话。在94.1%的机群提示缓存命中率下，分词时间可占到首词元延迟的64%。TokTier是一种有状态分词服务，其契约是：发出的词元ID始终与请求文本的完整参考分词完全一致。对于会话延续，它在追加点周围重新分词一个小窗口，并且仅在通过每次请求的稳定边界检查后才拼接，失败时扩大窗口或回退到完整分词。对于没有可重用前缀的调用，它将对GPT家族正则表达式预分词分解为运行时局部规则，并在GPU上执行精确的预分词和BPE。一个抽样影子验证器会重新检查实时流量。在17个分词器家族中，差异化测试覆盖了1.5×10^10次拆分检查、12.4 TB的真实文本语料库和93,000多个重放的智能体步骤，零偏差。增量修复在100K到3M字符范围内耗时0.5-1.1毫秒，比HF分词快最多437倍，在1M长度下比预热的基于缓存的最强基线（Gigatoken）快2.1倍。GPU完整分词在0.87毫秒内编码100万字符的请求，比HF低最多491倍，比已发表的最快CPU方法低23.4倍。使用vLLM，在记录的突发流量下，首词元延迟中位数下降16%-34%，P99下降23%。在50毫秒P99目标下，四个修复核心加一个GPU可维持1,821个请求/秒，而16核无状态前端在40时即饱和。

## Abstract
LLM serving systems cache prompt KV state, yet most front ends still re-tokenize the full request text on every call. The cost lands on coding agents, which resubmit a long transcript after each small tool result, and reuse is hard because even a short append can change token boundaries near the end of the previous sequence. Across 153,951 calls from two agent ecosystems, the median call appends about 1.4K characters, and only 1.0-3.6% of calls start or rebuild a session with contexts of millions of characters. At a 94.1% fleet prompt-cache hit rate, tokenization reaches up to 64% of time to first token.   TokTier is a stateful tokenization service with one contract: emitted token IDs are always identical to full reference tokenization of the request text. For a session continuation, it re-tokenizes a small window around the append and splices only after a per-request stable-boundary check, widening the window or falling back to full tokenization on failure. For a call without a reusable prefix, it decomposes GPT-family regex pre-tokenization into run-local rules and runs exact pre-tokenization and BPE on a GPU. A sampled shadow verifier re-checks live traffic.   Across 17 tokenizer families, differential campaigns cover 1.5x10^10 split checks, a 12.4 TB real-text corpus, and 93,000+ replayed agent steps, with zero divergence. Incremental repair takes 0.5-1.1 ms from 100K to 3M characters, up to 437x faster than HF tokenization and 2.1x faster at 1M than the strongest cache-based baseline (Gigatoken) fully prewarmed. GPU full tokenization encodes a 1M-character request in 0.87 ms, up to 491x below HF and 23.4x below the fastest published CPU method. With vLLM, median time to first token drops 16-34% and P99 drops 23% under recorded bursts. Under a 50 ms P99 objective, four repair cores plus one GPU sustain 1,821 requests/s where a 16-core stateless front end saturates at 40.

## 1. 论文的核心问题与整体含义

- 大型语言模型（LLM）服务系统普遍采用前缀缓存（prefix caching）来复用未变化的提示词 KV 状态，但服务前端（front end）通常仍会在每一轮调用中对完整请求文本执行全量分词（tokenization）。
- 这一不匹配在编程智能体（coding agent）场景中尤为严重：智能体会在一个会话内反复提交很长的上下文字符串，并在末尾追加小段工具输出。由于追加内容可能改变之前序列靠近末尾的词元边界，缓存复用甚至增量分词都面临精确性挑战。
- 对两个智能体生态系统的 153,951 次调用分析显示：中位调用仅追加约 1.4K 字符，而仅有 1.0%–3.6% 的调用是会话启动或重建（携带全量长上下文）。在机群级提示缓存命中率达到 94.1% 时，分词开销可占首词元延迟（TTFT）的 10%–64%，成为服务瓶颈。
- 论文的核心含义：分词不应再以“每次请求全量重新扫描文本”的静态方式实现，而应像 KV 缓存一样，将会话级状态带入分词层，实现与参考分词完全一致的“有状态”高效服务。

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

### 核心思想
- TokTier 是有状态分词服务，位于请求路由器和模型引擎之间，对所有请求强制执行一项契约：**输出的 token ID 必须与冻结参考分词器对完整请求文本进行全量分词的结果逐位一致**。
- 它将工作负载分为两种模式：
  - **会话延续（session continuation）**：绝大多数请求，可复用先前会话的词元状态，采用增量修复。
  - **会话初始化/重建（state miss）**：少见但体积大，通常在 GPU 上执行精确全量分词。

### 关键技术细节与算法流程

**① 为什么不能直接拼接旧前缀与新词元？**
- 分词不可组合：`tokenize(A) ∥ tokenize(B)` 不一定等于 `tokenize(A ∥ B)`。例如“pipeline”一词被“pipe”和“line”切开时，独立分词会产出两个 token，而完整分词只产出一个 token。预分词器可能移动 piece 边界，BPE 合并顺序也随之改变，甚至可在数字分组、空白前瞻等规则下越过任意固定半径传播。

**② 增量修复（incremental repair）**
- 系统保存每个活跃会话的 token ID 序列和字节跨度，以及文本位置到 token 记录的索引。
- 处理一次追加：仅对旧上下文最后 w=512 个字符与新增文本 Δ 组成的小窗口做重新分词。
- 将新窗口与缓存记录比较，找出在位置和 token ID 上都相等的最长连续运行（matched run）。
- **稳定边界检查（stable boundary check）**：该运行须包含至少两个 token、覆盖的字符数超过词表最长 token 长度（如 Llama 家族为 128 字符），且必须包含一个“同步边界”——即字符类转换处，该处右侧的预分词输出在证明上与左侧文本无关。
- 检查通过则在运行末尾拼接（有定理证明拼接位置可与证书边界互换），输出即精确的全量分词结果。失败则扩大窗口重试，最多 5 次，最终回退到全量参考分词。检查失败只增加延迟，绝不改变输出。
- 形式化证明（附录 A）：将前端记为 `F = E* ∘ G`，其中 G 将输入拆分为 units，E 逐 unit 映射到 token ID。如果存在拼接证书（splice certificate），则按块拼接的 token 序列等于全量序列。

**③ GPU 精确全量分词**
- 针对无会话前缀可复用的大请求，将 GPT 家族正则预分词重新表述为“run 分解”：
  - 将每个字符分类为字母/数字/空白/其他四类，形成最大同字符类运行；
  - 每个字符是否为 piece 起点仅取决于其在运行内的偏移、跨越边界的至多 4 字符回看、以及三个运行级汇总；
  - 用并行前缀扫描和独立逐字符谓词完成，消除串行正则依赖。
- GPU BPE 流水线按 piece 长度分派（≤32 字节用单线程/piece，33–128 字节用 warp/piece，更长用 block/piece），并使用 CUDA figure 和最小设备同步（host 同步从 8 次降到 2 次）保证单请求延迟。
- 对不支持 GPU 的家族、小片段、GPU 背压等情况回退到 CPU 参考路径，契约不变。

**④ 运行时验证**
- 影子验证器（shadow verifier）以采样方式将输出重新与参考分词结果对比，捕获依赖执行历史（如之前曾编码过长前缀）的 bug。

## 6. 论文的主要结论与发现

- **正确性**：在 17 个 token 族、12.4 TB 真实语料与 9.3 万+ Agent 步骤上零差异，证明两种快速路径都可与参考结果完全一致。
- **性能**：
  - 增量修复在 100K–3M 字符上下文下中位 0.5–1.1 ms，比 HF 快最多 437 倍；在 1M 字符下比完全预热的 Gigatoken 快 2.1 倍，在 2M 下快 3.0 倍。
  - GPU 全量分词 1M 字符 0.87 ms，比 HF 低最多 491 倍，比已发表的最快 CPU 方法低 23.4 倍，批量吞吐 3.8–4.7 GB/s。
  - 与 vLLM 集成后，中位 TTFT 降低 16–34%，记录突发下 P99 降低 23%。
  - 50 ms P99 目标下，4 修复核 + 1 GPU 可服务 1,821 req/s，而 16 核无状态 CPU 前端只能服务 40 req/s。
- **状态化分词可行**：会话级词元状态可以保留更久于 KV 缓存，成本仅为每 token ~16 字节，且能提高会话状态命中率（从 5 分钟 TTL 调整到 1 小时可额外命中 2–6% 的调用）。
- **近似 GPU 方法不可接受**：仅在合并层面做并行加速的替代方案（如 plateau 提交）会在 0.34%–4.0% 的 pieces 上偏离参考输出，因此被排除。

## 7. 优点

1. **严格正确性保证**：将正确性契约置于一切性能优化之上，并以形式化定理 + 多层级差分测试 + 运行时影子验证三重保障支撑。
2. **针对真实负载设计**：基于大规模真实 Agent 轨迹确定“大多数调用是小追加、少数是大初始化”的两峰分布，使系统设计高度契合实际场景。
3. **创新的稳定边界检查**：不是简单用固定重叠窗口，而是基于每个 tokenizer 家族的稳定字符类转换证明“右侧输出不受左侧影响”，从根本上排除长距离传播的边界问题。
4. **GPU 端精确预分词**：通过 run 分解将串行正则扫描变为并行谓词，在不改变输出前提下大幅提升全量分词性能。
5. **落地性好**：与 vLLM 兼容只需通过 `prompt_token_ids` 接口，无需修改调度器；前缀缓存键空间与文本写入的前缀一致（验证命中率 99.84%）。
6. **充分披露局限**：对 GPU 路径的瓶颈（BPE 合并依赖链）、未支持的家族、NFC 归一化未完全 GPU 化以及会话状态构建开销均做了诚实说明。

## 8. 不足与局限

- **范围覆盖**：增量修复只对 15/17 个家族适用；另两个家族（归一化会抹除空白结构的两种）无法用稳定边界证做修复，只能全量回退；WordPiece 未纳入快速路径。
- **GPU 路径依赖链受限**：精确 BPE 的串行合并依赖链主导延迟，即使 L2 驻留、按架构调优、piece 记忆化等方法都无法进一步提升；作者明确批注“只有高时钟 GPU 才合适”。
- **会话状态构建缺口**：GPU 全量分词目前不输出字节跨度，导致需要会话状态的初始化请求仍须用 CPU 参考分词器补齐，会增加最高约 14 ms 开销。
- **负载覆盖局限**：个人追踪集仅覆盖 6 用户/9 机器，集中于编程智能体；虽然多来源交叉验证，但未覆盖所有可能的 Agent 应用，也未对未来新增 tokenizer 版本做出保证（每组新版本都需重新认证）。
- **存在性能回退点**：
  - 全量分词在超大请求与 NFC 快速检查失败时，P90 会显著退化（如 4.4M 字符下 CPU 归一化导致 P90 达 133 ms）。
  - 大附加（>50K 字符）会破坏修复路径的 P99 目标，且当前路由器不区分大小提升；作者提供了三种探索性路由和原型数据，但未纳入默认。
- **公平性细节**：比较中已尽量向基线有利方向倾斜（如 Gigatoken 使用完全预热/空缓存最优配置），容量对比中“45 倍”被明确说明是异构资源的结果，不可解释为纯算法增益。
