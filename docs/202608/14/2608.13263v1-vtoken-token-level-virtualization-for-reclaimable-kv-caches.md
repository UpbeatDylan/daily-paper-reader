## 摘要
大语言模型服务面临一个关键的内存瓶颈：KV缓存随序列长度和批大小增长。PagedAttention使用固定大小的内存块来减少分配器级别的碎片，但最近的KV驱逐算法以比块级管理更细的粒度（即Token级）进行操作。这种不匹配导致块内碎片，使很大一部分已分配的KV内存无法回收。我们提出vToken，一个轻量级的Token级虚拟化层，将逻辑Token活跃性与物理块放置解耦。vToken通过Token表间接寻址维护稳定的逻辑Token视图，并通过异步重打包活跃Token实现物理回收。该设计保持PagedAttention内核和CUDA Graph兼容性。我们在vLLM中实现vToken，并使用H2O、Random和Scissorhands跨模型进行评估。与配对的Naive-Evict基线相比，vToken将每个请求保留的KV块减少27.2%至72.3%，并将SLA约束吞吐量提高最多1.37倍。在受约束的活跃KV预算下，它将最大可行并发性扩展最多2倍，同时将每个策略的集成足迹从500多行减少到50行以下。

## Abstract
Large language model serving faces a critical memory bottleneck: the KV cache grows with sequence length and batch size. PagedAttention uses fixed-size memory blocks to reduce allocator-level fragmentation, but recent KV eviction algorithms operate at a token granularity finer than block-level management. This mismatch causes intra-block fragmentation, leaving a large fraction of allocated KV memory unreclaimable. We present vToken, a lightweight token-level virtualization layer that decouples logical token liveness from physical block placement. vToken maintains a stable logical token view through token-table indirection and realizes physical reclamation by repacking live tokens asynchronously. The design preserves PagedAttention kernels and CUDA Graph compatibility. We implement vToken in vLLM and evaluate it with H2O, Random, and Scissorhands across models. Compared with a paired Naive-Evict baseline, vToken reduces retained KV blocks per request by 27.2\%--72.3\% and improves SLA-constrained throughput by up to 1.37$\times$. Under a constrained active-KV budget, it extends the maximum feasible concurrency by up to 2$\times$, while reducing the per-policy integration footprint from 500+ lines to under 50.

## 1. 核心问题与整体含义（研究动机与背景）

- **问题背景**：LLM推理服务中，KV缓存（Key-Value Cache）随序列长度和批大小线性增长，成为决定系统并发度与吞吐量的首要内存瓶颈。例如，13B LLaMA模型在32K上下文下KV缓存即超过25GB，远超模型权重。PagedAttention（vLLM）借鉴操作系统虚拟内存分页，将KV缓存划分为固定大小块（通常16个token/块），以降低外部碎片，成为事实上的运行时基石。
- **核心矛盾（Granularity Mismatch）**：H2O、StreamingLLM、Scissorhands、Random等token级驱逐算法在**单个token粒度**上决定保留/驱逐，但运行时以**块粒度**管理分配与回收。当一个块中同时含有"已驱逐"与"保留"token时，该块整体无法释放，块内空洞（intra-block fragmentation）不可复用。作者在16K上下文下测得，块利用率普遍≤50%，块内浪费比例高达40%–60%，大量GPU内存被"锁定"在低利用率块中。
- **额外代价**：token级策略与块级运行时之间的语义鸿沟，迫使开发者手工将token级决策翻译为块级操作（等待整块清空，或深度修改分配器以迁走存活token），单一H2O策略集成就需要修改超过500行跨模块代码，严重阻碍算法迭代。
- **论文含义**：这是一个缺位的运行时抽象层问题——系统缺少token级活跃性（liveness）与块级回收（reclamation）之间的桥梁。vToken的目标正是在不改变PagedAttention内核与CUDA Graph的前提下，让token级驱逐决策能真正转化为可复用的物理KV容量。降低块大小（16→8/4）并不能消除本质矛盾，只会增加元数据开销与Kernel带宽损失；纯token粒度分配又因GPU分配粒度与元数据膨胀而不可行。因此需要一种既保留块管理效率、又支持token级语义的轻量抽象。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想：Token级虚拟化边界

在驱逐策略与PagedAttention块运行时之间插入**一层轻量token级虚拟化层**，建立双向契约：
- **向上**：对策略暴露token级逻辑视图（逻辑token ID），策略只需声明"哪些token不再需要"，无需感知物理块、slot或重定位时机。
- **向下**：运行时维护token级逻辑地址空间，拥有逻辑→物理映射，负责slot映射刷新与碎片回收决策，实现"决策（deciding）"与"物理回收（reclaiming）"的解耦，使回收可延迟、可批量、可在后台执行。

### 2.2 核心机制一：Token Table（token表）与逻辑地址空间

每个请求维护一张token表，记录每个逻辑token当前物理位置（块ID, 块内偏移）与存活标志。三个接口：
- `evict_token(req_id, token_id)`：逻辑标记token为失活（KV数据仍物理保留，直到回收后端处理）；
- `sync_new_tokens(req_id, block_ids, total_len)`：注册新生成token的物理位置；
- `apply_moves(req_id, moves)`：回收拷贝完成后，原子更新token物理位置。

关键设计细节：
- 表本身与层数/注意力头数无关，仅序列长度线性增长；16K序列约需256KB元数据（<0.1% KV缓存FP16 footprint）。
- CPU侧维护权威表；GPU侧维护查找缓存加速slot翻译，仅在结构性变更（驱逐、重定位）时刷新，append-only增长时增量追加。
- 该设计对策略完全"块不可知"（block-agnostic），策略调用时无需知道token位于何处。

### 2.3 核心机制二：物理回收后端（Reclamation Backend）——懒压缩（Lazy Compaction）

四阶段流程：
1. **回收资格判定（Eligibility）**：维护每块活跃token计数 $n_b$，增量更新碎片率公式 $F = 1 - \frac{\sum n_i}{N \cdot S}$，仅在碎片率超过阈值 $\theta_F$ 且空闲块接近水位线时触发规划，避免频繁扫描全表。
2. **余量感知准入（Headroom-aware Admission）**：为解决"回收启动恰恰需要空闲块但压力最大时无空闲块"的困境，在调度器内保留**有上界的疏散余量（bounded evacuation headroom）**，从现有KV块预算内拨付而非新增内存池。只有余量能提供目标块且预计净释放为正时，计划才被准入。
3. **重定位规划（Relocation Planning）**：请求局部规划。选择低利用率源块，设存活token总数为 $T_{live}$，需要目的块数 $\lceil T_{live}/S \rceil$；仅当释放块数>消耗目的块数时执行。每个move记录（tokenID, 源位置, 目的位置），尽量保持逻辑token顺序以保留缓存局部性。
4. **阶段感知异步拷贝（Stage-aware Asynchronous Copy）**：解码步骤分为Attention forward（HBM带宽瓶颈）、FFN（计算瓶颈）、post-forward（CPU侧逻辑、GPU低利用率）三阶段。vToken**不在attention阶段发起拷贝**（避免带宽争用），而是在forward后于独立CUDA重定位流上启动拷贝，与采样/调度重叠；下一步Attention launch前插入流级CUDA事件wait作为依赖，若拷贝已提前完成则该fence为空操作。整个路径无CPU侧同步阻塞。

### 2.4 正确性不变量（四大保证）

- **I1 Token守恒**：所有重定位事件不改变活跃token的逻辑身份与KV内容；
- **I2 唯一映射**：每个活跃token唯一映射一个物理槽位，且每个占用槽位至多被一个token引用；
- **I3 Attention前可见性**：重定位的KV条目只有拷贝完成后才能被Attention读取（通过CUDA事件依赖保证，以流级wait而非全局同步实现）；
- **I4 布局感知规划**：规划基于一致的块列表与活性快照、同一请求不重叠进行中的规划、且预计块数严格下降时才提交；共享前缀块被保守跳过。

### 2.5 集成流程（与vLLM调度器）

- **Slot映射改造**：原线性计算 slot = block_id × block_size + offset 改为查token表：`slot = token_table[token_id].block_id × S + token_table[token_id].offset`。该翻译在输入预备阶段完成，每个token仅查一次，Attention内核无修改。
- **Hook点**：调度器侧（余量预留）、worker侧（机会式回收启动+异步拷贝）、pre-attention同步（CUDA事件依赖）。
- **CUDA Graph兼容**：不禁用Graph、不重新捕获；KV张量与graph捕获的输入buffer保持稳定，仅replay前按token表更新可变的slot映射buffer；重定位在graph外独立流执行，并通过事件依赖保证看到更新后数据。

## 6. 主要结论与发现

1. **碎片问题是真实且严重的**：token级驱逐作用于vLLM块管理之上时，大多数分配块的利用率≤50%，块内浪费达40%–60%，大量逻辑上已节省的KV容量被物理"困住"。
2. **物理回收带来显著效率提升**：相对于Naive-Evict，vToken将每请求保留KV块数降低27.2%–72.3%（论文摘要与正文表述为16%–85%区间，语义为各种组合下的范围），平均内存利用率提高约21.7%–21.9%。
3. **SLA约束下吞吐显著提升**：Mistral-7B上可行吞吐提升9.9%–37.3%，p95延迟降低9.9%–27.5%；Llama-3.1-8B平均吞吐提升18.9%，p95延迟降低14.7%。
4. **Scissorhands策略受益最大**：由于持久注意力模式使活跃token物理上更分散，vToken提升可达33.3%–103.7%吞吐、降低21.8%–33.0% p95延迟。
5. **容量前沿大幅扩展**：Llama-3.1-8B（gpu_mem_util=0.35）下并发从5扩展到8（+60%），0.50下从11扩展到22（2×）；Qwen2.5-14B下从3扩展到6（2×）。
6. **开销可控**：稳态间接寻址开销<1%（与Native vLLM几乎持平）；异步拷贝消除了显式同步停滞；主要CPU开销来自规划器侧的opportunity checking，可通过批量/索引化优化。
7. **集成成本大幅降低**：策略集成从修改4-6文件500+行，降至1-2文件<50行，策略只需自定义`SelectVictims`钩子。

## 7. 优点与亮点

1. **精准的问题诊断**：将"块内碎片"与"算法集成障碍"统一归因于缺失的运行时抽象层，用形式化定义（碎片率公式）+ 量化实验双重佐证，动机扎实。
2. **设计优雅、侵入性低**：token表间接寻址作为核心抽象，向上保持PagedAttention与CUDA Graph完全兼容（无需kernel改动、无需graph重捕获），向下提供policy-neutral的复用接口，这是相比PagedEviction（强制页对齐策略）、vAttention（页级虚拟化）或Zipage（专用有界缓存管线）的关键差异。
3. **异步回收工程细节扎实**：阶段感知

阶段感知的异步拷贝设计表明作者对LLM推理内核的微架构行为（注意力前向为带宽瓶颈、FFN为计算瓶颈、前后处理为CPU侧低GPU利用率时段）有深入理解，通过CUDA流级调度将重定位从关键路径中剥离，既避免了带宽争用又实现了拷贝与采样的重叠，且用流级事件等待代替全局同步，工程实现精密。
4. **实验方法严谨**：配对对照（Naive-Evict vs vToken）严格隔离变量，正确性不变量（I1/I2）在线校验与Rouge文本质量对比，使"性能提升不以质量或正确性为代价"的论点有实证支撑；补充实验覆盖了内存效率、SLA吞吐、容量前沿、开销、敏感性、前缀缓存等多维度。
5. **集成体验友好、可扩展性好**：以`SelectVictims`单一钩子为接口的设计，将token级策略从块管理的"翻译负担"中解放出来，降低了社区算法落地的门槛；该抽象对策略语义中立（不要求特定驱逐准则），理论上可容纳更多未来驱逐算法。

## 8. 缺点与局限性

1. **验证范围受限（单机单卡）**：论文明确实验仅限单GPU解码快速路径。未在张量并行/流水线并行等生产级多卡配置下验证，尽管讨论部分分析了TP下per-GPU局部token表与余量预留的可行性，但缺乏实证支持。在面向大规模推理服务的现实场景中（通常16–32卡甚至更大），该结论的可迁移性存疑。
2. **语义覆盖不完整（无Preflight/连续批处理边界效应）**：实验完全聚焦解码阶段，未涉及prefill与decode混合调度、长prompt首次解码前的预填充内存行为，也未分析在连续批处理（continuous batching）中请求动态加入/退出对碎片率和回收触发频率的动态影响。
3. **硬件与算力报告的透明性不足**：未报告总GPU小时数、单实验时长、功耗等资源数据，也未报告CPU配置、主机内存带宽、NVMe/存储等因素对异步拷贝与规划开销的间接影响，这降低了实验可复现性与算力审计价值。
4. **工作负载代表性有限**：两个数据集（ShareGPT、LongBench）和一种合成前缀负载覆盖了对话与长文阅读，但未覆盖代码生成、多轮Agent交互、工具调用、检索增强生成等现代生产负载，这些场景的注意力分布与token生命周期差异可能改变碎片化特征；前缀缓存实验使用合成数据，无法反映真实生产中的前缀分布与共享度波动。
5. **模型规模上限较低**：最大验证模型为Qwen2.5-14B，未在70B以上规模验证；虽然容量前沿实验显示2倍扩展，但更大模型下KV缓存与权重占比、块分配粒度与调度开销的相对关系可能发生变化。
6. **对策略语义的隐含依赖未完全量化**：垃圾（Garbage）碎片消除的核心前提是驱逐策略的预测性；对于前瞻性差、驱逐时间戳接近的活跃token（如短视策略），物理重定位的净收益可能大幅缩水，论文对该边界场景的定量分析较薄。
7. **额外元数据开销的长期增长风险**：token表随序列长度线性增长（16K约256KB）虽然绝对值小，但在极高并发（数千请求）或超长上下文（100K+）下，CPU侧表的管理与GPU侧查找缓存的刷新频率可能成为新瓶颈，论文对这类极端配置的扩展性分析较少。

## 9. 综合评价与适用场景建议

### 9.1 综合评价

vToken是一篇典型的系统方向优秀论文：问题诊断精准、抽象设计优雅、工程实现扎实、实验验证系统。它回答了一个关键问题——"当token级驱逐算法与块级缓存管理并存时，系统如何真正兑现内存收益"——并给出了一个兼具理论边界（四大不变量）与工程可行性（CUDA Graph兼容、无内核修改）的解决方案。其核心贡献不是提出新的驱逐策略，而是为策略与运行时之间缺失的一层提供了"缺失的抽象"，这种抽象层的价值往往被低估，但对于系统生态的演进具有重要意义。

### 9.2 适用场景建议

- **最适用**：面向长上下文、高并发的单卡或小规模推理服务（如16K–32K上下文、7B–14B模型），希望在引入token级驱逐算法（H2O/Scissorhands等）时快速获得实际内存收益且不牺牲生成质量的环境。
- **较适用**：需要频繁调整、试验不同驱逐策略的研发团队，vToken的低集成成本（<50行）显著加速策略迭代。
- **需谨慎**：追求严格可审计性与资源共享的多卡生产集群（需先验证TP扩展）、需要同时精确控制prefill/decode交互的场景、以及token生命周期极短且驱逐决策缺乏预测性的工作负载。

### 9.3 延伸思考

该工作为后续研究打开了几条自然方向：① 将token级虚拟化扩展至跨设备/分布式vLLM；② 与prefix caching结合实现"语义级前缀共享"而不受物理块对齐约束；③ 将碎片率的在线监控与动态自适应阈值引入调度决策（如根据当前碎片率自动调节驱逐激进程度）；④ 在更大规模模型与更多生产负载上建立碎片化量化基准。总体而言，这是一篇动机明确、方法自洽、贡献扎实的高质量系统论文，其思想对KV缓存管理乃至更一般的"算法决策与物理回收解耦"设计具有参考价值。
